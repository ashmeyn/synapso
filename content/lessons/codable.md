## Сначала прочитаем вход

Давай сначала прочитаем ответ глазами. Игра 5 называется «Кодовые имена», число игроков — 4. Серверный ключ player_count отличается от Swift-имени playerCount, subtitle может отсутствовать или быть null.

JSON — текстовый формат данных. В Swift нужен Game с типами, а не строка, из которой ты ищешь кусочки вручную. Сегодня получаем байты локально; сетевой слой должен отдельно проверить HTTP-ответ, как в rest.

## Пишем в лоб: имя не совпало

Угадай, какой ключ запросит синтезированный декодер.

```swift
import Foundation
struct Game: Decodable { let id: Int; let title: String; let playerCount: Int }
let data = Data(#"{"id":5,"title":"Кодовые имена","player_count":4}"#.utf8)
do {
    _ = try JSONDecoder().decode(Game.self, from: data)
    print("Прочитано")
} catch DecodingError.keyNotFound(let key, _) {
    print("Нет ключа: \(key.stringValue)")
} catch {
    print("Другая ошибка")
}
```

Вывод «Нет ключа: playerCount». В JSON есть player_count, но без правила сопоставления декодер ищет имя свойства. try! превратил бы такой обычный сбой данных в падение. Не переименовывай JSON мысленно: опиши связь явно.

## Codable задаёт два контракта

Теперь назовём два направления работы. Decodable означает возможность прочитать тип из внешних данных, Encodable — записать его. Codable объединяет оба. JSONDecoder и JSONEncoder — реализации для JSON; Codable не ограничен только этим форматом.

Для простых свойств компилятор может синтезировать нужные методы. String, Int и Optional уже поддерживают эти контракты. Если только читаешь ответ, достаточно Decodable; если планируешь запись и чтение, выбирай Codable. Для нашей карточки покажем оба направления.

## CodingKeys связывает два имени

Окей, объявим модель. CodingKeys — перечисление ключей, а строковое значение case указывает имя во внешних данных.

```swift
struct Game: Codable {
    let id: Int
    let title: String
    let playerCount: Int
    let subtitle: String?
    enum CodingKeys: String, CodingKey {
        case id, title, subtitle
        case playerCount = "player_count"
    }
}
```

Декодер читает id как Int, title как String, player_count как playerCount и subtitle как String?. `Game.self` в вызове decode означает тип, который нужно построить. Список CodingKeys включает все свойства, участвующие здесь в кодировании и декодировании. Он похож на словарь перевода названий полей, а не на команду превратить строку в число.

## Optional не исправляет неверный тип

Тут не торопись добавлять вопросительный знак ко всем полям. Проверь три входа subtitle: отсутствует → nil; null → nil; "" → существующая пустая строка. Оператор ?? даст запасной текст только в первых двух случаях.

Для player_count нужен JSON-номер 4. Строка "4" не соответствует Int и приводит к typeMismatch. Отсутствующий обязательный ключ даёт keyNotFound; null для обязательного значения — valueNotFound. Даже Optional String? не делает число 42 допустимой строкой.

Новые поля is_cooperative: Bool и cover_path: String? подчиняются тем же правилам: true — Bool, "true" — String. Этого достаточно для переноса в последних ступенях.

## Ошибку обрабатываем вокруг decode

Давай прочитаем данные без риска падения. Game уже объявлен. Data создаём из UTF-8 байтов JSON-строки; raw-строка `#"..."#` сохраняет внутренние кавычки.

```swift
let json = #"{"id":5,"title":"Кодовые имена","player_count":4,"subtitle":null}"#
let data = Data(json.utf8)
do {
    let game = try JSONDecoder().decode(Game.self, from: data)
    print(game.title)
    print(game.playerCount)
    print(game.subtitle ?? "Без подзаголовка")
} catch {
    print("Некорректные данные")
}
```

Вывод — название, 4, «Без подзаголовка». try отмечает операцию, которая может бросить ошибку; catch здесь показывает общий ответ, а точную диагностику можно отдельно сохранить для отладки. Различай сломанный JSON-текст и корректный JSON с неподходящими полями: оба не дают рабочую карточку, но причины разные.

## Проверим обратное направление

Продолжим внутри do после создания game. JSONEncoder вернёт Data, затем декодер восстановит модель.

```swift
let encoder = JSONEncoder()
let encoded = try encoder.encode(game)
let restored = try JSONDecoder().decode(Game.self, from: encoded)
print(restored.id)
print(restored.playerCount)
```

Вывод — 5 и 4. Сравниваем значения модели, не порядок ключей JSON: порядок не является частью контракта. При синтезированном кодировании Optional nil обычно пропускает ключ; отсутствие и null читаются одинаково, но не обязаны записываться одинаковым текстом.

Если внешнему API нужен именно null вместо отсутствующего поля, потребуется явное кодирование по его контракту. В наших ступенях достаточно стандартного поведения.

## Собираем декодирование карточки

Окей, теперь соберём самостоятельный пример без сети.

```swift
import Foundation
struct Game: Codable {
    let id: Int
    let title: String
    let playerCount: Int
    let subtitle: String?
    enum CodingKeys: String, CodingKey {
        case id, title, subtitle
        case playerCount = "player_count"
    }
}
let json = #"{"id":5,"title":"Кодовые имена","player_count":4,"subtitle":null}"#
let data = Data(json.utf8)
do {
    let game = try JSONDecoder().decode(Game.self, from: data)
    print(game.title)
    print(game.playerCount)
    print(game.subtitle ?? "Без подзаголовка")
} catch {
    print("Некорректные данные")
}
```

- Несовпадающие имена сопоставляй, неверные типы не маскируй.
- Optional выбирай для допустимого отсутствия, а не чтобы исчезали все ошибки.
- Проверяй decode через do/catch и round trip по значениям.

## Проверь себя

Закрой модель и восстанови путь одного поля.

- Как player_count превращается в playerCount и почему это не превращает "4" в 4?
- Чем для subtitle различаются отсутствие, null и пустая строка?
- Почему после encode/decode сравниваем свойства, а не точный JSON-текст?

## Ответы к «Проверь себя»

- В `CodingKeys` строка `case playerCount = "player_count"` говорит декодеру, под каким внешним ключом искать значение для свойства `playerCount`; без этого правила синтезированный декодер ищет ключ `playerCount` и бросает `keyNotFound`. Это словарь перевода названий, а не преобразование типов: свойство объявлено `Int`, поэтому строка `"4"` даёт `typeMismatch`. Неверный тип исправляет сервер или модель, а не сопоставление имён.
- Для `subtitle: String?` отсутствующий ключ и `null` дают одно и то же `nil`, и `subtitle ?? "Без подзаголовка"` покажет запасной текст. Пустая строка `""` — это существующее значение, поэтому `??` её пропустит и подзаголовок будет пустым. Optional описывает допустимое отсутствие, но не делает допустимым неверный тип: число 42 для `String?` всё равно ошибка.
- Порядок ключей JSON не входит в контракт, а синтезированный кодировщик для `nil` обычно пропускает ключ, хотя на входе мог быть `null`: текст может отличаться при одинаковых данных. Поэтому round trip проверяешь по значениям модели: `let encoded = try JSONEncoder().encode(game)`, `let restored = try JSONDecoder().decode(Game.self, from: encoded)`, затем `restored.id == 5` и `restored.playerCount == 4`.

# ГЛУБЖЕ

## convertFromSnakeCase и явные ключи

Не включай сразу два способа перевода имён. Стратегия decoder.keyDecodingStrategy = .convertFromSnakeCase может переводить имена автоматически. Не смешивай её без проверки с CodingKeys, в которых уже записаны сырые имена player_count: стратегия меняет ключи до сопоставления.

Для нескольких известных полей явные CodingKeys делают контракт заметным. Для большого однообразного ответа стратегия может уменьшить код, но аббревиатуры и особые названия потребуют внимания.

## Начальное значение не всегда запасное

Здесь начальное значение может создать ложное чувство безопасности. Добавить `var playerCount = 4` недостаточно, чтобы синтезированный decode автоматически принимал отсутствие обязательного ключа. Начальное значение свойства и правило внешнего формата — разные вещи.

Если контракт разрешает отсутствующее число и задаёт значение по умолчанию, реализуй init(from:) с decodeIfPresent и явным запасным значением. Не добавляй fallback без договорённости: неверный обязательный ответ может иначе выглядеть корректным.

## Вложенность и даты

Смотри сначала на форму ответа. Если карточка лежит внутри {"game": {...}}, нужна внешняя модель-обёртка или явный разбор вложенного контейнера. CodingKeys сам по себе не делает вложенный объект плоским.

Даты тоже требуют согласованного формата и стратегии декодирования. Сначала посмотри реальные данные и контракт, затем выбирай Date; название поля date не гарантирует подходящий формат.

## decodeIfPresent не проглатывает всё

Даже в собственном декодере не путай отсутствие с повреждением. В собственном init(from:) decodeIfPresent вернёт nil для отсутствующего ключа и null, но неверный тип всё ещё способен бросить ошибку. Это поддержка допустимого отсутствия, не универсальное восстановление повреждённых данных.

Для редактора ошибок сохрани codingPath: он показывает путь к проблемному полю внутри структуры. Пользователю же нужен понятный отказ загрузки, а не сырая техническая диагностика.
