## Что принимаем в PR

Сначала прочитай задачу: список хранит вещи по id, индекс пришёл извне и может быть недопустимым. Review — проверка предлагаемого изменения до объединения. Это как второй взгляд перед отправкой посылки: проверяем содержимое по обещанию, а не меняем упаковку по личному вкусу. Наше обещание — безопасное чтение и удаление после обновления списка.

```swift
struct PackingItem { let id: Int; let title: String }
func titleAt(_ values: [PackingItem], index: Int) -> String {
    guard values.indices.contains(index) else { return "Нет вещи" }
    return values[index].title
}
```

## Попытка в лоб: почти правильная граница

Ниже PR меняет одну строку. Для index=0 и count=1 всё работает, для index=1 возвращаем «Нет вещи»; но index=-1 проходит новый guard и вызывает trap. Размер diff маленький, риск реальный. Перед замечанием назови конкретный вход, который опровергает обещание.

```text
diff --git a/PackingList.swift b/PackingList.swift
--- a/PackingList.swift
+++ b/PackingList.swift
@@ -3,2 +3,2 @@
-    guard values.indices.contains(index) else { return "Нет вещи" }
+    guard index < values.count else { return "Нет вещи" }
     return values[index].title
```

## Замечание, которое можно проверить

Сформулируй вопрос вместе с доказательством: «Блокирует: при index=-1 новый guard пропускает обращение за границу. Можем сохранить проверку indices.contains и добавить тест на -1? Иначе экран падает на недопустимом входе». Вопрос не должен маскировать обязательность: баг блокирует принятие. Для имени helper напиши «не блокирует, предложение» и объясни читаемость.

## Что проверить и что показать самому

В корректности ищи края, идентичность, ошибки и эффекты; в читаемости — понятные имена и лишнюю сложность; в тестах — проверенный контракт и регрессию. Размер PR ограничивай одной связной задачей, а не магическим числом строк. До отправки сам прочитай diff, убери случайные файлы, проверь сценарий и опиши что, почему и как проверил. Не называй компиляцию проверкой поведения.

Для этого PR минимальная регрессия проверяет -1, 0, count и пустой массив. Тест со стабом не доказывает всю работу UI; приложение и окружение проверяются отдельно.

## Краш-отчёт: ищем первый кадр приложения

Crashlytics собирает краши и позволяет анализировать затронутых пользователей, версии, события и контекст. В нашем учебном стеке верхний кадр Swift показывает механизм, первый кадр приложения — место remove(at:). selectedIndex=2 при count=1 объясняет trap; confirm — вызывающая сторона, но не автоматически причина. Ниже намеренно вымышленные данные задачи, не выгрузка сервиса.

```text

Ошибка: индекс за пределами массива, main thread
0 Swift   Array.remove(at:)
1 PackApp PackingList.removeSelected()  PackingList.swift:6
2 PackApp PackingController.confirm()   PackingController.swift:18
Данные воспроизведения: selectedIndex=2, values.count=1
Строка 6: values.remove(at: selectedIndex)
```

## dSYM даёт имена, не объяснение

Символикация переводит адреса в имена функций и доступные строки по символам конкретной сборки. dSYM должен соответствовать бинарнику по UUID; файл от соседнего build не заменяет его. Если кадров приложения ещё нет, добейся подходящих символов, затем ищи воспроизведение. Даже строка со символами — отправная точка: причина может быть в сохранённом старом индексе до обновления списка.

## Группировка, non-fatal и приоритет

Группа issue объединяет связанные события по анализу стека и других признаков; это не гарантия одной причины и не группировка только по номеру строки. Сравнивай число пользователей и влияние, а не только события: два человека могут нажать повторно 80 раз. Non-fatal — пойманная ошибка, записанная явно без завершения приложения; не превращай каждый ожидаемый пустой список в ошибку отчёта. Потеря данных, безопасность и недоступный основной путь могут поднять приоритет выше простого счёта.

## Итог: убрали старую позицию

По контракту отсутствующий выбранный id — уже нечего удалять; выбор после попытки сбрасывается. Исправленный самостоятельный пример ниже хранит selectedID, поэтому обновление порядка и исчезновение вещи не превращают старую позицию в чужую вещь или crash. Пройди сначала 93, которого уже нет, затем 91, который есть.

```swift
struct PackingItem { let id: Int; let title: String }
final class PackingList {
    var values: [PackingItem] = []
    var selectedID: Int?
    func removeSelected() {
        guard let id = selectedID else { return }
        values.removeAll { $0.id == id }
        selectedID = nil
    }
}
let list = PackingList()
list.selectedID = 93
list.values = [PackingItem(id: 91, title: "Куртка")]
list.removeSelected()
assert(list.values.map { $0.id } == [91])
assert(list.selectedID == nil)
list.selectedID = 91
list.removeSelected()
assert(list.values.isEmpty)
```

Self-review: diff решает одну причину, нет force unwrap и кэша индекса, тесты охватывают исчезновение и перестановку id, описание отделяет запуск от компиляции. После выпуска сверяй версию исправления и новые события; отсутствие отчёта сразу не доказывает исчезновение проблемы.

## Проверь себя

Перед одобрением предложи наблюдаемый критерий.

- Какой вход делает маленький diff блокирующим и как спросить о правке?
- Как пройти от кадра Swift через кадр приложения к причине и какой dSYM нужен?
- Чем отличаются число событий, число пользователей и тяжесть, и что входит в self-review?

## Ответы к «Проверь себя»

- Новый `guard index < values.count` пропускает `index = -1`, и `values[index]` падает trap, хотя `0` и `1` при `count = 1` работают. Маленький размер diff не отменяет нарушенного обещания безопасного чтения, поэтому замечание блокирующее и строится как вход + последствие + предложение: «Блокирует: при index=-1 обращение за границу. Можем сохранить `indices.contains` и добавить тест на -1?». Вопросительная форма не маскирует обязательность, а мелочи вроде имени helper помечаешь отдельно как «не блокирует, предложение».
- Верхний кадр `Array.remove(at:)` показывает механизм, поэтому спускаешься до первого кадра приложения — `PackingList.removeSelected()` в строке 6 — и сверяешь данные: `selectedIndex = 2` при `values.count = 1` объясняет trap. `confirm()` ниже — вызывающая сторона, а не автоматически причина: причина в сохранённой старой позиции, и лечится она хранением `selectedID` вместо индекса. Имена и строки даёт dSYM той же сборки, совпадающий с бинарником по UUID; файл от соседнего build не подходит, и даже символы — лишь отправная точка.
- События считают повторы, и два человека могут нажать 80 раз, поэтому приоритет сравниваешь по числу затронутых пользователей и тяжести последствий: потеря данных, безопасность или недоступный основной путь поднимают его выше простого счёта. Self-review до отправки: сам прочитать diff, убрать случайные файлы, проверить сценарий и описать что, почему и как проверил. Регрессия охватывает края (-1, 0, count, пустой массив), а компиляцию не выдаёшь за проверку поведения.

# ГЛУБЖЕ

## Контекст до первой строки приложения

Если верхний кадр указывает на освобождение объекта, причина могла случиться раньше. Сопоставь потоки, ошибку, доступные breadcrumbs и предыдущие действия, затем воспроизведи под debugger. Не объявляй виновным метод лишь потому, что он первый знакомый в стеке.

## Состояние события без личных данных

Для списка можно записать безопасные контекстные поля: count и этап операции. Не отправляй названия личных вещей или весь пользовательский текст ради отладки. Дополнительные ключи помогают сузить воспроизведение, но не восстанавливают каждую строку выполнения; они не заменяют тест и анализ владельца состояния.

## Как записать non-fatal осмысленно

Если экспорт списка не смог подготовить шаблон, покажи человеку понятное восстановимое состояние и при необходимости запиши одну диагностическую ошибку через адаптер. В Firebase SDK для этого есть record(error:); адаптер позволяет тестировать свой сценарий без SDK и сети. Не вызывай fatalError только ради появления отчёта: это меняет восстановимую ошибку на искусственный краш.

## Рабочий спор в review

Когда исправление понятно, не обсуждай стиль в каждом файле того же PR. Отдели обязательный край от предложения, договорись о критерии теста и проверь итоговый diff после правки. Если предлагаешь большую смену архитектуры, покажи связанную проблему и вынеси отдельную задачу, иначе небольшое исправление застрянет без пользы.
