## Сначала сохрани смысл списания

Назови правило: остаток 2, take(1) успешен, следующий take(2) должен вернуть false и сохранить 1. Lock нужен для целого перехода «проверил → уменьшил», включая чтения состояния.

## Пишем в лоб: оба увидели два

Проиграй модель без настоящей гонки потоков: оба обращения запомнили доступные 2 и решили взять по 2. Каждый записал 0; приняты два списания при запасе на одно.

```swift
var available = 2
let first = available
let second = available
let acceptedFirst = first >= 2
let acceptedSecond = second >= 2
available = first - 2
available = second - 2
print(acceptedFirst, acceptedSecond, available)
```

Вывод true true 0. Это последовательная модель потерянного обновления и ошибочного допуска, а не безопасное предсказание результата настоящего data race.

## Lock защищает критическую секцию

Объяви один private NSLock и весь доступ проводи через него. lock.lock() блокирует вызывающий поток, если ресурс занят. После успешного захвата сразу ставь defer unlock: ранний return тоже освободит ресурс.

```swift
func take(_ amount: Int) -> Bool {
    lock.lock(); defer { lock.unlock() }
    guard amount > 0, available >= amount else { return false }
    available -= amount
    return true
}
```

Это метод ToolStock с lock и available из итога. Аналогия: ключ от одного шкафа остаётся у тебя на всё списание, а не только на просмотр остатка. Другой путь с другим lock этот шкаф не защищает.

## Защищай чтение, не только изменение

Добавь read через тот же lock. Незащищённый getter может пересечься с записью; короткое свойство не становится безопасным само собой.

```swift
func read() -> Int {
    lock.lock(); defer { lock.unlock() }
    return available
}
```

Возвращается Int-снимок. unlock должен выполнить тот же поток, который захватил NSLock. Не передавай освобождение ресурса произвольному callback на другом потоке.

## Подвох: публичный read уже берёт lock

Найди скрытый повтор: take захватил lock и вызывает read, который делает lock.lock ещё раз. NSLock нерекурсивен; этот вызов неправильный и может зависнуть или получить диагностику. Для успешного запуска его не используем.

```swift
func take(_ amount: Int) -> Bool {
    lock.lock(); defer { lock.unlock() }
    guard amount > 0, read() >= amount else { return false }
    available -= amount
    return true
}
```

Исправление внутри уже захваченной секции — читать available напрямую. Если нужен private helper без захвата, явно закрепи его условие «вызывать только под lock», не открывай его снаружи.

## Не держи NSLock через await

Перед вызовом async-источника сделай короткий синхронный метод снимка и отпусти lock. После await снова возьми lock и заново проверь нужное условие. Поток после приостановки может быть другим; блокирующий lock нельзя переносить через эту паузу.

## Выбери контракт, затем механизм

Сравни варианты на одном take. NSLock защищает синхронную секцию и при конфликте блокирует поток. Serial queue с sync тоже заставляет caller ждать; async требует отдельного контракта результата. Actor позволяет внешней задаче ожидать через await без блокировки потока ради этого ожидания, но после внутреннего await состояние могло измениться. Составная проверка и изменение должны оставаться неделимыми в выбранном механизме.

## Итог: запас меняется только под владельцем

Собери ToolStock и проверь три строки. Методы синхронные и короткие, без await, тяжёлых расчётов и неизвестных callback под lock.

```swift
import Foundation
final class ToolStock {
    private let lock = NSLock()
    private var available = 2
    func take(_ amount: Int) -> Bool {
        lock.lock(); defer { lock.unlock() }
        guard amount > 0, available >= amount else { return false }
        available -= amount
        return true
    }
    func read() -> Int {
        lock.lock(); defer { lock.unlock() }
        return available
    }
}
let stock = ToolStock()
print(stock.take(1))
print(stock.take(2))
print(stock.read())
```

Вывод true, false, 1. Два конкурентных take(2) смогут успешно списать только один раз: второй увидит уже изменённый остаток. Успешный прогон теста сам по себе не доказывает отсутствие всех гонок приложения.

## Проверь себя

Проверь все выходы и границу ожидания.

- Почему defer ставится сразу после lock?
- Почему read нельзя вызывать из take под тем же NSLock?
- Что меняется в контракте при переходе на actor?

## Ответы к «Проверь себя»

- `defer` выполняется при любом выходе из метода, включая ранний `return` из `guard`. Если поставить его сразу после успешного захвата — `lock.lock(); defer { lock.unlock() }`, — то ни один путь не уйдёт с удержанным lock. Иначе отказной `return false` оставит шкаф запертым, и следующий `take` или `read` навсегда заблокирует свой поток.
- `read()` сам делает `lock.lock()`, а `take` уже держит этот lock. NSLock нерекурсивен: повторный захват тем же потоком не проходит, вызов неправильный и может зависнуть или получить диагностику. Поэтому внутри уже захваченной секции читаешь `available` напрямую, а помощник без захвата, если нужен, делаешь `private` с условием «вызывать только под lock».
- NSLock при конфликте блокирует поток, а actor позволяет внешней задаче ждать через `await` без блокировки потока ради этого ожидания. Поэтому вызывающий код меняется: вместо обычного `stock.take(1)` пишешь `await stock.take(1)`, и ждёт задача, а не заблокированный поток. Зато после внутреннего `await` состояние актора могло измениться, так что проверку и списание держишь неделимыми — в одном сегменте без паузы между ними.

# ГЛУБЖЕ

## Recursive lock не решает любой цикл

Не лечи архитектуру простой заменой на NSRecursiveLock. Он позволяет повторный захват тем же потоком, но не устраняет взаимное ожидание двух ресурсов, долгую секцию или несогласованный доступ без владельца.

## Не запускай чужой callback под lock

Сначала скопируй нужное значение, отпусти lock, затем вызови callback. Он может снова обратиться к объекту или захватить другой ресурс. Если после callback нужен переход состояния, войди в новую секцию и перепроверь условие.

## Снимок пары и утечка изменяемой ссылки

Для нескольких полей возвращай согласованный снимок одним захватом. Если вернул элемент-класс, caller может менять его без lock; вместо этого возвращай значение или копию с понятным контрактом. Защищённый контейнер не защищает любые ссылки, которые из него вынесли.

## await и строгая диагностика

Оставляй lock/unlock внутри синхронного helper, который завершается до await. Современный SDK диагностирует прямой вызов этих методов из async-контекста; режим Swift 5 не делает перенос lock через await корректным. Sendable для обёртки тоже требует обоснования всех путей доступа, а не только добавления аннотации.

## Лёгкий lock с состоянием внутри

С iOS 16 есть OSAllocatedUnfairLock из модуля os. Он хранит защищаемое значение в самом lock и даёт доступ только через withLock, поэтому забыть unlock или тронуть значение снаружи нельзя.

```swift
import os
final class TapCounter {
    private let state = OSAllocatedUnfairLock(initialState: 0)
    func tap() { state.withLock { $0 += 1 } }
    func read() -> Int { state.withLock { $0 } }
}
```

«Unfair» значит без очереди: lock получает тот, кто успел, — это быстрее. Он тоже нерекурсивный, и тело withLock синхронное: await внутри не напишешь, долгие операции туда не клади.
