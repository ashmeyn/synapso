## Начни с наблюдения на экране

Проследи сценарий: экран открыт, пульсы идут; пользователь прокручивает список, обновления задерживаются. Главный поток не обязан зависнуть: RunLoop мог обслуживать другой режим. RunLoop — цикл обработки источников событий и таймеров потока; главный UI-цикл запускается инфраструктурой приложения.

## Пишем в лоб: только обычный режим

Сначала проиграй явную модель: normal представляет .default, tracking — режим отслеживания прокрутки UIKit. Здесь moveToNextFire — метод нашего ModeModel, не API Foundation и не ожидание реального времени.

```swift
enum ClockMode { case normal, tracking }
struct ModeModel {
    var common = false
    var ticks = 0
    mutating func moveToNextFire(in mode: ClockMode) {
        if common || mode == .normal { ticks += 1 }
    }
}
var clock = ModeModel()
clock.moveToNextFire(in: .normal)
clock.moveToNextFire(in: .tracking)
print(clock.ticks)
```

Вывод 1. В модели tracking не обслуживает default-only таймер. Она объясняет правило выбора режима, а не проверяет настоящий скролл.

## Режим выбирает обслуживаемые источники

Запомни границу: Timer.scheduledTimer регистрируется в .default текущего RunLoop. Во время UIKit tracking default-only таймер может не срабатывать; после возврата в подходящий режим он снова обслуживается. .common — набор общих режимов, не отдельный режим исполнения и не «все режимы вообще». В обычном UIKit-приложении он охватывает default и tracking.

## Добавляем в common явно

Создай Timer без автоматической регистрации (не scheduledTimer) и добавь его в RunLoop.main с .common. Вызов выполняется на главном потоке. Интервал 3600 нужен только чтобы ручная проверка не ждала ближайшего автоматического события.

```swift
import Foundation
func makeCommonTimer(tick: @escaping () -> Void) -> Timer {
    precondition(Thread.isMainThread)
    let timer = Timer(timeInterval: 3600, repeats: true) { _ in
        tick()
    }
    RunLoop.main.add(timer, forMode: .common)
    return timer
}
```

Пульс получает tick через замыкание. .common не помогает, если главный поток заблокирован долгой работой; режим регистрации не создаёт отдельного исполнителя.

## Удержание: таймер не слабая ссылка

Нарисуй связи: RunLoop удерживает зарегистрированный Timer; Timer удерживает target либо блок; блок может сильно захватить self, а self хранит Timer. [weak self] разрывает захват владельца, invalidate снимает таймер с обслуживания. Одна мера не заменяет другую. Аналогия: слабый адрес получателя не отменяет запущенную рассылку.

## Подвох: повторный start оставил первый таймер

Проверь старый handle перед заменой: присвоить новый Timer свойству недостаточно, RunLoop продолжит держать первый. Сначала invalidate старый, затем создай и сохрани новый. При уходе с экрана вызывай stop на том же потоке, где таймер установлен; не рассчитывай только на deinit, который цикл может не допустить.

## Ручной fire и фоновый RunLoop

Вызови timer.fire() вручную, чтобы проверить действие и состояние, затем invalidate и проверь isValid. fire не доказывает регистрацию в нужном режиме. На созданном фоновом Thread RunLoop не начинает крутиться от одного обращения к RunLoop.current или scheduledTimer; ему нужно явное обслуживание и условие выхода. DispatchQueue не является владельцем выделенного потока с постоянным RunLoop.

## Итог: владелец не захвачен сильно

Собери модель экрана: start/stop и обращения к ticks выполняются на главном потоке. [weak self] позволяет владельцу освободиться; если его уже нет при событии, блок останавливает оставшийся таймер.

```swift
import Foundation
final class LessonClock {
    private(set) var ticks = 0
    private(set) var timer: Timer?
    func start() {
        precondition(Thread.isMainThread)
        stop()
        let next = Timer(timeInterval: 3600, repeats: true) {
            [weak self] timer in
            guard let self else { timer.invalidate(); return }
            self.ticks += 1
        }
        timer = next
        RunLoop.main.add(next, forMode: .common)
    }
    func stop() {
        precondition(Thread.isMainThread)
        timer?.invalidate()
        timer = nil
    }
}
```

После start и двух ручных fire ticks равен 2. После stop старый handle имеет isValid == false, свойство timer — nil. Это проверка действия и жизненного цикла; реальную прокрутку проверяют отдельно в UIKit.

# ГЛУБЖЕ

## Не считай время числом событий

Если нужен обратный отсчёт, считай остаток от deadline и текущего времени, а не уменьшая число на каждом tick. Timer может опаздывать и не является точными часами; после задержки не обещай событие на каждый пропущенный интервал.

## Одно событие и tolerance

Для напоминания выбери repeats: false: после срабатывания таймер инвалидируется автоматически. Для повторяющегося таймера tolerance допускает дополнительный сдвиг ради эффективности; она не исправляет неправильный режим или заблокированный поток.

## target требует явного teardown

В target/selector-варианте Timer сильно держит target до invalidation. Нужно внешнее событие stop, пока владелец ещё доступен. Не обещай, что deinit сам разорвёт связь, которая не даёт ему начаться.

## Combine и фоновое обслуживание

Для Combine аналог — Timer.publish(every: 1, on: .main, in: .common).autoconnect(); отменяй подписку при окончании её жизненного цикла. Если всё же нужен фоновый RunLoop, организуй отдельный поток, обслуживаемый режим, источники и выход; не запускай бесконечный цикл ради одного UI-таймера.
