## Закрыт ли экран для памяти

Начни с контракта: после закрытия экран 9 больше не нужен и внешних владельцев быть не должно. Просто отсутствие deinit пока ничего не доказывает — сначала выясним, какие ссылки мы оставили.

Вместо настоящего таймера используем PulseSource, который хранит действие и вызывает его только по tick(). Это позволяет воспроизвести удержание без RunLoop, оборудования и Xcode.

## Пишем в лоб: источник держит действие

Нарисуй стрелки после start: экран владеет source, source владеет onTick, замыкание сильно захватывает self. Последняя стрелка возвращается к экрану.

```swift
final class PulseSource {
    var onTick: (() -> Void)?
    func tick() { onTick?() }
}
final class BreathingScreen {
    let id = 9
    let source = PulseSource()
    func start() { source.onTick = { print(self.id) } }
    func close() { source.onTick = nil }
    deinit { print("Экран дыхания освобождён") }
}
```

screen = nil удаляет внешнюю ссылку, но цикл остаётся. В этом опыте закрытие — удаление внешнего владельца; метод close отдельно очищает действие и нужен для проверки исправления.

## Наблюдаем, не становясь владельцем

Добавь weak-наблюдателя к экрану до удаления внешнего владельца. Он не поддерживает жизнь объекта: nil после освобождения поможет проверить исходную гипотезу. BreathingScreen и PulseSource уже объявлены выше.

```swift
var screen: BreathingScreen? = BreathingScreen()
weak var observer = screen
screen!.start()
screen = nil
print(observer == nil)
observer?.close()
print(observer == nil)
```

Вывод false, «Экран дыхания освобождён», true. Первый false показывает, что экран удерживается. Затем observer?.close() временно обращается к живому объекту и разрывает цикл; после возврата объект освобождается. Это уборка демонстрации, не стратегия для недоступного утёкшего объекта.

## Читаем кто держит, а не где создан

Теперь проговори граф: BreathingScreen → PulseSource → onTick → BreathingScreen. Все три связи сильные, внешняя screen уже nil. Замкнутая цепь объясняет, почему объект остаётся жив.

Аналогия: ищешь не место, где вещь выдали, а руки, которые сейчас её держат. Стек создания помогает найти код рождения; входящие связи помогают найти текущего владельца. Это разные вопросы.

## Исправляем ту связь, которая необязательна

Замени захват на weak self: событие после закрытия может не обновлять экран, поэтому источник не обязан владеть получателем. Здесь -1 — локальная отметка отсутствующего получателя, не номер реального экрана.

```swift
final class BreathingScreen {
    let id = 9
    let source = PulseSource()
    func start() { source.onTick = { [weak self] in print(self?.id ?? -1) } }
    func close() { source.onTick = nil }
    deinit { print("Экран дыхания освобождён") }
}
```

Экран по-прежнему владеет источником, но путь от действия к экрану больше не сильный. Если источник сохранён снаружи, его действие может ещё существовать; это не мешает освобождению экрана.

## Уборка работы и владение

Сохрани второй способ исправления: при явном close можно удалить onTick ещё до screen = nil. После этого сильный захват исчезает. Не вызывай close только из deinit циклического объекта: до deinit он как раз не добирается.

В живом приложении остановка таймера, отмена запроса или отписка зависят от API источника. Наш close удаляет локальное действие, а не обещает отменить любую систему событий.

## Как проверить этот случай в Memory Graph

Для реального приложения повтори тот же сценарий: запусти Debug-сборку, открой экран, начни упражнение, закрой его. Затем нажми Debug Memory Graph в панели отладки Xcode; приложение приостановится для снимка. Здесь Xcode не запускаем — это инструкция для проверки в лаборатории.

- Найди тип BreathingScreen и выбери оставшийся экземпляр. Если тип переименован, ищи фактический класс экрана.
- Проследи входящие связи от замыкания или контекста, затем от источника, затем обратно от экрана. Уточни в инспекторе вид связи; не считай каждую стрелку сильной автоматически.
- Найди конкретное свойство или захват в исходнике, исправь его, заново запусти тот же сценарий и сравни снимок.

Названия узлов контекста замыкания могут отличаться от onTick. Не ищи обязательный фиолетовый значок: важно, кто удерживает ненужный экземпляр, а не цвет подсказки.

## Итог: проверка до и после

Собери локальный пример с источником, оставшимся снаружи. Первый tick печатает 9; после screen = nil вывод deinit и true подтверждают освобождение в этой модели. Источник может жить отдельно.

```swift
final class PulseSource {
    var onTick: (() -> Void)?
    func tick() { onTick?() }
}
final class BreathingScreen {
    let id = 9
    let source = PulseSource()
    func start() { source.onTick = { [weak self] in print(self?.id ?? -1) } }
    func close() { source.onTick = nil }
    deinit { print("Экран дыхания освобождён") }
}
var screen: BreathingScreen? = BreathingScreen()
weak var observer = screen
let source = screen!.source
screen!.start()
source.tick()
screen = nil
print(observer == nil)
source.onTick = nil
```

Исправление проверено поведением, а не только наличием weak в тексте. Для настоящего экрана останется повторить его реальный сценарий и проверить граф: модель не доказывает состояние всего приложения.

## Проверь себя

Расскажи диагностику человеку, который не видел исходник.

- Какая цепочка удерживает экран после удаления screen?
- Почему weak-наблюдатель не добавляет ещё одного владельца?
- Почему отсутствие deinit без проверки остальных владельцев недостаточно для вывода об утечке?

## Ответы к «Проверь себя»

- После `screen = nil` остаётся замкнутая цепь: `BreathingScreen` → `source` → `onTick` → `BreathingScreen`, потому что замыкание `{ print(self.id) }` сильно захватывает `self`. Все три связи сильные, поэтому внешняя ссылка ушла, а экран жив и `deinit` не печатается. Чинишь необязательную связь: `[weak self]` в `onTick` или `close()` с `source.onTick = nil` до удаления экрана.
- `weak var observer = screen` не удерживает объект и сам становится `nil`, когда экран освобождён. Поэтому он не меняет число владельцев и не мешает эксперименту, а лишь показывает, жив ли объект: `observer == nil` даёт false, пока экран удерживают, и true после освобождения. Сильный наблюдатель сам стал бы ещё одним владельцем и испортил бы проверку.
- Отсутствие `deinit` говорит только, что у объекта ещё есть сильный владелец, но не говорит, кто это. Это может быть цикл, а может быть обычная внешняя ссылка, которую ты сам оставил. Поэтому сначала читаешь входящие связи (на модели — по стрелкам, в приложении — в Memory Graph) и находишь конкретное свойство или захват, а потом проверяешь исправление поведением: `deinit` и `observer == nil`.

# ГЛУБЖЕ

## Instruments: сравниваем повторения

В Xcode выбери Product → Profile и открой шаблон с Allocations; при необходимости добавь Leaks. Начни запись, сделай несколько одинаковых циклов открытия и закрытия экрана, отметь поколения или сравни интервалы и живые экземпляры целевого типа. Это план ручной проверки, не выполненный здесь профиль.

Allocations помогает увидеть рост и оставшиеся выделения. Leaks ищет определённые утечки, но отсутствие его предупреждения не доказывает отсутствие лишнего удержания. Входящий путь к ещё достижимому объекту ищи также через Memory Graph.

## Кэш и история тоже могут удерживать

Проверь корень: если экран хранится в recent, существует путь от обычного внешнего владельца. Для освобождения нужно удалить его оттуда; замена захвата на weak не очищает массив.

Если такая история нужна продукту, объект удерживается намеренно. Если экран уже не нужен, это лишнее удержание. Рост памяти может быть связан с этим, с циклами или другими ресурсами; по одному графику нельзя выбрать причину.

## Наблюдатель может испортить проверку

Не добавляй let saved = observer перед проверкой nil: разворачивание слабой ссылки создаёт временного сильного владельца. Пока он нужен коду, объект остаётся живым уже по причине самого теста.

Используй короткую проверку observer == nil после явного удаления известных владельцев. Не делай вывод о точном времени deinit любого локального let только по закрывающей скобке; оптимизация времени жизни и другие владельцы требуют отдельного разбора.

## Проверка освобождения не заменяет профиль

Повтори локальную проверку несколько раз и сохрани weak-наблюдатели вместо самих экранов. Так тест не создаёт дополнительный контейнер сильных владельцев. Для каждого завершённого экземпляра ожидаем nil.

Этот тест ловит конкретную регрессию владения. Он не измеряет RSS, графический буфер, системный кэш или все объекты приложения. После исправления снова проверь реальный экран и источник событий в Xcode.
