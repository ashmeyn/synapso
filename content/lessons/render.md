## Новая величина — ещё не новый кадр

Уровень изменился с 20 до 80. Если меняешь ширину дочернего слоя, нужна раскладка; если рисуешь полоску сам, нужно обновить содержимое. Начни с вопроса «что именно устарело?». RunLoop главного потока обрабатывает события и работу приложения; обновления view/layer обычно накапливаются до обработки раскладки, display и commit.

## Пишем в лоб: не тот запрос

В ProgressLayer метод layoutSublayers вычисляет fill.frame по percent. После начального layout ширина fill=20. Следующий фрагмент продолжает этот контекст: меняем percent, но просим только display. Ручной layoutIfNeeded не обязан пересчитывать чистую геометрию, поэтому ширина остаётся 20.

```swift
layer.percent = 80
layer.setNeedsDisplay()
layer.layoutIfNeeded()
print(Int(layer.fill.frame.width))
```

Объявления ProgressLayer и исходная настройка полностью даны в практике. Исправление — запрос нужного прохода, а не принудительный вызов метода раскладки напрямую.

## layout: пометить или выполнить

Представь обновления как очередь правок чертежа: setNeedsLayout отмечает устаревшую геометрию, layoutIfNeeded выполняет нужную раскладку сейчас. У UIView обработчик — layoutSubviews, у CALayer — layoutSublayers. Публичный getter needsLayout() относится к CALayer; не придумывай UIView.needsLayout().

```swift
layer.setNeedsLayout()
assert(layer.needsLayout())
layer.layoutIfNeeded()
assert(!layer.needsLayout())
```

Здесь layer — самостоятельный CALayer из ручного контекста. У view для проверки флага можно смотреть view.layer, но это не доказательство, что все потомки или весь кадр уже готовы.

## display: обновить собственное рисование

Для custom LevelView хранится level. При его изменении setNeedsDisplay сообщает, что содержимое нужно нарисовать заново. Следующий метод находится внутри этой UIView, где объявлено `private(set) var level = 20`. Не проси layout, если меняются только пиксели в прежних bounds.

```swift
func updateLevel(_ value: Int) {
    let next = min(max(value, 0), 100)
    guard next != level else { return }
    level = next
    setNeedsDisplay()
}
```

setNeedsDisplay не вызывает draw синхронно в этой строке. Не каждое изменение UI требует draw: многие свойства слоёв меняют композицию уже готового содержимого.

## draw получает контекст

В той же LevelView переопредели draw и используй текущий UIGraphics-контекст. UIKit предоставляет его при рисовании; вне подходящего контекста он может отсутствовать. Ширина рисуемой полосы берётся из актуальных bounds и level. Прочитай отдельно источник данных и источник размеров.

```swift
override func draw(_ rect: CGRect) {
    guard let context = UIGraphicsGetCurrentContext() else { return }
    context.setFillColor(UIColor.systemTeal.cgColor)
    context.fill(CGRect(
        x: 0, y: 0, width: bounds.width * CGFloat(level) / 100,
        height: bounds.height
    ))
}
```

Ручной вызов draw внутри bitmap-renderer проверяет тело рисования, а не автоматическое планирование UIKit. Не запускай тяжёлое декодирование или загрузку файла внутри draw.

## После display ещё есть commit

В обычном цикле приложение раскладывает нужные элементы и обновляет запрошенное содержимое, затем Core Animation фиксирует транзакцию дерева слоёв и передаёт данные в render server. Тот готовит композицию с помощью GPU для показа. Это схема, не обещание одного callback каждого вида: изменения могут потребовать повторных проходов. Не называй возврат из layoutIfNeeded моментом готового экранного кадра.

## Почему main задерживает показ

Тяжёлая работа на главном потоке может задержать события, layout, display или commit; кадр не успевает к нужному показу. Интервал при 60 Гц около 16.7 мс, при 120 Гц около 8.3 мс — ориентир для всего кадра, не выделенный бюджет твоей функции. Частота может меняться. Подготовь данные вне критического участка, затем примени готовое состояние на main; конкретные причины задержки подтверждаются измерениями, не только флагами.

## Итог: явный ручной проход слоя

Наш TraceLayer журналирует настоящие layoutSublayers и display. Очистим начальные события, пометим обе работы, затем вызовем их явно по порядку. Это проверяет обработчики и dirty-флаги standalone CALayer; не имитирует render server или RunLoop целого приложения.

```swift
import QuartzCore
import CoreGraphics
final class TraceLayer: CALayer {
    var events: [String] = []
    override func layoutSublayers() {
        super.layoutSublayers()
        events.append("layout")
    }
    override func display() {
        events.append("display")
        super.display()
    }
}
let layer = TraceLayer()
layer.bounds = CGRect(x: 0, y: 0, width: 100, height: 40)
layer.layoutIfNeeded()
layer.displayIfNeeded()
layer.events.removeAll()
layer.setNeedsLayout()
layer.setNeedsDisplay()
layer.layoutIfNeeded()
layer.displayIfNeeded()
assert(layer.events == ["layout", "display"])
```

layoutIfNeeded и displayIfNeeded здесь вызваны вручную. Журнал layout → display не доказывает автоматический порядок всех UIKit callbacks или отсутствие пропущенных кадров.

## Проверь себя

Закрой код и выбери нужный запрос для каждого изменения.

- Как отличается ширина дочернего элемента от пикселей внутри прежних bounds?
- Почему setNeedsDisplay не означает немедленный draw, а layoutIfNeeded не означает завершённый commit?
- Почему несколько setNeedsLayout можно собрать перед одним явным проходом?

## Ответы к «Проверь себя»

- Ширина дочернего элемента — геометрия, поэтому просишь layout: `setNeedsLayout()`, и пересчёт идёт в `layoutSublayers` (у UIView — `layoutSubviews`). Пиксели внутри прежних bounds — собственное содержимое: `setNeedsDisplay()`, и позже вызовется `draw`. Перепутаешь — получишь ошибку из урока: после `percent = 80` с одним `setNeedsDisplay()` ручной `layoutIfNeeded()` не пересчитывает чистую геометрию, и fill остаётся шириной 20.
- `setNeedsDisplay()` лишь помечает содержимое устаревшим; `draw` вызовется позже, в проходе display, а не в этой строке. `layoutIfNeeded()` выполняет раскладку сейчас, но за ней в цикле ещё идут display, commit транзакции дерева слоёв, render server и GPU. Поэтому возврат из `layoutIfNeeded()` — не готовый кадр на экране, и проверять это время им нельзя.
- `setNeedsLayout()` не выполняет работу, а только ставит флаг «геометрия устарела»; повторная пометка ставит тот же флаг, как правка в очереди чертежа из урока. Один `layoutIfNeeded()` в конце выполнит `layoutSublayers` один раз и прочитает последнее значение: после `percent` 30, 50, 80 получишь `passes == 1` и ширину 80. Так промежуточные значения не тратят время кадра на лишние проходы.

# ГЛУБЖЕ

## Offscreen rendering

Если для эффекта нужен промежуточный render target, затем его результат участвует в композиции — это offscreen rendering. Маска или вычисляемая по альфа-содержимому тень могут потребовать дополнительной работы; конкретное поведение зависит от эффекта и системы. Не объявляй каждый cornerRadius обязательным offscreen-pass.

## shadowPath и маски

При известной форме shadowPath даёт готовый контур и может уменьшить необходимость определять его по содержимому. Сложная mask может потребовать промежуточного результата. Проверь форму и актуальность пути после layout; одни свойства слоя не измеряют стоимость эффекта и не доказывают, что offscreen исчез.

## Не заставляй каждый setter раскладывать всё

setNeedsLayout коалесцирует запросы: несколько пометок до прохода не обязаны давать несколько обработок. В ручном контексте измени модель несколько раз, помечай после каждого изменения, а layoutIfNeeded вызови один раз в конце. Синхронная раскладка нужна, когда следующая операция действительно читает готовую геометрию.

## Измерения и честная граница

Без Instruments и настоящего отображения мы не проверяем fps, GPU-проходы и соблюдение дедлайна кадра. Ручной лог и флаги показывают только исполненную работу в конкретном дереве. Даже CATransaction.commit не означает, что изображение уже показано пользователю.
