## Где находится рамка

Сначала спроси: относительно кого заданы числа? Окно `viewport` стоит в `root` в точке (40,30), рамка `marker` — внутри окна в (70,20). Без преобразований и с нулевыми bounds.origin начало рамки в корне будет (110,50). В этом уроке все view созданы кодом, без Auto Layout.

```swift
import UIKit
let root = UIView(frame: CGRect(x: 0, y: 0, width: 320, height: 200))
let viewport = UIView(frame: CGRect(x: 40, y: 30, width: 120, height: 80))
let marker = UIView(frame: CGRect(x: 70, y: 20, width: 20, height: 10))
root.addSubview(viewport)
viewport.addSubview(marker)
```

## Пишем в лоб: складываем позиции

Такое сложение кажется удобным, пока окно не сдвинуло свою область просмотра. Попробуй указать, какое число забыли: ниже guess даёт (110,50), а convert — (85,45). Фрагмент продолжает ранее объявленное дерево.

```swift
viewport.bounds.origin = CGPoint(x: 25, y: 5)
let guess = CGPoint(
    x: viewport.frame.minX + marker.frame.minX,
    y: viewport.frame.minY + marker.frame.minY
)
let actual = marker.convert(CGPoint.zero, to: root)
print(guess == actual)
```

Вывод — false. Позиция дочерней view выражена в локальных координатах родителя; они могут иметь ненулевое начало и transform.

## frame отвечает: где я у родителя

`frame` задаёт положение и размер view в координатах superview, когда transform единичный. Не смешивай его с локальной системой самого элемента. Для нашего окна x=40, y=30, ширина 120, высота 80; origin относится к корню, не к пикселям фотографии.

Представь bounds как участок карты в рамке, а frame — место рамки на столе: сдвиг участка не обязан передвигать рамку.

## bounds отвечает: что видно внутри

Поменяй начало bounds на (25,5). Левый верхний край окна теперь соответствует локальной точке (25,5), поэтому дочерние элементы визуально смещаются на −25 и −5. В нашем случае frame окна остаётся прежним. Так устроена модель прокрутки: `UIScrollView` управляет областью через contentOffset и bounds, но здесь мы меняем UIView вручную.

```swift
viewport.bounds.origin = CGPoint(x: 25, y: 5)
print(viewport.frame.origin)
print(viewport.bounds.origin)
```

Фрагмент продолжает дерево миссии. bounds не обязан начинаться с нуля; не вычитай origin вручную в каждом месте приложения.

## Переводим координаты штатным инструментом

Теперь поручим UIKit пройти всё дерево координат. `marker.convert(_:to:)` принимает точку в координатах marker и возвращает её в координатах root. Для прямоугольника передай marker.bounds. Назови, чей прямоугольник ты переводишь, до вызова.

```swift
let point = marker.convert(CGPoint.zero, to: root)
let rect = marker.convert(marker.bounds, to: root)
assert(point == CGPoint(x: 85, y: 45))
assert(rect == CGRect(x: 85, y: 45, width: 20, height: 10))
```

Продолжаем дерево со сдвигом bounds. Преобразование учитывает родителей, origins и transforms; одинаковые числовые координаты разных view не означают одно место.

## Подвох: transform и охватывающий прямоугольник

При повороте или масштабе видимая область может занимать другой прямоугольник у родителя. Но Apple считает свойство frame неопределённым при неединичном transform: не задавай его и не строй на его значении контракт. Получи охватывающий прямоугольник через convert(bounds,to:), а содержимое и размещение меняй через bounds и center. Попробуй отдельно назвать размер содержимого и его масштаб.

## Размер содержимого и центр

В отдельном примере ниже viewport уже добавлен в root и пока имеет единичный transform. Сначала задаём локальную область 80×40 и центр (100,80), затем масштаб ×2. convert покажет область 160×80 с началом (20,40); локальный bounds останется 80×40.

```swift
viewport.bounds = CGRect(x: 0, y: 0, width: 80, height: 40)
viewport.center = CGPoint(x: 100, y: 80)
viewport.transform = CGAffineTransform(scaleX: 2, y: 2)
let envelope = viewport.convert(viewport.bounds, to: root)
```

Сверяй вычисления с допуском для CGFloat. Охватывающий прямоугольник после поворота — не точная форма повернутой view и не её зона касания.

## Итог: рамка в соседнем слое

Собери знакомое дерево со сдвигом окна, затем добавь слой подсказок в корень. Нам нужно положение рамки в overlay, а не в root: отправителем остаётся marker, получателем становится overlay. Восстанови (75,40), прежде чем читать итог.

```swift
import UIKit
let root = UIView(frame: CGRect(x: 0, y: 0, width: 320, height: 200))
let viewport = UIView(frame: CGRect(x: 40, y: 30, width: 120, height: 80))
let marker = UIView(frame: CGRect(x: 70, y: 20, width: 20, height: 10))
root.addSubview(viewport)
viewport.addSubview(marker)
viewport.bounds.origin = CGPoint(x: 25, y: 5)
let overlay = UIView(frame: CGRect(x: 10, y: 5, width: 200, height: 100))
root.addSubview(overlay)
let hint = UIView(frame: marker.convert(marker.bounds, to: overlay))
overlay.addSubview(hint)
assert(hint.frame == CGRect(x: 75, y: 40, width: 20, height: 10))
```

Рамка подсказки занимает то же место в корне, хотя её frame имеет другие числа. Все transforms в этом итоговом примере единичные.

## Проверь себя

Закрой код и объясни, чьи координаты нужны в каждом шаге.

- Почему bounds.origin может изменить положение содержимого без сдвига frame окна?
- Почему сложение frame.origin не заменяет convert?
- Как изменить масштабированную view, не записывая в неопределённый frame?

## Ответы к «Проверь себя»

- `frame` отвечает на вопрос «где я у родителя», а `bounds` — «какой участок своей системы я показываю». `viewport.bounds.origin = CGPoint(x: 25, y: 5)` ставит в левый верхний угол окна локальную точку (25,5), поэтому дети визуально сдвигаются на −25 и −5, а `viewport.frame.origin` остаётся (40,30). Как в аналогии урока: двигается участок карты, а рамка на столе стоит на месте; так устроена прокрутка.
- Сложение `viewport.frame.minX + marker.frame.minX` учитывает только места рамок и забывает локальную систему родителя: его `bounds.origin` и transform. После сдвига bounds на (25,5) guess даёт (110,50), а на деле marker в корне в (85,45), поэтому `guess == actual` — false. `marker.convert(CGPoint.zero, to: root)` или `convert(marker.bounds, to: root)` проходит всё дерево сам, так что вручную вычитать origin в разных местах не нужно.
- При неединичном transform свойство `frame` не определено, поэтому его не задаёшь и на его значение не опираешься. Размер содержимого меняешь через `bounds` (например, `CGRect(x: 0, y: 0, width: 80, height: 40)`), положение — через `center`, масштаб — через `transform`. Видимый охватывающий прямоугольник получаешь `viewport.convert(viewport.bounds, to: root)`: при ×2 будет 160×80 с началом (20,40), а локальный `bounds` останется 80×40.

# ГЛУБЖЕ

## Обратное направление convert

Если точка уже пришла в координатах root, используй marker.convert(point, from: root). Не переворачивай мысленно знак origin: у API явно названа исходная система. После преобразования проверяй попадание относительно настоящего marker.bounds, который тоже может начинаться не с нуля.

## Перенос между родителями

Прежде чем вынуть view из старого контейнера, сохрани её прямоугольник через convert в новый контейнер. Затем поменяй superview и присвой сохранённый frame, если transform единичный и размещение управляется вручную. Проверь место в корне до и после: совпадение локального frame тут ничего не доказывает.

## Auto Layout и геометрия

Если constraints управляют view, следующая раскладка может перезаписать вручную заданный frame. Поэтому для следующей темы отдели вычисление координат от изменения ограничений. `layoutIfNeeded` помогает получить актуальную геометрию перед чтением; он не превращает координаты одной view в координаты другой.

## Поворот и численная проверка

При повороте на 90° охватывающий прямоугольник меняет ширину и высоту местами, но CGFloat может содержать малую погрешность. Сравни с допуском. На произвольном угле такой прямоугольник включает пустые углы; касания нельзя определять только по нему.
