## Две работы, одно завершение

Назови событие готовности: обе карточки уже обработаны, после этого панель сообщает «Панель готова». DispatchGroup отслеживает незавершённые работы; она не собирает их результаты и не делает общий массив безопасным.

Будем печатать готовые id без общего изменяемого хранилища. Для прозрачного вывода worker serial, но сама группа может объединять работы разных очередей.

## Пишем в лоб: leave слишком рано

Проверь момент окончания работы, а не наличие пары методов. В примере отпускаем группу до вызова finish: баланс уже нулевой, карточка ещё не обработана.

```swift
import Dispatch
// Контекст: внешняя фоновая работа, не главная очередь.
func inspectEarlyLeave() {
    let group = DispatchGroup()
    group.enter()
    let finish = { print("Карточка 71") }
    group.leave()
    print(group.wait(timeout: .now()) == .success)
    finish()
}
```

Фоновая проверка печатает true, затем «Карточка 71». Группа считает учёт законченным раньше реального действия. Это воспроизводимая ошибка границы, без sleep и гонки тайминга.

## enter до запуска, leave по окончании

Поставь enter до отправки работы. Иначе notify может увидеть пустую группу раньше, чем задача успеет зарегистрироваться. leave должен соответствовать ровно одному enter и происходить после учитываемого действия.

```swift
group.enter()
worker.async {
    defer { group.leave() }
    print("Карточка 71")
}
```

group и worker объявлены в итоговом примере. defer выполняется при выходе из текущего блока, включая ранний return. Если внутри запускается ещё одна асинхронная операция, leave нужен в её настоящем completion, а не в defer короткой оболочки.

## notify доставляет событие, не останавливая caller

Зарегистрируй notify после постановки всей известной партии. Когда баланс этой группы станет нулевым, блок будет поставлен на указанную очередь. Он не обязан выполниться прямо в строке регистрации.

```swift
group.notify(queue: .main) {
    print("Панель готова")
    done()
}
```

Здесь done — callback refreshGarden. Главная очередь должна продолжать исполнять работы. notify не отменяет ошибочные операции, не передаёт их значения автоматически и не означает успех — только завершение учёта.

## Пройдём баланс двух карточек

Проследи одну допустимую историю: enter 71 → 1, enter 72 → 2, leave 71 → 1, leave 72 → 0, затем notify. Если первая работа закончится между enter двух карточек, промежуточный ноль тоже возможен; notify ещё не зарегистрирован, потому что партия сначала полностью поставлена.

Это счётчик нашего учёта, не порядок завершения любых конкурентных работ. Для новой партии лучше создать свою группу и зарегистрировать notify после её постановки, а не добавлять будущие enter после уже пустой группы.

## Подвох: return пропустил leave

Посмотри на guard: нет карточки 72 — выходим. Если leave стоит только после успешной печати, баланс останется положительным и notify не получит условия завершения.

Помести defer в начало учитываемой работы до guard. Не добавляй второй leave на ошибку вместе с defer: лишний leave нарушает баланс и может вызвать аварийную диагностику. Отсутствие notify не всегда значит медленную сеть — сначала проверь каждый путь.

## notify и wait решают разное

Выбери по месту вызова: notify ставит продолжение и не блокирует вызывающего; wait удерживает вызывающий поток до нуля или timeout. Не делай wait на главном потоке, который должен обслуживать UI или completion группы.

В фоновой проверке wait(timeout: .now()) может немедленно сообщить .timedOut. Это не отмена работы и не разрешение читать незавершённые результаты. В ступени 6 после проверки вручную закончим учёт и доставим notify на main.

## Итог: завершение после обеих работ

Собери самостоятельную функцию. Каждый worker-блок сам завершает один enter; notify вызывается для целой заранее поставленной партии.

```swift
import Dispatch
func refreshGarden(done: @escaping () -> Void) {
    let worker = DispatchQueue(label: "garden.cards")
    let group = DispatchGroup()
    for id in [71, 72] {
        group.enter()
        worker.async {
            defer { group.leave() }
            print("Карточка \(id)")
        }
    }
    group.notify(queue: .main) {
        print("Панель готова")
        done()
    }
}
```

Вывод «Карточка 71», «Карточка 72», «Панель готова», затем done. В UI можно вызвать refreshGarden без ожидания главного потока. Нужные данные и обработка ошибок должны иметь отдельный контракт.

## Проверь себя

Проверь каждый путь работы, включая пропуск.

- Почему enter ставится до отправки задачи?
- Где нужен leave, если блок запускает ещё одну async-операцию?
- Почему timeout wait не означает, что работа отменена?

## Ответы к «Проверь себя»

- DispatchGroup считает незавершённые работы, и учёт работы начинается с `enter`. Если отправить задачу раньше, группа на мгновение выглядит пустой, и `notify` может сработать до того, как задача успела зарегистрироваться. Поэтому порядок такой: `group.enter()`, затем `worker.async { defer { group.leave() } … }`, а `notify` — после постановки всей партии.
- `leave` закрывает ровно один `enter` и ставится после учитываемого действия. Если блок запускает ещё одну асинхронную операцию, `defer` короткой оболочки отпустит группу сразу, когда работа ещё не сделана, — это та же ошибка «leave слишком рано». Значит, `leave` переносишь в настоящий completion вложенной операции и следишь, чтобы на каждом пути, включая ранний `return`, он был ровно один.
- `wait(timeout:)` только ограничивает, сколько вызывающий поток готов ждать нуля баланса; `.timedOut` значит «ещё не дождался». Работы группы об этом не знают и продолжают выполняться, их `leave` придут позже. Поэтому по `.timedOut` нельзя считать работу отменённой и нельзя читать её незавершённые результаты.

# ГЛУБЖЕ

## Системный учёт или ручной

Для целой работы worker.async(group: group) связывает учёт с временем самого блока. Это удобно, пока блок не заканчивается раньше настоящей асинхронной операции.

Не смешивай автоматический учёт блока с несимметричным ручным leave. Если внутри сохраняется callback и результат придёт позже, вручную enter до запуска и leave ровно в конечном callback.

## Callback может ответить несколько раз

Сначала узнай контракт источника. На один enter нужен один leave, а источник может ошибочно или намеренно выдавать несколько событий. Просто leave на каждый callback опасен.

Для one-shot-адаптера нужен синхронизированный флаг «уже завершено»; не используй обычный общий Bool без владельца. Для постоянного потока событий DispatchGroup обычно не является моделью завершения всей подписки.

## Группа не блокировка результатов

Если две concurrent-работы одновременно append в общий Array, группа не защитит память: она только считает незавершённое. Результаты должны собираться через отдельного владельца, например очередь из race.

Читай готовый снимок после завершения учёта, соблюдая тот же интерфейс владельца. notify не превращает неправильные записи до него в безопасные.

## Не жди свою же очередь

Нарисуй граф: работа на serial-очереди вызывает wait, а leave поставлен async на ту же очередь. Ожидающий блок мешает исполниться тому, кто должен закончить ожидание.

Такой код остаётся неправильным и вне главного потока. Меняй блокирующее ожидание на notify или меняй архитектуру исполнения; название «background» само по себе не спасает.
