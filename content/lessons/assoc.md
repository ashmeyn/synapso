## Назови, что должно оставаться типом

Сохрани Int для id 71 и String для «Фото». Associated type — имя типа внутри контракта протокола; конкретная реализация выбирает, что означает Item. Это не разрешение каждому элементу свободно менять тип.

## Пишем в лоб: протокол как готовый тип

Проверь прежнюю идею «положим источники просто в [Feed]». В старом Swift до расширения existential-возможностей протокол с associatedtype нельзя было так использовать как обычный тип. В современном Swift можно написать [any Feed], но это коробки с разными скрытыми Item, а не единый `[Feed<Int>]`. Связь с конкретным Int на таком интерфейсе не сохранится автоматически.

## associatedtype связывает результат с реализацией

Объяви Feed и IDFeed. Используй typealias: здесь он явно задаёт Int; у NameFeed тип можно вывести из first() -> String?. Это типы одного метода конкретного соответствия протоколу.

```swift
protocol Feed {
    associatedtype Item
    func first() -> Item?
}
struct IDFeed: Feed {
    typealias Item = Int
    let ids: [Int]
    func first() -> Int? { ids.first }
}
struct NameFeed: Feed {
    let names: [String]
    func first() -> String? { names.first }
}
```

IDFeed(ids: [71]).first() имеет тип Int?. В NameFeed такой же контракт обслуживает String?, потому что Item выводится из реализации. Синтаксис имени Item не является generic-параметром самого протокола.

## some: реализация скрывает один тип

Создай две реализации карточки. Затем функция makeCard возвращает some Card и всегда создаёт IDCard. Caller видит контракт summary, но не получает обещания конкретного имени IDCard.

```swift
protocol Card { func summary() -> String }
struct IDCard: Card {
    let id: Int
    func summary() -> String { "Проект \(id)" }
}
struct NameCard: Card {
    let name: String
    func summary() -> String { name }
}
```

Аналогия: some — запечатанная серия одной модели, any — коробка, в которую разрешено положить разные подходящие модели. У some возвращаемого значения конкретный тип выбирает реализация функции; generic-параметр C на входе, напротив, связан с выбором вызывающего.

## Подвох: some не переключает тип на ветке

Прочитай chooseCard: одна ветка IDCard, другая NameCard. Если возвращаемый тип some Card, компилятор отвергнет такой обычный if: все пути должны согласоваться на одном скрытом конкретном типе. Значения одного типа могут различаться, сами типы — нет.

```swift
func makeCard(id: Int) -> some Card { IDCard(id: id) }
let card = makeCard(id: 71)
print(card.summary())
```

Card и IDCard объявлены выше. Вывод «Проект 71». Для разных реализаций по условию выбери any Card, либо создай один общий конкретный тип, представляющий варианты. Result builder может собирать общий тип сам; его здесь не используем.

## any: выбираем разные реализации для списка

Сохрани две карточки в явно объявленный [any Card]. Caller может выбирать, какой соответствующий тип положить в список; existential-возврат фабрики тоже может упаковывать разные реализации по ветке.

```swift
let cards: [any Card] = [IDCard(id: 71), NameCard(name: "Фото")]
for card in cards { print(card.summary()) }
```

Типы карточек уже объявлены. Вывод «Проект 71», «Фото». any может требовать упаковки, дополнительной косвенности и выделения памяти в зависимости от значения; фиксированной цены или обязательного heap для каждой коробки не обещаем.

## Primary associated type ограничивает коробку

Попробуй `any Collection<Int>`: Collection — стандартный протокол, его primary associated type Element фиксируется как Int. Это не новый generic-класс; ограничение сохраняет тип элементов при разных реализациях коллекции.

```swift
func total(_ values: any Collection<Int>) -> Int {
    values.reduce(0, +)
}
print(total([71, 72]))
print(total(Set([71, 72])))
```

И Array, и Set дают сумму 143. Для своего Feed primary associated type можно объявить в заголовке `protocol Feed<Item>`, сохранив associatedtype Item в теле; это отдельный синтаксис ограничения, а не способ превратить протокол в конкретный контейнер.

## Итог: типизированный источник и разнородный UI

Собери самостоятельный пример. Источник сохраняет Int, opaque-фабрика скрывает одну модель, existential-список принимает две реализации.

```swift
protocol Feed {
    associatedtype Item
    func first() -> Item?
}
struct IDFeed: Feed {
    typealias Item = Int
    let ids: [Int]
    func first() -> Int? { ids.first }
}
protocol Card { func summary() -> String }
struct IDCard: Card {
    let id: Int
    func summary() -> String { "Проект \(id)" }
}
struct NameCard: Card {
    let name: String
    func summary() -> String { name }
}
func makeCard(id: Int) -> some Card { IDCard(id: id) }
let feed = IDFeed(ids: [71, 72])
print(makeCard(id: feed.first() ?? 0).summary())
let cards: [any Card] = [IDCard(id: 72), NameCard(name: "Фото")]
for card in cards { print(card.summary()) }
```

Вывод «Проект 71», «Проект 72», «Фото». Если нужно получить Int из любого подходящего Feed, напиши generic-функцию с `where F.Item == Int`: связь проверит компилятор, без as? на результате.

## Проверь себя

Сначала скажи, кто выбирает тип.

- Где Item задан явно, а где выводится?
- Почему обычный if с двумя типами не подходит some?
- Что сохраняет `any Collection<Int>` по сравнению с any Collection?

## Ответы к «Проверь себя»

- В `IDFeed` Item задан явно через `typealias Item = Int`, а в `NameFeed` выводится из сигнатуры `first() -> String?`. В обоих случаях тип выбирает реализация, а не caller и не каждый элемент по отдельности. Поэтому `IDFeed(ids: [71]).first()` имеет тип `Int?`, и связь с Int держит компилятор.
- `some Card` на возврате обещает один скрытый конкретный тип, который выбирает сама функция: запечатанная серия одной модели. Если одна ветка возвращает `IDCard`, а другая `NameCard`, пути не согласуются на одном типе, и компилятор отвергает такой `if`. Разные реализации по условию — это `any Card` или один общий конкретный тип с вариантами.
- `any Collection<Int>` фиксирует primary associated type: какая бы коллекция ни пришла, Array или Set, её `Element` — Int. Поэтому внутри можно написать `values.reduce(0, +)` и получить сумму 143. У голого `any Collection` тип элементов скрыт, и такой связи с Int нет.

# ГЛУБЖЕ

## Existential не сохраняет все связи

Если метод принимает Item, нельзя передать произвольный Int в any Sink: скрытый Item может быть String. Generic-функция с S.Item на входе сохраняет связь. Современное открытие existential помогает многим вызовам, но не обещает доступности любых операций с неизвестным Item.

## Два источника с одним Item

Для сравнения первых значений задай where A.Item == B.Item и A.Item: Equatable. Имена типов источников могут отличаться; общим остаётся тип результата. Два пустых источника сравниваются как два nil по выбранному контракту Optional.

## Каждое opaque-объявление имеет свою идентичность

Не обещай, что результаты двух разных функций -> some Card взаимозаменяемы как один видимый тип, даже если внутри сейчас одна модель. Их opaque-идентичность задаётся объявлением; existential может упаковать обе, когда такая потеря конкретности подходит задаче.

## Не смешивай some на входе и выходе

Обозначение параметра some Card работает как сокращённый generic-параметр и зависит от аргумента caller. В этом уроке основная модель some относится к возвращаемому значению: скрытый тип выбирает реализация. Не переноси правило выбора буквально на все позиции слова some.
