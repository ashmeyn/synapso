## Сначала назови, кто ждёт

В поиске участвуют две serial-очереди: index и settings. Одного правила «разные очереди, значит безопасно» недостаточно. Если каждая ждёт работу другой, завершить ожидание некому.

Deadlock — ситуация, где участники не могут продолжить из-за замкнутого ожидания. В отличие от временно долгой работы, здесь скорость процессора и приоритет не устранят зависимость.

## Пишем в лоб: A ждёт B, B ждёт A

Прочитай код как граф ожиданий. Блок index ждёт settings.sync; блок settings ждёт index.sync; index не может завершить первый блок, пока не завершится settings.

```swift
import Dispatch
let index = DispatchQueue(label: "library.index")
let settings = DispatchQueue(label: "library.settings")
index.sync {
    print("Индекс 41")
    settings.sync {
        print("Настройки")
        index.sync { print("Книга 41") }
    }
}
```

Успешного полного вывода здесь нет: «Книга 41» не является достижимым нормальным результатом этой цепочки. Dispatch может обнаружить неправильный вызов и аварийно завершить процесс. Это ошибочный пример для чтения и компиляции, не программа для успешного запуска.

## Ожидание не равно зависимости данных

Сохрани порядок «индекс → настройки → результат», но перестань блокировать исполнителя до следующей фазы. async ставит следующую работу, а текущий блок получает возможность закончиться.

Аналогия: вместо двух людей, каждый из которых ждёт ответа другого и не отвечает сам, передаём записку с результатом следующему участнику. Очередь продолжит обрабатывать поставленные работы после завершения текущей.

## Передаём результат в следующую фазу

Напиши callback done: это замыкание для готовой строки, сохраняемое до завершения цепочки. Здесь передаются неизменяемые id и title; общую изменяемую модель мы не открываем.

```swift
index.async {
    settings.async {
        index.async {
            let title = "Книга \(id)"
            DispatchQueue.main.async { done(title) }
        }
    }
}
```

Это тело findBook с очередями index/settings, id 41 и done, объявленными в итоговом примере. Внешние блоки не ждут внутренние, поэтому очередь index сможет принять последнюю фазу.

## main.sync с главного потока

Проверь другой цикл: если код уже выполняется на главном потоке приложения, main.sync ждёт выполнение на очереди, чей текущий блок не может завершиться. Это самозависимость главной очереди.

```swift
import Dispatch
// Контекст: эта функция вызвана на главном потоке приложения.
func showBook(done: @escaping () -> Void) {
    DispatchQueue.main.sync {
        print("Книга 41")
        done()
    }
}
```

Для доставки позже замени sync на async. Если код по контракту уже обязан исполняться на главной очереди и дополнительная постановка не нужна, допустим прямой вызов; в нашем задании сохраняем асинхронную доставку. Исходник не запускаем как успешный пример.

## UI ждёт worker, worker ждёт UI

Попробуй другую цепочку: главный поток вызывает worker.sync, а worker внутри делает main.sync. Даже разные имена очередей не помогают: главный поток ждёт worker, worker ждёт главную очередь.

Исправление для этой миссии — worker.async, затем main.async с готовым результатом. Просто поменять один sync наугад не означает, что вся система безопасна: выпиши оставшиеся ожидания и проверь, нужен ли вызывающему коду немедленный результат.

## Не теряем смысл результата

Назови контракт после исправления: findBook возвращается до появления строки, а done получит её позже на главной очереди. Нельзя сразу после вызова читать ещё не обновлённую общую переменную и считать поиск завершённым.

Порядок фаз сохраняется вложенной постановкой, а не скоростью выполнения. Для числа совпадений можно тем же способом передать Int: это перенос механизма, а не обещание произвольного порядка независимых работ.

## Итог: цикл очередей без цикла ожиданий

Собери полный пример. Здесь работа может вернуться на index, потому что её первый блок уже не ждёт последнюю фазу. Повторное обращение к очереди само по себе не является deadlock; опасно замкнутое ожидание.

```swift
import Dispatch
func findBook(id: Int, done: @escaping (String) -> Void) {
    let index = DispatchQueue(label: "library.index")
    let settings = DispatchQueue(label: "library.settings")
    index.async {
        print("Индекс \(id)")
        settings.async {
            print("Настройки")
            index.async {
                let title = "Книга \(id)"
                DispatchQueue.main.async { done(title) }
            }
        }
    }
}
```

При findBook(id: 41) сначала выйдут «Индекс 41», «Настройки», затем done получит «Книга 41». Чтобы увидеть callback в приложении, главная очередь должна продолжать исполнять работы. Без её блокирующего ожидания это часть нормального жизненного цикла UI.

# ГЛУБЖЕ

## Два ресурса: один порядок захвата

Если участники держат ресурсы, проверь порядок: A захватил первый и ждёт второй, B захватил второй и ждёт первый. Это тот же граф ожидания, даже без DispatchQueue.

Для двух NSLock можно установить общий порядок: всегда first.lock(), затем second.lock(), затем unlock в обратном порядке. lock ждёт свободный ресурс, unlock отпускает его. Все пути должны соблюдать этот порядок; повторный захват того же нерекурсивного lock тоже опасен.

## Timeout не исправляет архитектуру

Не называй timeout полным исправлением. Он может ограничить ожидание, но после неуспеха нужно обработать результат, отпустить уже захваченные ресурсы и восстановить согласованное состояние.

Если продолжить как будто ресурс получен, появится другая ошибка. Для нашей цепочки проще убрать ненужное блокирующее ожидание и явно доставить готовое значение.

## Прямой помощник и владелец состояния

Если внутри settings можно использовать чистый расчёт вместо обратного запроса на index, передай нужный снимок и вызови обычную функцию. Так можно убрать одно ребро ожидания.

Но нельзя напрямую читать состояние index, которое принадлежит другой очереди. Снимок должен быть получен безопасно заранее и не раскрывать изменяемое общее хранилище.

## Как искать в приложении

При зависании приостанови приложение в Xcode и посмотри стеки ожидающих потоков: где sync, lock или wait и кто должен дать продолжение. Составь граф, а не вывод «поток занят, значит deadlock».

Замкнутое ожидание отличается от долгой операции, бесконечного расчёта и исчерпания исполнителей. Отсутствие одного конкретного стека не доказывает безопасность всех путей.
