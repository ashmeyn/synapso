## Когда появится подпись

Начнём со времени, а не с аннотации. Экран показывает «Ожидание»; после результата — «Тёплый свет». Функция запроса возвращается раньше результата, поэтому вернуть готовую подпись обычным return пока нельзя.

В примере нет обработки изображения и фоновых потоков. PreviewQueue — учебный объект с одним ожидающим обработчиком: request запоминает его, finish вызывает вручную. Новый request заменяет предыдущий; это объявленный контракт, не очередь всех работ.

## Пишем в лоб: вернули старую строку

Для этого фрагмента нужна PreviewQueue из раздела «Сохраним и освободим обработчик»: она сохраняет callback и вызывает его только в finish. Посмотри на локальный title: функция возвращает его до finish.

```swift
func previewTitle(queue: PreviewQueue) -> String {
    var title = "Ожидание"
    queue.request { title = $0 }
    return title
}
let queue = PreviewQueue()
let title = previewTitle(queue: queue)
queue.finish("Тёплый свет")
print(title)
```

Вывод «Ожидание». Сохранённый обработчик изменил захваченную переменную внутри функции, но вызывающему коду уже отдано прежнее строковое значение. Давай передадим результат туда, где он действительно появляется, через completion — обработчик завершения.

## Здесь параметр покидает вызов

Если убрать @escaping из сигнатуры request, присваивание не скомпилируется. Параметр вида `(String) -> Void` по умолчанию non-escaping: функция не вправе сохранить его для использования после возврата.

```swift
final class PreviewQueue {
    private var pending: ((String) -> Void)?
    func request(_ completion: (String) -> Void) {
        pending = completion // ❌ параметр сохраняется после возврата
    }
}
```

Свойство pending может пережить вызов request. Поэтому параметр должен быть `@escaping (String) -> Void`. @escaping разрешает такую жизнь, но само по себе не запускает поток и не обещает, когда либо сколько раз обработчик будет вызван. Это как оставить контакт для ответа вместо разговора, законченного до твоего ухода.

## Сохраним и освободим обработчик

Теперь поставь аннотацию и прочитай finish по строкам. Сначала берём обработчик, затем удаляем его из свойства, только после этого вызываем.

```swift
final class PreviewQueue {
    private var pending: ((String) -> Void)?
    func request(_ completion: @escaping (String) -> Void) {
        pending = completion
    }
    func finish(_ text: String) {
        let completion = pending
        pending = nil
        completion?(text)
    }
    func cancel() { pending = nil }
}
```

`completion?(text)` вызывает Optional-замыкание, если оно есть. Очистка до вызова помогает выдержать повторный finish и ситуацию, когда сам обработчик создаст следующий request. cancel лишь убирает ожидающий обработчик; это не отмена настоящего вычисления изображения.

## Немедленному параметру аннотация не нужна

Сравни другой шаг того же редактора: подготовка текста выполняется прямо сейчас, результат возвращается до выхода из функции.

```swift
func prepareTitle(_ text: String, transform: (String) -> String) -> String {
    transform(text)
}
print(prepareTitle("Тёплый свет") { $0.uppercased() })
```

Вывод «ТЁПЛЫЙ СВЕТ». transform нигде не сохраняется, поэтому оставляем его non-escaping. Не расставляй @escaping по принципу «любое замыкание»: сначала спроси, должен ли параметр пережить вызов.

## Результат обновит владельца

Очередь уже существует. Давай передадим подпись модели экрана в обработчике, а не через слишком ранний return.

```swift
final class PreviewScreen {
    private(set) var title = "Ожидание"
    func start(queue: PreviewQueue) {
        queue.request { [weak self] text in self?.title = text }
    }
}
```

queue держит обработчик, а обработчик обращается к экрану. weak self из clos не удерживает экран ради ожидающего ответа. Если экран исчез, изменение пропускается; аннотация @escaping сама этого не решает. Здесь явно видны self и обращение к title.

## Пройди два завершения и отмену

Назови состояние после каждого действия: start → «Ожидание»; finish("Тёплый свет") → «Тёплый свет»; второй finish → та же подпись, потому что pending уже nil. Если cancel вызвать до первого finish, экран останется в ожидании.

Обрати внимание: правило одноразовости реализует finish, а не @escaping. И всё происходит в одном потоке по нашим ручным вызовам. Прежде чем переносить модель в настоящую асинхронную обработку, нужно отдельно выбрать исполнителя и защиту состояния.

## Собираем отложенный ответ

Окей, вот весь маршрут. Прогнозируй каждую строку print до запуска.

```swift
final class PreviewQueue {
    private var pending: ((String) -> Void)?
    func request(_ completion: @escaping (String) -> Void) {
        pending = completion
    }
    func finish(_ text: String) {
        let completion = pending
        pending = nil
        completion?(text)
    }
    func cancel() { pending = nil }
}
final class PreviewScreen {
    private(set) var title = "Ожидание"
    func start(queue: PreviewQueue) {
        queue.request { [weak self] text in self?.title = text }
    }
}
let queue = PreviewQueue()
let screen = PreviewScreen()
screen.start(queue: queue)
print(screen.title)
queue.finish("Тёплый свет")
print(screen.title)
queue.finish("Лишний ответ")
print(screen.title)
```

Вывод: «Ожидание», «Тёплый свет», «Тёплый свет».

- Сохраняемый параметр-замыкание помечай @escaping.
- Результат, который появится позже, передавай в момент завершения.
- Одноразовый обработчик очищай до вызова; захват владельца выбирай отдельно.

## Проверь себя

Убери готовый код и восстанови временную линию.

- Почему обычный return не отдаёт будущую подпись?
- Почему request требует @escaping, а prepareTitle — нет?
- Что гарантирует очистка pending и почему weak self не заменяет её?

## Ответы к «Проверь себя»

- `previewTitle` возвращается раньше, чем кто-то вызовет `finish`: в момент `return title` там ещё «Ожидание», и вызывающему коду отдаётся копия этой строки. Сохранённый обработчик позже меняет только захваченную локальную переменную, которую уже никто не читает. Поэтому будущий результат передаёшь в момент завершения через completion и обновляешь модель экрана: `queue.request { [weak self] text in self?.title = text }`.
- `request` кладёт параметр в свойство `pending`, которое переживает вызов, а параметр-замыкание по умолчанию non-escaping, так что без `@escaping (String) -> Void` присваивание не скомпилируется. `prepareTitle` вызывает `transform(text)` прямо сейчас и возвращает результат до выхода, ничего не сохраняя, поэтому аннотация не нужна. Сначала спрашиваешь, должен ли параметр пережить вызов, а не ставишь `@escaping` на любое замыкание.
- `finish` сначала берёт обработчик, потом `pending = nil`, и только затем `completion?(text)`: обработчик сработает один раз, повторный `finish("Лишний ответ")` найдёт `nil`, а новый `request` изнутри обработчика не будет стёрт. `[weak self]` решает другую задачу: очередь не удерживает экран ради ожидающего ответа. Пока экран жив, без очистки второй `finish` снова вызвал бы обработчик и перезаписал подпись.

# ГЛУБЖЕ

## Escaping может быть вызван сразу

Не выводи время выполнения только из сигнатуры. Функция с @escaping может сразу вызвать обработчик, сохранить его, сделать оба действия или вообще не вызвать: конкретные гарантии задаёт её контракт.

У нашей очереди один слот и ручной finish. Если API обещает «ровно один ответ», это нужно обеспечить реализацией, включая ошибку и отмену. Аннотация такого обещания не содержит.

## Optional и явный self

Посмотри, где написано @escaping: у непосредственного параметра функции. Хранимое свойство `((String) -> Void)?` не получает эту аннотацию; Optional-замыкание может храниться и без неё.

Swift также допускает некоторые формы неявного self после явного захвата `[self]` или раскрытия weak self. Не запоминай абсолютное «в любом escaping всегда пишется self.». Для обучения оставляем захват и доступ заметными; сильный `[self]` сам по себе не разрывает кольцо.

## Очистка до вызова

Проверь повторный вход: обработчик первого результата вызывает request для следующего. Если finish сначала вызовет обработчик, а потом обнулит pending, он сотрёт уже новую подписку.

Поэтому забираем старый обработчик в локальную константу и освобождаем слот до вызова. Это корректность последовательного алгоритма; для одновременных вызовов с разных потоков одной перестановки строк недостаточно.

## От completion к async

Если обработчик заменён функцией `async -> String`, строка приходит через await, а параметра-замыкания в такой сигнатуре больше нет. Вопрос @escaping к отсутствующему параметру неприменим.

Не обещай исчезновение всех удержаний: Task тоже может захватывать владельца и жить дольше экрана. А обёртка старого API через continuation требует собственного правила «возобновить ровно один раз».
