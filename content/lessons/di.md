## Сначала заметим зависимость

Экран показывает покупки, но сам список кто-то должен предоставить. Этот источник — зависимость: объект, без которого загрузчик не выполнит свою работу. Для проверки дадим покупку 7 «Хлеб» и ожидаем одну строку.

Никакой сети и файлового API пока нет. `SavedShoppingSource` в нашей учебной версии возвращает пустой список. Нам нужно подставить другой источник и убедиться, что экранная модель пользуется именно им.

## Пишем в лоб: источник уже выбран за нас

Здесь ShoppingSource и ShoppingItem уже объявлены. Посмотри, кто решает, откуда брать данные.

```swift
struct SavedShoppingSource: ShoppingSource {
    func items() -> [ShoppingItem] { [] }
}
final class ShoppingViewModel {
    private let source = SavedShoppingSource()
    var items: [ShoppingItem] = []
    func load() { items = source.items() }
}
```

Создашь рядом тестовый источник с «Хлебом» — load всё равно получит пустой список. ViewModel сама создала SavedShoppingSource и не принимает замену. Это и есть проблема, которую решает Dependency Injection: зависимость передаётся снаружи.

Не делай отсюда вывод, что создание объекта внутри всегда ошибка. Проблема возникает, когда источник нужно выбирать, заменять или проверять отдельно от потребителя.

## Опишем нужную операцию

Возьми контракт из proto: потребителю требуется только получить массив покупок. id отличает покупку, title служит подписью.

```swift
struct ShoppingItem {
    let id: Int
    let title: String
}
protocol ShoppingSource {
    func items() -> [ShoppingItem]
}
```

Источник с заданным результатом будет возвращать то, что ему передали. Это не настоящий сетевой клиент, а управляемая реализация для проверки.

```swift
struct FixedShoppingSource: ShoppingSource {
    let result: [ShoppingItem]
    func items() -> [ShoppingItem] { result }
}
```

Не добавляй в протокол сохранение или удаление, пока потребитель их не вызывает. Маленький контракт проще выполнить и проверить.

## init делает зависимость обязательной

Убери создание источника из свойства. `init` — инициализатор: он получает всё необходимое для нового экземпляра. `self.source` — свойство экземпляра, source справа — переданный параметр.

```swift
final class ShoppingViewModel {
    private let source: any ShoppingSource
    var items: [ShoppingItem] = []
    init(source: any ShoppingSource) { self.source = source }
    func load() { items = source.items() }
}
```

Контекст — ShoppingSource и ShoppingItem выше. Потребитель знает операции контракта, но не выбирает конкретный источник. `let` не позволяет впоследствии заменить эту зависимость; это не обещание неизменяемости объекта, если реализация окажется классом.

Передача зависимости похожа на подключение выбранного аккумулятора к устройству: устройство использует питание, а какой аккумулятор подключить, решает сборщик.

## Соберём объекты снаружи

Теперь место выбора хорошо видно. Это продолжение предыдущих объявлений.

```swift
let source = FixedShoppingSource(result: [ShoppingItem(id: 7, title: "Хлеб")])
let viewModel = ShoppingViewModel(source: source)
viewModel.load()
print(viewModel.items.count)
```

Вывод — 1. Источник создали снаружи, init сохранил его, load обратился к сохранённому источнику. В приложении это делает место сборки экрана; в проверке — код проверки.

Сама DI не требует протокола: можно передать и конкретный тип. Здесь протокол нужен, чтобы один потребитель принимал разные реализации. Для SwiftUI наблюдение из obs добавляется отдельно; оно не является частью определения DI.

## Когда зависимость нужна только одному вызову

Предпросмотру списка источник может требоваться лишь на время запроса. Тогда его удобно передать параметром метода, не хранить в объекте.

```swift
final class ShoppingPreview {
    func count(source: any ShoppingSource) -> Int { source.items().count }
}
```

Это продолжение контракта ShoppingSource. Вызови `preview.count(source: source)` с созданными экземплярами. Предпросмотр не запоминает источник и при следующем вызове может получить другой.

Перенеси тот же принцип на бюджет покупок: BudgetSource обещает `limit() -> Int`, ViewModel принимает его в init и вычисляет подпись из возвращённого числа. Заменяемая зависимость может выдавать число, а не только массив.

## Пройдём замену и пустой результат

Начни с источника, возвращающего одну покупку: после load items содержит id 7. Теперь создай другую ViewModel с `FixedShoppingSource(result: [])`: после load её items пуст. Код load одинаковый, ответы определяет переданный источник.

Подвох в init: написать `self.source = SavedShoppingSource()` и проигнорировать параметр. Формально параметр появился, но подстановка всё ещё не работает. Исправление — `self.source = source`.

Пустой список здесь допустим и не является ошибкой. В этом синхронном контракте мы не моделируем сбой сети. Не приписывай заглушке гарантий будущего реального сервиса.

## Собираем проверяемую загрузку

Весь пример запускается без интерфейса. ViewModel здесь обычный объект: проверяем выбор источника, не механизм обновления SwiftUI.

```swift
struct ShoppingItem {
    let id: Int
    let title: String
}
protocol ShoppingSource {
    func items() -> [ShoppingItem]
}
struct FixedShoppingSource: ShoppingSource {
    let result: [ShoppingItem]
    func items() -> [ShoppingItem] { result }
}
final class ShoppingViewModel {
    private let source: any ShoppingSource
    var items: [ShoppingItem] = []
    init(source: any ShoppingSource) { self.source = source }
    func load() { items = source.items() }
}
let source = FixedShoppingSource(result: [ShoppingItem(id: 7, title: "Хлеб")])
let viewModel = ShoppingViewModel(source: source)
viewModel.load()
print(viewModel.items.count)
```

- Долгая обязательная зависимость — параметр init и сохранённое свойство.
- Зависимость одного действия — параметр метода.
- Место сборки выбирает реализацию; потребитель выполняет её контракт.

- Когда источник лучше передать методу, а не сохранить в init?

# ГЛУБЖЕ

## Передача через свойство

Иногда объект сначала создают, а зависимость задают позже. Это тоже DI, но возникает промежуток, в котором объект может быть не готов к работе. Придётся явно определить поведение до установки источника.

Если источник обязателен, init проще: неполный экземпляр нельзя создать. Передачу через свойство выбирай, когда действительно нужна поздняя настройка или замена, а не потому, что так меньше параметров.

## Место сборки и контейнер

В большом приложении экрану нужен источник, источнику — клиент и настройки. Место, собирающее эту цепочку, часто называют композиционным корнем. DI-контейнер может автоматизировать сборку, но принцип остаётся тем же.

Не заменяй передачу зависимости поиском глобального сервиса внутри ViewModel. Тогда зависимость снова скрыта от init, а проверка зависит от общего состояния. Сначала сделай зависимости видимыми; автоматизацию добавишь при реальной сложности сборки.

## DI и инверсия зависимостей

Попробуй разделить два утверждения: «объект получает источник извне» описывает DI; «объект зависит от контракта, а не детали» описывает направленность зависимостей. Они часто работают вместе, но не являются синонимами.

В нашем случае any ShoppingSource позволяет FixedShoppingSource и SavedShoppingSource подходить одному потребителю. Передача конкретного источника извне всё ещё была бы DI, просто возможностей заменить тип было бы меньше.

## Что умеет проверять заглушка

FixedShoppingSource подтверждает, что потребитель работает с известными ответами: один элемент, несколько, пусто. Он не подтверждает чтение файла, сеть или корректность реальной базы.

Если важно проверить число вызовов items, пригодится источник, который их считает. Если нужны ошибки, их сначала придётся выразить в контракте. Подбирай двойник под утверждение, которое проверяешь, а не называй любой заменяющий объект мок-сервисом.
