## Сначала договоримся о результате

Открой план 72 с названием «Поездка». Вверху — название, ниже — поле редактирования. Замени его на «Выходные»: обе части экрана должны показать новую строку.

Ты уже умеешь держать значение в `@State`. Теперь вынесем данные в `class` — объект, на который можно ссылаться из разных блоков. Присваивание такой модели передаёт ссылку на тот же объект. Подробности памяти пока не нужны: нам важно не создать два разных плана.

## Пишем в лоб: объект изменился, экран не знает

Посмотри на попытку ниже. `let` закрепляет ссылку, но свойства объекта по ней менять можно.

```swift
import SwiftUI
final class TripPlan {
    let id = 72
    var title = "Поездка"
}
struct TripScreen: View {
    let plan = TripPlan()
    var body: some View {
        Button(plan.title) { plan.title = "Выходные" }
    }
}
```

После нажатия `plan.title` действительно станет «Выходные». Но у обычного класса здесь нет наблюдения: эта запись сама не сообщает SwiftUI, что нужно пересчитать `body`. Кнопка может остаться с прежним названием; постороннее обновление способно скрыть баг. Поэтому «однажды увидел новый текст» ещё не доказывает правильную связь.

## Дадим модели способ сообщать об изменениях

Начнём со связки, которую встретишь в существующих проектах. `ObservableObject` — контракт для объекта, сообщающего об изменениях; `@Published` помечает свойство, изменения которого он публикует. `final` запрещает наследование от класса, здесь оно нам не требуется.

```swift
import SwiftUI
final class TripPlan: ObservableObject {
    let id = 72
    @Published var title = "Поездка"
}
```

Остановись на этой границе: модель уже сообщает об изменениях, но экран ещё должен подписаться. Само слово `@Published` не превращает любую надпись в слушателя.

## Назначим владельца

`TripScreen` создаёт план и отвечает за его жизнь на экране. Для такой модели объяви `@StateObject`: SwiftUI сохраняет объект между пересчётами этого экрана, пока сохраняется его идентичность, и наблюдает его изменения.

```swift
struct TripScreen: View {
    @StateObject private var plan = TripPlan()
    var body: some View {
        VStack {
            Text(plan.title)
            TextField("Название", text: $plan.title)
        }
    }
}
```

Здесь `TripPlan` — модель из предыдущего блока. `$plan.title` даёт полю `Binding<String>`, то есть доступ для чтения и записи заголовка. Наблюдение обновляет надпись; Binding доставляет запись в модель. Не смешивай эти две работы.

## Редактор получает тот же план

Теперь вынеси поле. Редактор не создаёт модель: ему передают готовый объект. `@ObservedObject` подписывает его на изменения переданного `ObservableObject`, но не задаёт постоянное хранилище владельца как `@StateObject`.

```swift
struct PlanEditor: View {
    @ObservedObject var plan: TripPlan
    var body: some View {
        TextField("Название", text: $plan.title)
    }
}
```

В прежнем `VStack` замени `TextField` на `PlanEditor(plan: plan)`. Передай именно `plan`, без `$`: параметр ждёт объект, а связь к строке создаёт сам редактор.

Владелец и редактор похожи на хозяина документа и приглашённого соавтора: документ один, право создавать его и право редактировать — разные роли.

## Современный путь: @Observable

Для iOS 17 и новее есть Observation. `@Observable` — макрос: компилятор добавляет модели механизм отслеживания чтения и изменений. `@Published` и `ObservableObject` в этой версии убираем.

```swift
import SwiftUI
import Observation
@Observable final class TripPlan {
    let id = 72
    var title = "Поездка"
}
```

Это альтернативная версия `TripPlan`, не второй класс с тем же именем в одном файле. Владелец теперь хранит модель через `@State`, а `Text` наблюдает свойства `@Observable`, прочитанные при вычислении `body`.

```swift
struct TripScreen: View {
    @State private var plan = TripPlan()
    var body: some View {
        VStack {
            Text(plan.title)
            PlanEditor(plan: plan)
        }
    }
}
```

Для редактирования дочернему экрану нужен `$plan.title`. У современной модели эту возможность даёт `@Bindable`: он создаёт связи к свойствам, но не назначает редактор владельцем.

```swift
struct PlanEditor: View {
    @Bindable var plan: TripPlan
    var body: some View {
        TextField("Название", text: $plan.title)
    }
}
```

Не пытайся заменить только одно слово в старой связке. Здесь меняются вместе модель, хранилище владельца и доступ редактора.

## Пройдём запись и поймаем второй экземпляр

Сначала произнеси цепочку: поле пишет «Выходные» через Binding → меняется `title` общего плана → читающие его блоки получают обновление. В старой связке сигнал идёт через `@Published`; в новой SwiftUI отслеживает чтения свойств.

Теперь подвох: в старом редакторе написать `@StateObject private var plan = TripPlan()`. Получится устойчивый, но отдельный объект. Поле меняет его, а верхняя надпись читает родительский. Одинаковый `id = 72` не делает два вызова `TripPlan()` одним объектом.

Верни `@ObservedObject var plan: TripPlan` и передачу `PlanEditor(plan: plan)`. В новой связке аналогичная ошибка — создать свой `@State` с новым `TripPlan()` вместо принятого `@Bindable`. Сначала проверь число объектов, потом обёртку.

## Собираем рабочий экран

Восстановим вариант с `ObservableObject` целиком: его полезно уверенно читать в рабочих проектах. Современную замену ты уже собрал выше.

```swift
import SwiftUI
final class TripPlan: ObservableObject {
    let id = 72
    @Published var title = "Поездка"
}
struct TripScreen: View {
    @StateObject private var plan = TripPlan()
    var body: some View {
        VStack {
            Text(plan.title)
            PlanEditor(plan: plan)
        }
    }
}
struct PlanEditor: View {
    @ObservedObject var plan: TripPlan
    var body: some View {
        TextField("Название", text: $plan.title)
    }
}
```

- Создаёшь `ObservableObject` на экране — выбирай `@StateObject`.
- Получаешь его от владельца — выбирай `@ObservedObject`.
- Для `@Observable` владелец использует `@State`; редактору с `$` нужен `@Bindable`.

## Проверь себя

Закрой код и объясни путь одной записи, а затем ответь:

- Почему обычный `class` в первой попытке менялся, но не сообщал экрану об изменении?
- Что произойдёт, если редактор создаст второй план с тем же id?
- Какие три части нужно изменить при переходе от старой связки к Observation?

## Ответы к «Проверь себя»

- Запись `plan.title = "Выходные"` действительно меняла свойство: `let` закрепляет ссылку, а не содержимое объекта. Но у обычного класса нет наблюдения, поэтому никто не говорит SwiftUI пересчитать `body`, и кнопка может остаться со старым названием. Отсюда правило: «однажды увидел новый текст» не доказывает связь — модели нужен способ сообщать (`ObservableObject` + `@Published` или `@Observable`), а экрану — подписка.
- Получится второй, отдельный объект: `@StateObject private var plan = TripPlan()` в редакторе создаёт свой устойчивый план. Поле меняет его, а верхняя надпись читает родительский, поэтому «Выходные» наверх не дойдут, а одинаковый `id = 72` не делает два вызова `TripPlan()` одним объектом. Чинится так: редактор принимает `@ObservedObject var plan: TripPlan`, родитель передаёт `PlanEditor(plan: plan)`.
- Меняются все три части вместе. Модель: `@Observable final class TripPlan` вместо `ObservableObject` и `@Published`. Владелец хранит её через `@State` вместо `@StateObject`, а редактор получает `@Bindable var plan`, чтобы делать `$plan.title`. Если заменить только одно слово, оставшиеся части будут рассчитаны на другую связку и работать не станут.

# ГЛУБЖЕ

## Только читать — Binding не нужен

Представь, что вместо поля редактор временно стал сводкой. Для современной модели достаточно обычного свойства: наблюдение определяется чтением в `body`, а не наличием `@Bindable`.

```swift
struct PlanSummary: View {
    let plan: TripPlan
    var body: some View {
        Text(plan.title)
    }
}
```

Это фрагмент для `@Observable TripPlan`. Передай `PlanSummary(plan: plan)` от владельца. `let` запрещает заменить ссылку внутри сводки, но не делает объект неизменяемым. `@Bindable` добавь, когда действительно понадобится связь для поля.

## Кто переживает пересчёт, а кто удаление

Попробуй разделить два события. Пересчёт `body` с сохранённой идентичностью экрана не пересоздаёт принадлежащий ему `@StateObject`. Удаление экрана из дерева и создание нового может создать новый план.

Сам `View` — значение, которое SwiftUI создаёт заново; постоянное хранилище связывается с его местом и идентичностью в интерфейсе. Поэтому `@ObservedObject var plan = TripPlan()` у владельца — ненадёжная замена: новый экземпляр может появиться при новом создании значения View. Получающий объект редактор должен принимать его извне.

Если план должен жить дольше экрана, подними владельца выше и передавай модель вниз. Наблюдение не является сохранением данных на диск.

## Что именно считается прочитанным

Добавь мысленно в современный план `var isPacked = false`. Если сводка читает только `title`, изменение `isPacked` само по себе не является зависимостью её `body`. Если `body` читает оба свойства, оба участвуют в наблюдении.

У `ObservableObject` сигнал изменения объекта не имеет такой же привязки к прочитанным свойствам: подписанный экран может пересчитываться после изменения другого `@Published`. Не обещай точное число вызовов `body`; SwiftUI управляет ими сам. Тебя интересуют зависимости и правильный результат, а не счётчик перерисовок.

## Переданный объект — не команда заменить хранилище

Допустим, план приходит в `init`, а ты кладёшь его в `@StateObject`. Остановись: пока идентичность экрана сохраняется, новое значение параметра не обязано заменить уже сохранённый объект. Начальное значение задаёт первоначальное хранилище.

Если родитель выбирает актуальный план и может передать другой, дочерний экран должен принимать `@ObservedObject`, а для современной модели — обычное свойство или `@Bindable`. Если требуется отдельная жизнь экрана с другим планом, это уже решение об идентичности, а не повод незаметно копировать модель в состояние.
