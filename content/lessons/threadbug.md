## Проверь, есть ли полезный результат

Начни с трёх вопросов: участники заблокированы? Они исполняют шаги? Растёт ли число готовых заявок? Deadlock — цикл ожидания из dead. Livelock — действия продолжаются, но система не продвигается; starvation — один участник не получает необходимого обслуживания, хотя другие могут продвигаться.

## Пишем в лоб: оба вежливо уступают

Проиграй синхронные раунды: обе заявки хотят общий слот; увидев конкурента, обе уступают; затем обе повторяют попытку. Это явная последовательная модель политики, не запуск случайно синхронизированных потоков.

```swift
var a = true
var b = true
var completed = 0
for _ in 0..<3 {
    let bothWant = a && b
    if bothWant { a = false; b = false }
    if !a && !b { a = true; b = true }
}
print(completed, a, b)
```

Вывод 0 true true. Переменные менялись в каждом раунде, заявок не завершили. Наблюдение короткой серии не доказывает бесконечность: модель повторяет одно состояние при каждом следующем таком раунде.

## Сломай симметрию единым порядком

Выбери одного первым по id. В этой модели центральный планировщик обслуживает отсортированный список; если работа берёт два ресурса, установи общий порядок захвата, как в dead. Аналогия: два человека перестают синхронно отходить в сторону, когда есть назначенная очередность.

```swift
func process(ids: [Int]) -> [Int] {
    var completed: [Int] = []
    for id in ids.sorted() { completed.append(id) }
    return completed
}
print(process(ids: [32, 31]))
```

Вывод [31, 32]. Это исправление политики модели, не обещание FIFO от NSLock или реального системного планировщика.

## Ограничь попытки, затем верни управление

Не делай бесконечный retry в горячем цикле. Здесь availability — заданные результаты отдельных возможностей допуска; maxAttempts ограничивает проверяемые шаги. При неуспехе возвращаем «Отложено»: вызывающий код сможет организовать новый запуск по событию готовности.

```swift
func claim(availability: [Bool], maxAttempts: Int) -> String {
    guard maxAttempts > 0 else { return "Отложено" }
    for free in availability.prefix(maxAttempts) {
        if free { return "Готово" }
    }
    return "Отложено"
}
print(claim(availability: [false, false, true], maxAttempts: 2))
```

Вывод «Отложено»: третья возможность не проверяется при бюджете 2. Ограничение попыток гарантирует выход этой функции, а не успех заявки и не справедливость системы.

## Priority inversion: high зависит от low

Прочитай граф: low держит lock; high ждёт его; medium не зависит от lock и получает шаги, задерживая low. Приоритет high не освобождает ресурс автоматически. В модели явно выбираем medium три раза.

```swift
var owner = "low"
var highDone = false
var mediumSteps = 0
for _ in 0..<3 {
    mediumSteps += 1
    // low не получает шаг освобождения; high ждёт owner.
}
print(owner, highDone, mediumSteps)
```

Вывод low false 3. Это зависимость приоритетов в заданном расписании; реальные QoS и порядок исполнения таким тестом не измеряются.

## Убери долгую работу из критической секции

Сделай под lock только снимок данных, отпусти его и выполняй build снаружи. Не держи блокировку на обработке файла, сетевом ожидании или неизвестном callback. Для записи результата после расчёта потребуется новый защищённый переход и проверка актуальности.

```swift
func export(build: (String) -> String) -> String {
    lock.lock()
    let snapshot = text
    lock.unlock()
    return build(snapshot)
}
```

Это метод ExportStore с private lock и text. build получает String-снимок; он может вызвать read, не захватывая уже удерживаемый lock повторно.

## Starvation и помощь системы

Дай фоновой очистке явный бюджет обслуживания, а не вечное правило «пока есть новое UI-задание, бери только его». OSAllocatedUnfairLock/os_unfair_lock позволяют системе видеть владельца и ожидание для помощи при priority inversion: система может временно повысить приоритет владельца, чтобы он скорее продолжил и освободил ресурс для high; QoS-повышение возможно у поддерживаемых синхронных зависимостей. Это не гарантия FIFO, отсутствия starvation или устранения долгой секции. Самодельный spin скрывает полезную информацию об ожидании.

Пройди политику «в каждом раунде новая UI-заявка, обслуживаем только её»: фон остаётся ожидающим, хотя UI продвигается.

```swift
var backgroundPending = true
var uiFinished = 0
for _ in 0..<3 {
    let uiPending = true
    if uiPending { uiFinished += 1 }
    else { backgroundPending = false }
}
print(uiFinished, backgroundPending)
```

Вывод 3 true. За три заданных раунда фон не получил слот; если политика и поступление UI-заявок продолжаются такими же, он не получит его и дальше. Это модель starvation при заданной политике, не измерение реального планировщика.

## Итог: очередь и конечная попытка

Собери два независимых исправления политики: назначенный порядок и выход после ограниченного числа попыток. Вызвавший код получает понятное «Отложено», а не зависает в бесконечном уступании.

```swift
func process(ids: [Int]) -> [Int] {
    var completed: [Int] = []
    for id in ids.sorted() { completed.append(id) }
    return completed
}
func claim(availability: [Bool], maxAttempts: Int) -> String {
    guard maxAttempts > 0 else { return "Отложено" }
    for free in availability.prefix(maxAttempts) {
        if free { return "Готово" }
    }
    return "Отложено"
}
let ordered = process(ids: [32, 31])
print(ordered)
print(claim(availability: [false, true], maxAttempts: 2))
print(claim(availability: [false, false, true], maxAttempts: 2))
```

Вывод [31, 32], «Готово», «Отложено». Для распределения между UI и фоном можно на каждом круге выделять по одному слоту каждой непустой очереди; ступень 6 реализует именно эту модель, без обещаний системной справедливости.

# ГЛУБЖЕ

## Не лечи всё максимальным QoS

Выбирай QoS по назначению работы. Повышение приоритета всех задач не уменьшает длительность критической секции и не создаёт исполнителей бесконечно. Наследование или продвижение QoS зависит от примитива и зависимости; не обещай его любой очереди, callback или semaphore.

## Unfair — буквально без гарантии очередности

Не строй доказательство справедливости на unfair lock. Освободивший поток может повторно получить lock раньше уже ожидавшего. Поддержка борьбы с inversion и порядок допуска — разные свойства; неблокирующий retry вокруг trylock также не является их заменой.

## Бюджет и реальное ожидание готовности

После ограниченной попытки зарегистрируй продолжение по событию доступности либо верни управляющему планировщику статус. Не ставь немедленно саму себя снова без ограничения общей политики: бесконечная цепочка callback способна сохранить отсутствие прогресса.

## Как читать зависание

Сначала ищи, кто владеет ресурсом, кто ждёт и кто реально получает шаги. Стеки и Thread Performance Checker помогут в приложении, но модель не измеряет приоритет ядра. Большая задержка сама по себе не доказывает ни starvation, ни livelock.
