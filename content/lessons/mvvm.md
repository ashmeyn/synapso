## Сначала определим ответы

У нас одна учебная посылка: `PK42`, статус «В пути». Для пустой строки отвечаем «Введите номер», для любого другого номера — «Не найдено». Сеть пока не нужна: проверяем разделение ответственности на локальных данных.

Набери `PK42` и нажми «Проверить». Потом сотри номер и нажми снова. Экран должен заменить прежний ответ, а не оставить успешный статус. Именно этот второй шаг часто пропускают, когда логика живёт прямо в кнопке.

## Пишем в лоб: удача запомнилась

Ниже — часть `body` ошибочного экрана. `number` и `message` уже объявлены как `@State` со значениями `""` и `"Введите номер"`.

```swift
Button("Проверить") {
    if number == "PK42" { message = "В пути" }
}
Text(message)
```

После `PK42` получим «В пути». После пустого ввода всё ещё «В пути»: второй ветки нет. Исправить условие в кнопке можно, но проверять его отдельно неудобно. Давай вынесем решение так, чтобы его можно было вызвать без интерфейса.

MVVM означает Model, View, ViewModel: данные и правила задачи, отображение, состояние и действия конкретного экрана. Это способ назначить обязанности, а не набор обязательных папок.

## Model отвечает за данные и поиск

Посмотри на правило само по себе. Метод — функция внутри типа; `for` здесь внешнее имя параметра, как в уроке функций.

```swift
struct Parcel {
    let id: String
    let status: String
    func findStatus(for number: String) -> String? {
        number == id ? status : nil
    }
}
```

`условие ? A : B` возвращает A при true, B при false. Поэтому для `PK42` вернётся статус этой посылки, для `XX` — nil. Model не выбирает подсказки экрана; отсутствие — это данные, которые ViewModel представит человеку. В маленьком примере правило лежит в Parcel; каталог из многих посылок позже потребует отдельного места для поиска.

## ViewModel связывает ввод с ответом

Теперь нужны две вещи, относящиеся к экрану: черновик номера и последний ответ. `@Observable` ты уже знаешь; он позволит экрану замечать изменения.

```swift
import Observation
@Observable final class TrackingViewModel {
    var number = ""
    var message = "Введите номер"
    private let parcel = Parcel(id: "PK42", status: "В пути")
    func search() {
        let status = parcel.findStatus(for: number) ?? "Не найдено"
        message = number.isEmpty ? "Введите номер" : status
    }
}
```

Это продолжение предыдущего `Parcel`. `private` прячет посылку внутри ViewModel: экрану нужен ответ, а не доступ к её хранению. Каждый `search()` заново присваивает message: пустой ввод получает подсказку, nil от Model — «Не найдено». `??` подставляет запасной текст для отсутствующего значения. Так оформление ответа остаётся у ViewModel. Ссылку на TrackingScreen она не хранит и его методы не вызывает: экран обновляется, читая наблюдаемое состояние.

Model, ViewModel и View похожи на справочник, сотрудника у окна и табло: справочник хранит сведения, сотрудник разбирает запрос, табло показывает ответ.

## View показывает и передаёт действие

Окей, вернёмся к экрану. `Parcel` и `TrackingViewModel` уже объявлены выше.

```swift
import SwiftUI
struct TrackingScreen: View {
    @State private var viewModel = TrackingViewModel()
    var body: some View {
        VStack {
            TextField("Номер", text: $viewModel.number)
            Button("Проверить") { viewModel.search() }
            Text(viewModel.message)
        }
    }
}
```

Экран владеет современной наблюдаемой моделью через `@State`. Поле меняет черновик, кнопка вызывает действие, надпись читает результат. Ни знания номера `PK42`, ни проверки на пустоту в разметке нет.

Модификаторы, отступы и расположение кнопок оставляй во View. Перенос всей разметки во ViewModel не добавит проверяемости правилам.

## Проверь цепочку без экрана

Создай ViewModel как обычный объект и повтори баговый маршрут. Эти строки продолжают её объявление, SwiftUI View им не нужен.

```swift
let viewModel = TrackingViewModel()
viewModel.number = "PK42"
viewModel.search()
print(viewModel.message)
viewModel.number = ""
viewModel.search()
print(viewModel.message)
viewModel.number = "XX"
viewModel.search()
print(viewModel.message)
```

Вывод: «В пути», «Введите номер», «Не найдено», каждое на новой строке. Сначала черновик меняется, затем search читает его и обновляет ответ. Обрати внимание: сам ввод ещё не запускает поиск. Мы показываем последний проверенный результат, а не вычисляем ответ на каждый символ.

## Независимое состояние и вычисляемый текст

Есть другая часть той же доставки: посылка весит 2 кг, пользователь выбирает 1–3 одинаковые коробки. Количество — состояние экрана, общий вес — результат расчёта. Держать оба числа изменяемыми не нужно.

Для этой версии Model предоставляет метод `totalWeight(copies:)`, возвращающий `weightKg * copies`. ViewModel хранит copies, а `weightText` вычисляет при чтении.

```swift
var weightText: String { "Вес: \(parcel.totalWeight(copies: copies)) кг" }
```

Фрагмент находится внутри `WeightViewModel`, где `copies = 1`, а parcel имеет `weightKg = 2`. Проверь 1 → 2 кг, 3 → 6 кг. Stepper из `state` редактирует `$viewModel.copies` в диапазоне `1...3`.

А переключатель оформления ответа — отдельный Bool экрана. Если добавишь «Показать номер», сохраняй номер последнего поиска: новый черновик не должен подписать старый результат чужим номером. При поиске запиши его вместе с message, а отображаемый текст вычисляй из них и флага. До первого непустого поиска оставляй обычную подсказку без префикса; условие `includeNumber && !searchedNumber.isEmpty` требует одновременно включённый флаг и непустой сохранённый номер.

## Собираем три обязанности

Сравни строки: сопоставление номера осталось у посылки, действие и оформление ответа — у ViewModel, разметка — у View.

```swift
import SwiftUI
import Observation
struct Parcel {
    let id: String
    let status: String
    func findStatus(for number: String) -> String? { number == id ? status : nil }
}
@Observable final class TrackingViewModel {
    var number = ""
    var message = "Введите номер"
    private let parcel = Parcel(id: "PK42", status: "В пути")
    func search() {
        let status = parcel.findStatus(for: number) ?? "Не найдено"
        message = number.isEmpty ? "Введите номер" : status
    }
}
struct TrackingScreen: View {
    @State private var viewModel = TrackingViewModel()
    var body: some View {
        VStack {
            TextField("Номер", text: $viewModel.number)
            Button("Проверить") { viewModel.search() }
            Text(viewModel.message)
        }
    }
}
```

- Для проверки поиска вызывай Model или ViewModel без SwiftUI View.
- Держи независимый черновик и последний ответ; вычисляемое представление результата не дублируй состоянием.
- Маленькому экрану без отдельной логики ViewModel может не понадобиться; добавляй её для понятной ответственности и проверки действий.

# ГЛУБЖЕ

## Где заканчивается ViewModel

Представь, что завтра появится второй экран посылки. Правило определения статуса не должно копироваться в обе ViewModel. Оно принадлежит данным или отдельной службе поиска; ViewModel выбирает, когда вызвать его и как представить ответ.

Не выноси любое умножение в отдельный тип автоматически. Спрашивай: это общее правило доставки или оформление одного экрана? Формат «Вес: … кг» — оформление; вес коробок — данные и расчёт задачи.

## ViewModel не обязана быть ObservableObject

Если ты поддерживаешь старую связку из obs, ViewModel может быть `ObservableObject` с `@Published`, а экран — владеть ею через `@StateObject`. В нашем iOS 17 примере выбраны `@Observable` и `@State`.

Попробуй назвать, что останется при замене наблюдения: роли Model/View/ViewModel и правило поиска. MVVM не требует конкретной обёртки SwiftUI и не гарантирует хорошую архитектуру одним названием класса.

## Когда поиск станет сетевым

У локального метода ответ появляется сразу. У сети появятся ожидание, ошибка и возможность получить старый ответ после нового запроса. Здесь уже нужно явно хранить состояние загрузки и связывать ответ с запросом, который всё ещё актуален.

Не добавляй сеть в body: его SwiftUI пересчитывает по своим причинам. Действие запускает работу, а результат обновляет состояние. Протокол для источника и передача зависимости помогут проверять это отдельно; их разберём в proto и di. Для асинхронной версии также понадобится согласовать обновления UI с MainActor.

## Какого теста достаточно для этого правила

Начни с трёх входов: известный, пустой, неизвестный. Затем проверь переход «успех → пусто»: он ловит оставшийся старый ответ, хотя каждый одиночный экран мог выглядеть правильно.

Проверка метода не подтверждает, что TextField действительно привязан к number. Для этого отдельно проверяют связку интерфейса. Не смешивай границы: тестируемый объект — хороший шаг, но кнопка ещё должна вызвать именно его действие.
