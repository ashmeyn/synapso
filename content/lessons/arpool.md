## Сначала определи, что остаётся

Архив может содержать тысячи квитанций; в упражнении их две: id 11 с двумя страницами и id 12 с тремя. На выходе нужны маленькие ReceiptSummary, а промежуточный разбор не нужно хранить.

Цель — подходящая граница жизни временных autoreleased-объектов, если вызываемый Foundation/Objective-C код их создаёт. Мы не обещаем конкретное снижение памяти на этих маленьких входах.

## Пишем в лоб: один пул на весь архив

Посмотри на границу, а не только на слово autoreleasepool. Если обернуть весь rows.map одним пулом, он опустошится лишь после завершения всей партии. Это не ошибка вывода, но не выполняет требование локальной границы на каждой записи.

```swift
let summaries = try autoreleasepool {
    try rows.map { try readSummary($0) }
}
```

Здесь rows — строки двух квитанций, readSummary объявим ниже. map применяет разбор к каждой строке и собирает результаты. Результат корректен: id [11, 12], всего пять страниц. Но autoreleased-временные объекты такой партии могут ждать общей границы; при большом импорте её стоит проверить профилированием.

## Что пул действительно делает

Отдели два механизма. ARC управляет сильным владением; autorelease откладывает release некоторых Objective-C объектов до опустошения текущего пула. autoreleasepool выполняет синхронное тело и опустошает созданный локальный пул при выходе.

Аналогия: пул — корзина отложенных действий по отпусканию объектов, которую опустошают на выбранной границе. Это не сборщик всех объектов и не команда освободить всю память: другие сильные владельцы продолжают действовать.

## Задаём данные и ошибку

Создай явный результат, чтобы не тащить наружу весь разобранный словарь. ReceiptSummary хранит только два Int; ImportError.invalid обозначает отсутствие нужных полей.

```swift
import Foundation
struct ReceiptSummary { let id: Int; let pages: Int }
enum ImportError: Error { case invalid }
let rows = [#"{"id":11,"pages":2}"#, #"{"id":12,"pages":3}"#]
```

Data(text.utf8) превращает текст в байты. Foundation JSONSerialization разбирает их в объект; через as? проверим, что получили словарь и числа. Это учебный локальный ввод, без чтения личных файлов.

## Разбираем одну запись

Пройди первую квитанцию вручную: JSONSerialization даёт объект, проверки находят id 11 и pages 2, функция возвращает ReceiptSummary. При ошибке поля выбрасывается ImportError.invalid; синтаксически неверный JSON может бросить ошибку Foundation.

```swift
func readSummary(_ text: String) throws -> ReceiptSummary {
    let data = Data(text.utf8)
    let object = try JSONSerialization.jsonObject(with: data)
    guard let row = object as? [String: Any],
          let id = row["id"] as? Int,
          let pages = row["pages"] as? Int else {
        throw ImportError.invalid
    }
    return ReceiptSummary(id: id, pages: pages)
}
```

Не объявляй каждый объект Foundation автоматически autoreleased: конкретные API, мосты типов и оптимизация влияют на временные объекты. Этот путь подходит для проверки локального пула в массовом импорте; сам код не доказывает объём autorelease.

## Переносим границу внутрь цикла

Теперь пул окружает только readSummary одной строки. Его возвращаемое значение остаётся доступно вызывающему коду, который добавляет его в summaries.

```swift
var summaries: [ReceiptSummary] = []
for text in rows {
    let summary = try autoreleasepool { try readSummary(text) }
    summaries.append(summary)
}
```

После первой итерации сохранён id 11, после второй — id 12. Локальный пул не удаляет нужный возвращённый результат. Массив результатов тоже занимает память и растёт; это отдельная стоимость.

## Подвох: ошибка и чистый Swift

Проверь два других контракта. Если одна запись ошибочна, поставь do/catch вокруг её try autoreleasepool, чтобы счётчик failed увеличился, а цикл продолжился. Выход с ошибкой тоже завершает локальный пул; не прячь ошибку за try?.

Если уже есть массив ReceiptSummary и нужно лишь сложить Int pages, локальный пул ради этого расчёта не нужен. Обычные Swift-значения не требуют autoreleasepool только потому, что ты находишься в цикле. Пул не исправляет ARC-цикл или массив, намеренно хранящий объекты.

## Итог: сохраняем только нужное

Восстанови самостоятельный пример и назови обе границы: временный разбор — внутри каждой итерации, необходимые результаты — в summaries.

```swift
import Foundation
struct ReceiptSummary { let id: Int; let pages: Int }
enum ImportError: Error { case invalid }
func readSummary(_ text: String) throws -> ReceiptSummary {
    let data = Data(text.utf8)
    let object = try JSONSerialization.jsonObject(with: data)
    guard let row = object as? [String: Any],
          let id = row["id"] as? Int,
          let pages = row["pages"] as? Int else {
        throw ImportError.invalid
    }
    return ReceiptSummary(id: id, pages: pages)
}
let rows = [#"{"id":11,"pages":2}"#, #"{"id":12,"pages":3}"#]
var summaries: [ReceiptSummary] = []
for text in rows {
    let summary = try autoreleasepool { try readSummary(text) }
    summaries.append(summary)
}
print(summaries.map { $0.id })
print(summaries.reduce(0) { $0 + $1.pages })
```

map в первом print извлекает id, reduce во втором складывает pages с начальным 0. Вывод [11, 12] и 5. При большом архиве сравни пик временных выделений с пулом и без него в Instruments. По этим двум строкам вывода нельзя заключить, сколько байтов освободилось.

## Проверь себя

Поясни решение без обещаний «память упадёт в столько-то раз».

- Почему один пул на весь map не даёт границу каждой записи?
- Почему возвращённый результат может жить после выхода из пула?
- Чем цикл Foundation-разбора отличается от сложения готовых Int?

## Ответы к «Проверь себя»

- `autoreleasepool` опустошается при выходе из своего тела, а тело здесь — весь `rows.map`. Значит, отложенные release временных объектов всех записей ждут конца всей партии. Результат верный ([11, 12], пять страниц), но границы на каждую запись нет; её даёт пул внутри цикла: `for text in rows { let summary = try autoreleasepool { try readSummary(text) }; summaries.append(summary) }`.
- Пул опустошает только отложенные release временных autoreleased-объектов, а не всё подряд: ARC продолжает управлять сильным владением. `ReceiptSummary` возвращается из тела `autoreleasepool` как результат, вызывающий код сохраняет его в `summary` и добавляет в `summaries`. Раз у значения есть владелец, оно живёт дальше, а временный разбор отпускается на границе пула.
- Foundation-разбор через `JSONSerialization` может создавать временные autoreleased-объекты Objective-C, и при массовом импорте их стоит отпускать на каждой записи. Сложение готовых `Int` через `summaries.reduce(0) { $0 + $1.pages }` работает с обычными Swift-значениями, autorelease там нет, и пул не нужен. Выигрыш от пула не обещаешь заранее, а проверяешь замером в Instruments.

# ГЛУБЖЕ

## Сильные результаты не исчезают

Попробуй вернуть из autoreleasepool объект класса и сохранить его снаружи. Сильный владелец продолжает удерживать его после выхода. То же касается объектов, добавленных в долгоживущий массив.

Чтобы проверить результат, наблюдай логический жизненный цикл, а для памяти отдельно снимай профиль. Очистка пула не заменяет удаление ненужного массива или разрыв retain cycle.

## Когда пул уместен в Swift

Ищи массовые синхронные вызовы Objective-C/Foundation или других Cocoa API, создающие временные autoreleased-объекты: импорт, декодирование, обработка изображений. Локальная граница иногда уменьшает пик временной памяти; измерение покажет, нужен ли этот приём конкретному пути.

Не ставь пул вокруг каждого Swift-init, Int-операции или коллекции автоматически. Не каждый вызов Foundation создаёт такую нагрузку, а наличие String или Data в коде само по себе не доказывает её.

## Выбери размер партии

Если результат нужен только как итоговое число, верни из пула pages и сразу добавь к totalPages, не собирая все сводки. Если нужен весь список, его стоимость остаётся независимо от пулов.

Граница может быть одной записью или небольшой партией: слишком частые дополнительные границы тоже имеют стоимость. Не выбирай размер по мифу о гарантированных мегабайтах; сравни варианты на реальной нагрузке.

## Синхронная граница

autoreleasepool принимает синхронное тело, в котором нельзя просто написать await. Оборачивание запуска Task не создаёт пул вокруг всей последующей асинхронной работы.

Если позже импорт станет асинхронным, выдели синхронный Cocoa-этап и окружи пулом именно его там, где он выполняется. Управление потоками и отменой — отдельная задача, не эффект пула.
