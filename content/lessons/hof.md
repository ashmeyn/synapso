goals:
- выбрать `filter`, `map`, `compactMap` и `reduce` по задаче
- не путать отбрасывание невалидной суммы с её исправлением

## Смотрим на записи

У перевода есть получатель, текст суммы и отметка проведения. Мы не должны включать непроведённый перевод в сумму переводов и не можем сложить строки как числа.

```swift
struct Transfer {
    let recipient: String
    let amountText: String
    let posted: Bool
}
```

## Пишем в лоб

Стажёр делает одну длинную цепочку и молча выбрасывает всё, что не распарсилось. Число получается, но мы не знаем, был ли пропущен проведённый перевод с некорректной суммой. Это уже бизнес-баг.

```swift
let totalAmount = transfers.filter(\.posted)
    .compactMap { Int($0.amountText) }
    .reduce(0, +)
```

Сначала разберём смысл каждой операции, затем решим, допустим ли такой пропуск.

## Оставляем проведённые записи

`filter` получает каждый элемент и оставляет тот, для которого условие истинно. Исходный массив не меняется.

```swift
let postedTransfers = transfers.filter { $0.posted }
```

Вопрос кода теперь читается прямо: «какие записи проведены?». Это и есть польза функций над коллекциями, когда шаги названы по смыслу.

## Делаем подписи для экрана

`map` преобразует каждый элемент в новое значение. Число элементов остаётся тем же.

```swift
let recipients = postedTransfers.map { $0.recipient }
```

Если в `postedTransfers` три перевода одному человеку, в `recipients` будут три одинаковых имени. `map` не делает список уникальным.

## Пробуем получить числа

`Int(text)` возвращает `Int?`: строка может быть не числом. `map` сохранил бы и `nil`; `compactMap` оставит только успешно полученные значения.

```swift
let amounts = postedTransfers.compactMap { Int($0.amountText) }
```

Это технически удобно, но в нашей задаче безопасно только если пропущенные суммы явно обработаны. Иначе сумма переводов будет занижена без сообщения об ошибке.

## Складываем результат

`reduce` начинает с начального значения и объединяет элементы по одному. Здесь начальный итог — ноль, операция — сложение.

```swift
let totalAmount = amounts.reduce(0, +)
```

Такое выражение заменяет цикл с аккумулятором. `map`, `filter` и `compactMap` возвращают новые коллекции; исходные `transfers` остаются прежними.

## Подвох: проведено, но сумма сломана

Для отчёта о деньгах нельзя тихо отбросить проведённый перевод. Проверяем, все ли проведённые записи превратились в числа, и показываем проблему вместо правдоподобной неправильной суммы.

```swift
func totalAmount(for transfers: [Transfer]) -> Int? {
    let posted = transfers.filter { $0.posted }
    let amounts = posted.compactMap { Int($0.amountText) }
    guard amounts.count == posted.count else { return nil }
    return amounts.reduce(0, +)
}
```

Если тебя спросят на собесе, объясни не только «какую функцию высшего порядка взять», но и «имеешь ли право потерять элемент».

## Что отдаём экрану

```swift
struct Transfer {
    let recipient: String
    let amountText: String
    let posted: Bool
}
struct TransferSummary { let recipients: [String]; let totalAmount: Int }
func summary(for transfers: [Transfer]) -> TransferSummary? {
    let posted = transfers.filter { $0.posted }
    let recipients = posted.map { $0.recipient }
    let amounts = posted.compactMap { Int($0.amountText) }
    guard amounts.count == posted.count else { return nil }
    return TransferSummary(recipients: recipients,
                           totalAmount: amounts.reduce(0, +))
}
```

- `filter` отвечает «кого оставить?»; `map` — «во что превратить каждого?».
- `compactMap` убирает `nil`, но сначала спроси, можно ли терять запись.
- `reduce` собирает одно значение из последовательности.

## Проверь себя

- Почему `map` не делает названия получателей уникальными?
- Какая сумма пропадёт при `compactMap { Int($0.amountText) }`?
- Почему перед `reduce` мы сравниваем количества проведённых записей и чисел?

## Ответы к «Проверь себя»

- `map` преобразует каждый элемент в новое значение, и элементов на выходе ровно столько же, сколько на входе. Три перевода одному человеку дадут три одинаковых имени в `recipients`. Уникальность `map` не обещает: это отдельная задача, и решать её нужно другим инструментом.
- Пропадёт сумма проведённого перевода, у которого `amountText` не превращается в число: `Int(text)` вернёт `nil`, а `compactMap` молча его выбросит. Итог посчитается из остальных и окажется заниженным, без всякого сообщения об ошибке. Для отчёта о деньгах это бизнес-баг: правдоподобное, но неправильное число.
- Если `amounts.count` меньше `posted.count`, значит какая-то проведённая сумма не распарсилась и выпала в `compactMap`. Поэтому ставишь `guard amounts.count == posted.count else { return nil }` и сообщаешь о проблеме вместо заниженного итога. Только если ничего не потеряно, `amounts.reduce(0, +)` даёт честную сумму.

# ГЛУБЖЕ

## flatMap решает другую задачу

Если переводы сгруппированы по дням, `flatMap` соберёт вложенные массивы в один список. `compactMap` решает другую задачу: убирает `nil`.

```swift
let transfersByDay = [["Анна", "Олег"], ["Илья"]]
let allRecipients = transfersByDay.flatMap { $0 }
```

## reduce(into:) для изменяемого результата

Если на следующем экране понадобится словарь частот получателей, `reduce(into:)` даёт изменяемый аккумулятор и не требует создавать новый словарь на каждом шаге.

```swift
let counts = recipients.reduce(into: [String: Int]()) { result, name in
    result[name, default: 0] += 1
}
```

## Цепочка не всегда лучший код

Каждое преобразование должно отражать правило задачи. Если нужно сообщить, какая именно проведённая запись содержит плохую сумму, один явный цикл с ошибкой может быть понятнее цепочки. Функциональный стиль — инструмент чтения, а не соревнование в количестве вызовов.
