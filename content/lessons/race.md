## Два завершения должны дать два

Зафиксируй ожидаемый результат до многопоточного кода: completed начинается с 0, два упражнения прибавляют по единице, итог — 2. Если получилась 1, одна операция затёрла результат другой.

Мы сначала проиграем эту ошибку в одном потоке. Это модель возможного чередования, а не настоящий несинхронизированный доступ потоков; она позволяет объяснить причину без случайного тайминга.

## Пишем в лоб: оба прочитали старое

Пройди шесть строк вручную. A и B успевают прочитать 0; A записывает 1, затем B записывает свою 1 вместо ожидаемой 2.

```swift
var completed = 0
let readA = completed
let readB = completed
completed = readA + 1
completed = readB + 1
print(completed)
```

Вывод 1. Ошибка воспроизводится при каждом запуске модели. В реальном sharedState += 1 есть чтение, расчёт и запись; сама короткая запись не гарантирует атомарность относительно другого потока.

## Гонка данных и гонка решения

Раздели термины. Data race — несинхронизированный доступ разных потоков к одной памяти, где хотя бы один доступ записывает. Такой код не получает безопасного контракта результата. Race condition шире: результат зависит от чередования логических шагов, даже если отдельные обращения защищены.

Наша последовательная модель показывает потерянное обновление, не создавая настоящий data race. Дальше исправим всю операцию, а не будем надеяться, что TSan обязан найти этот учебный однопоточный пример.

## Одна очередь владеет состоянием

Спрячь stored и дай ему одну private serial-очередь. Все чтения и изменения проходят через неё; increment помещает чтение, прибавление и запись в один блок.

```swift
import Dispatch
final class CompletedCounter {
    private let queue = DispatchQueue(label: "practice.counter")
    private var stored = 0
    func increment() { queue.sync { stored += 1 } }
    func read() -> Int { queue.sync { stored } }
}
```

Внешние вызывающие стороны не получают stored и не выбирают другую очередь. Методы вызываются снаружи private queue: иначе их sync стал бы ловушкой из queues. Аналогия: одна касса фиксирует целую операцию, а не выдаёт номер и считает оплату в отдельных очередях.

## Проверка и изменение — одна операция

Проверь на примере лимита: если осталось одно разрешённое завершение, два обращения не должны оба увидеть свободное место. guard и прибавление должны находиться в одном sync-блоке. CompletedCounter уже объявлен; это новый метод внутри него.

```swift
func claim(limit: Int) -> Bool {
    queue.sync {
        guard stored < limit else { return false }
        stored += 1
        return true
    }
}
```

При limit 1 последовательные вызовы дают true, false, а stored становится 1. Для limit 0 — false без изменения. Так же проверяют положительный остаток и уменьшают его: проверка и запись должны оставаться неделимыми для других операций этой очереди.

## Подвох: два безопасных доступа ещё не операция

Разбей increment на read() и store(). Каждое обращение может отдельно идти через serial-очередь, но между ними снова помещается другая операция.

```swift
let readA = counter.read()
let readB = counter.read()
counter.store(readA + 1)
counter.store(readB + 1)
print(counter.read())
```

Для ошибочного CompletedCounter со store(_:), который пишет через свою очередь, модель снова даёт 1. Это логическая гонка составной операции при защищённых отдельных доступах. Исправь интерфейс на increment(), чтобы вызывающий код не собирал операцию из раздельных частей.

## Как проверить настоящий доступ в TSan

Для реального приложения выбери схему Xcode: Edit Scheme → Run → Diagnostics → Thread Sanitizer. Запусти на поддерживаемом симуляторе или macOS, воспроизведи работу нескольких отправителей и открой отчёт с обеими сторонами доступа к общей памяти. На физическом iOS-устройстве TSan не используется. Здесь инструмент не запускался.

Проверь, где идёт запись и где второй доступ, через какую очередь или другую синхронизацию проходит каждый. После исправления повтори сценарий. Отсутствие отчёта не доказывает отсутствие всех логических гонок; последовательная модель потери обновления и раздельные read/store могут не давать data race для обнаружения.

## Итог: один атомарный для очереди шаг

Восстанови маленький самостоятельный пример. Два increment завершаются до read, потому что каждый внешний sync ждёт всю работу.

```swift
import Dispatch
final class CompletedCounter {
    private let queue = DispatchQueue(label: "practice.counter")
    private var stored = 0
    func increment() { queue.sync { stored += 1 } }
    func read() -> Int { queue.sync { stored } }
}
let counter = CompletedCounter()
counter.increment()
counter.increment()
print(counter.read())
```

Вывод 2. Если вызывать increment из разных потоков, одна и та же private serial-очередь не позволит двум её блокам перекрыться. Чтение тоже должно идти через неё; две разные serial-очереди для одной переменной этого свойства не дают.

# ГЛУБЖЕ

## Не смешивай владельцев

Найди все пути к состоянию: getter, setter, логирование, callback и тест. Один прямой доступ в обход private queue уже нарушает выбранную дисциплину. serial в имени другой очереди не синхронизирует её с первой.

Не возвращай наружу изменяемый объект-хранилище, который можно править без очереди. Если нужно состояние для отображения, верни самостоятельный снимок значения.

## UI и ожидающие вызовы

Проверь цену sync: вызывающий поток ждёт. Если обработка долгая или очередь занята, это может мешать UI. Наш пример короткий и без интерфейса; он объясняет владение, а не задаёт лучший API для любой нагрузки.

При переходе на async изменится контракт результата: понадобится completion, async/await или другой согласованный механизм. Не читай sharedState сразу после постановки и не считай работу завершённой.

## Снимок нескольких полей

Представь totals completed и failed. Два отдельных защищённых getter могут увидеть значения разных логических моментов. Если экрану нужна согласованная пара, скопируй оба поля в одном блоке очереди.

Это не обещание отсутствия всех ошибок приложения: очередь сериализует выбранные операции. Правила переходов между состояниями нужно выразить в этих операциях.

## Проверяем инвариант, а не удачный запуск

Для счётчика проверяй итог числа операций; для лимита — сколько claim реально вернули true; для остатка — невозможность отрицательного значения. Один запуск без потерь не доказывает безопасность незащищённого кода.

Детерминированная модель объясняет возможное чередование, TSan помогает искать настоящие доступы, а тест исправленного интерфейса проверяет нужный результат. Эти три проверки имеют разные границы.
