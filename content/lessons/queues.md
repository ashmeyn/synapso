## Два разных решения

Сначала ответь на два вопроса: должны ли экспорты уровней идти по одному, и должен ли вызывающий код ждать завершения? Эти вопросы не зависят друг от друга.

Очередь DispatchQueue планирует работы. serial не исполняет две свои работы одновременно; concurrent допускает перекрытие. sync ждёт завершения отправленной работы, async возвращает управление после постановки, не ожидая её окончания. Поэтому async сохраняет escaping-замыкание для последующего исполнения; тело sync завершается до возврата вызова.

## Пишем в лоб: async значит параллельно

Проверь предположение на очереди без атрибута concurrent. Два async-вызова не превращают её в конкурентную.

```swift
import Dispatch
let queue = DispatchQueue(label: "levels.export")
queue.async { print("Уровень 7") }
queue.async { print("Уровень 8") }
queue.sync {}
print("Готово")
```

Вывод «Уровень 7», «Уровень 8», «Готово». Это custom serial-очередь; из одного вызывающего потока работы отправлены в этом порядке. Последний sync с пустым телом служит в локальном примере точкой ожидания предыдущих работ. Вызов находится снаружи очереди.

## Очередь не равна одному потоку

Отдели порядок от исполнителя. Custom serial-очередь может выполнять разные работы на разных системных потоках; важна невозможность перекрытия её работ. main — особая serial-очередь, связанная с главным потоком.

Аналогия: очередь — диспетчер заданий, поток — исполнитель. Не делай вывод «async создаёт новый поток» или «sync всегда выполняет на другом потоке»: Dispatch выбирает исполнение, а контракт здесь про порядок и ожидание.

## sync завершает работу до следующей строки

Теперь вызывающему коду нужен завершённый экспорт. Пройди три сообщения: до вызова, внутри завершившегося sync, после возврата.

```swift
import Dispatch
let queue = DispatchQueue(label: "levels.export")
print("До")
queue.sync { print("Экспорт 7") }
print("После")
```

Вывод «До», «Экспорт 7», «После». sync может вернуть значение тела: let result = queue.sync { encodeLevel(id: 7) }. Это удобно для короткой синхронной модели; тяжёлую работу нельзя так заставлять ждать UI-поток без учёта отзывчивости.

## async не задаёт порядок с вызывающим кодом

Замени только sync на async в прошлом примере. «До» останется первым, но «Экспорт 7» и «После» могут поменяться местами: работа может начаться до или после следующей строки вызывающего кода.

Для проверки локального примера в конце можно вызвать queue.sync {} снаружи той же serial-очереди. Это ожидание теста, а не причина использовать блокирующий код в интерфейсе. Если UI нужен результат позже, нужен отдельный контракт доставки результата; async сам не возвращает результат тела вызывающей строке.

## concurrent допускает перекрытие

Задай attributes: .concurrent, если независимые экспорты допускают перекрытие. Он не обещает, что они реально исполнятся одновременно или что второй обязательно завершится первым. Внутри каждой работы порядок её собственных строк сохраняется.

В практике используем DispatchWorkItem — объект отправляемой работы. first.wait() и second.wait() позволяют локальной проверке дождаться обеих уже отправленных работ. wait не нужно выполнять из работы, которая должна сама завершиться, или превращать в блокировку UI. Это простой контроль конца примера, не часть экспорта.

## Подвох: очередь ждёт саму себя

Нарисуй ожидание в следующем фрагменте: внешняя работа уже выполняется на serial-очереди, внутренний sync хочет завершить ещё одну работу на ней. Она не может начаться, пока внешняя не закончилась, а внешняя ждёт внутреннюю.

```swift
import Dispatch
let queue = DispatchQueue(label: "levels.export")
queue.sync {
    print("Начало")
    queue.sync { print("Экспорт 7") }
    print("Конец")
}
```

Это deadlock. Dispatch может обнаружить неправильный вызов и аварийно завершить программу вместо вечного зависания; «Конец» не является ожидаемым успешным результатом. Исправь вызов обычным синхронным помощником внутри текущей работы. Полный разбор deadlock будет отдельным уроком.

## Итог: две независимые работы

Собери пример конкурентного экспорта с явным ожиданием в вызывающем локальном коде. Для serial-варианта убери attributes: .concurrent — получишь строгую последовательность обеих работ.

```swift
import Dispatch
let queue = DispatchQueue(label: "levels.export", attributes: .concurrent)
let first = DispatchWorkItem {
    print("7:начало")
    print("7:конец")
}
let second = DispatchWorkItem {
    print("8:начало")
    print("8:конец")
}
queue.async(execute: first)
queue.async(execute: second)
first.wait()
second.wait()
print("Готово")
```

Для concurrent гарантированы «7:начало» раньше «7:конец», «8:начало» раньше «8:конец» и «Готово» после обоих концов. Между работами единственную последовательность не назначаем. Два wait ждут уже отправленные работы, не делают их serial.

# ГЛУБЖЕ

## Порядок постановки и окончания

Назови, кто отправляет работы. В примерах отправитель один, поэтому порядок постановки известен. Если несколько потоков одновременно отправляют работы, их относительный порядок нельзя вывести из расположения двух фрагментов в исходнике.

Даже при известном порядке постановки на concurrent-очередь порядок завершения не фиксирован. Не строй зависимости данных на надежде «A отправили раньше B». Зависимость нужно выразить отдельно.

## main — не универсальное место ожидания

Перед sync или wait спроси, кто сейчас ждёт. main.sync с главного потока создаёт ожидание своей очереди; ожидание тяжёлого экспорта на главном потоке мешает интерфейсу.

Наши программы — локальные проверки без UI. В приложении обычно выполняют тяжёлую работу вне главного потока и доставляют готовое UI-состояние обратно по нужному контракту. Это не обещание, что любая Foundation-функция безопасна на любом потоке.

## Две serial-очереди не одна

Попробуй распределить доступ к одному массиву между двумя custom serial-очередями. Каждая упорядочит свои работы, но они могут выполняться одновременно друг с другом. Общий массив защищён не будет.

serial — свойство конкретного пути исполнения, а не глобальная блокировка памяти. В следующем уроке дадим общему состоянию одну очередь-владельца и будем проводить через неё все доступы.

## Когда прямой помощник уместен

Исправление вложенного sync через обычную функцию работает, если функция используется внутри уже выбранной очереди и не делает повторную постановку. Не открывай такую функцию произвольным внешним вызывающим сторонам, если внутри есть состояние, принадлежащее очереди.

В нашем экспорте encodeLevel только строит строку. Для состояния нужны закрытый интерфейс и чёткие границы доступа, иначе исправление deadlock может оставить гонку.
