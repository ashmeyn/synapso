## Задача: закрыть запись без живого хвоста

Смотри: микрофон нам не нужен. Есть локальная модель сессии записи и сохранённое действие, которое показывает её номер. Когда экран заканчивает работу, мы хотим отпустить сессию. Но «убрал одну переменную» ещё не означает «убрал всех владельцев».

После миссии ты сможешь нарисовать цепочку сильных владельцев, добавить `deinit` и найти замыкание, которое продолжает держать объект.

## Пишем в лоб: обнуляем одну переменную

Окей, сначала уберём `first`. Кажется, сессия уже должна исчезнуть, но `second` всё ещё держит тот же экземпляр. Не ищи здесь копию объекта: присваивание класса создаёт ещё одну ссылку.

```swift
final class RecordingSession {
    let id: Int
    init(id: Int) { self.id = id }
    deinit { print("Освобождена сессия \(id)") }
}
var first: RecordingSession? = RecordingSession(id: 31)
var second = first
first = nil
print("Первую ссылку убрали")
print(second!.id)
second = nil
print("Вторую ссылку убрали")
```

Порядок вывода: «Первую ссылку убрали», `31`, «Освобождена сессия 31», «Вторую ссылку убрали». Освобождение происходит при удалении последнего владельца в этом примере, а не при первой строке с `nil`.

## Что именно делает ARC

Остановись здесь и назови всех, кто держит сессию. Обычная ссылка на экземпляр класса сильная: она удерживает его в живых. ARC — Automatic Reference Counting — автоматически поддерживает такое владение при работе программы. Когда сильных владельцев больше нет, объект освобождается.

Одна аналогия: объект живёт, пока хотя бы один человек держит ключ от его комнаты. Важно, что мы будем считать видимых владельцев из кода, а не читать внутренний счётчик runtime. Временные ссылки и оптимизация компилятора в эту учебную схему не входят.

## deinit: заметить конец жизни

Добавь наблюдаемую отметку прямо в класс — так проверим свой прогноз. `deinit` не нужно вызывать вручную: Swift вызывает его при освобождении экземпляра класса. Он не возвращает значение и не принимает параметры.

```swift
final class RecordingSession {
    let id: Int
    init(id: Int) { self.id = id }
    deinit { print("Освобождена сессия \(id)") }
}
```

Здесь сообщение — способ проверить цепочку, а не команда «остановить запись». Завершение пользовательского действия лучше делать отдельным методом: живой объект вполне может уже не записывать ничего.

## Подвох: действие тоже держит сессию

Тут легко пропустить владельца: сохранённое замыкание захватывает объект. Список `[session = first!]` вычисляет `first!` при создании замыкания и хранит сильную ссылку под именем `session`. Позднее `first = nil` этот захват не меняет.

```swift
var saved: (() -> Void)? = { [session = first!] in
    print(session.id)
}
```

Смотри, в этой миссии `first!` безопасен только потому, что мы только что создали сессию и ещё не обнулили её. Для произвольного Optional сначала нужен `guard let`. Наша задача здесь — владение, не угадывание наличия объекта.

## Считаем владельцев по шагам

Давай пройдём цепочку на бумаге. После создания `first` есть один видимый владелец; после `second = first` — два; после создания `saved` — три. `first = nil` оставляет `second` и захват, `second = nil` оставляет захват. Вызов `saved?()` не очищает сохранённое действие. Только `saved = nil` убирает последнего владельца сессии в этой программе.

Числа относятся к схеме владения, а не к измерению ARC. Мы не используем `CFGetRetainCount` и не обещаем точное значение внутреннего счётчика.

## Тот же принцип для очереди

Предскажи, что изменится с очередью: массив тоже может держать объект; сильная ссылка не обязана лежать в отдельной переменной. Если сессию положили в `pending`, обнуления `session` мало. Пока элемент доступен через массив, экземпляр жив.

```swift
var session: RecordingSession? = RecordingSession(id: 32)
var pending: [RecordingSession] = [session!]
session = nil
print(pending[0].id)
pending.removeAll()
print("Очередь очищена")
```

Здесь сначала выйдет `32`, затем отметка из `deinit`, затем сообщение об очищенной очереди. Это перенос того же правила на другой контейнер, без ручного вызова `deinit`.

## Итог: отпускаем всех владельцев

Соберём весь пример. Мы намеренно оставляем замыкание последним владельцем, вызываем его и очищаем. Получается проверяемая история, а не надежда на то, что закрытие экрана само всё решит.

```swift
final class RecordingSession {
    let id: Int
    init(id: Int) { self.id = id }
    deinit { print("Освобождена сессия \(id)") }
}
var first: RecordingSession? = RecordingSession(id: 31)
var second = first
var saved: (() -> Void)? = { [session = first!] in
    print(session.id)
}
first = nil
second = nil
print("Осталось замыкание")
saved?()
saved = nil
print("Все владельцы убраны")
```

Вывод: «Осталось замыкание», `31`, «Освобождена сессия 31», «Все владельцы убраны». Объект не хранит `saved`, поэтому обратной связи и цикла здесь нет.

## Проверь себя

Ответь без запуска кода и отдельно запиши владельцев после каждой строки.

- Почему после `first = nil` сессия не освобождается?
- Почему вызов сохранённого замыкания не удаляет его захват?
- Какая строка убирает последнего владельца в итоговом примере?

## Ответы к «Проверь себя»

- `second = first` не копирует объект, а добавляет второго сильного владельца того же экземпляра. `first = nil` убирает только одну ссылку, а ARC освобождает объект, лишь когда сильных владельцев не осталось. Поэтому `deinit` срабатывает после `second = nil`: вывод «Первую ссылку убрали», `31`, и только потом «Освобождена сессия 31».
- Список `[session = first!]` при создании замыкания сохранил сильную ссылку на сессию внутри самого замыкания. Вызов `saved?()` лишь выполняет тело и печатает `31`, а сохранённое действие со своим захватом продолжает жить в `saved`. Владение исчезает, только когда уходит само замыкание: `saved = nil`.
- Последнего владельца убирает `saved = nil`: к этому моменту `first` и `second` уже `nil`, а сессию держит только захват замыкания. Поэтому вывод идёт «Осталось замыкание», `31`, «Освобождена сессия 31», «Все владельцы убраны». Цикла тут нет — сессия не хранит `saved`, так что одна очистка замыкания всё решает.

# ГЛУБЖЕ

## Время жизни и оптимизация

Не превращай наш пошаговый пример в правило «deinit всегда на закрывающей скобке». Компилятор может оптимизировать удержание и освобождение объектов; точный момент после последнего нужного использования не стоит угадывать по форме локального блока. Явные корни и наблюдаемые действия делают эти примеры проверяемыми, но не задают общее правило для любого локального `let`.

Если объект должен оставаться живым на время определённой операции, существует `withExtendedLifetime`. Это гарантия удержания до завершения операции, а не команда немедленно освободить объект после неё. Для важной бизнес-операции используй явный `stop()` или `close()`, а не надежду на момент `deinit`.

## Почему ARC не разбирает цикл

Вот отдельный опасный случай: объект хранит замыкание, а оно сильно захватывает этот объект. У каждого есть владелец внутри цепочки.

```swift
final class RecordingSession {
    let id: Int
    var onFinish: (() -> Void)?
    init(id: Int) { self.id = id }
    deinit { print("Освобождена сессия \(id)") }
    func installCallback() {
        onFinish = { print(self.id) }
    }
}
```

Сам по себе класс ещё не создаёт цикл: он появится после `installCallback()`. После удаления внешней ссылки замыкание и объект продолжат держать друг друга. ARC не является сборщиком циклического мусора. Разорвать связь можно явным очищением `onFinish`, пока объект ещё доступен; выбор `weak` или `unowned` отдельно зависит от нужного времени жизни.

## Слабый наблюдатель для проверки

`weak` позволяет наблюдать объект, не становясь его сильным владельцем. Слабая ссылка на экземпляр класса объявляется переменной Optional; после освобождения объекта она становится `nil`.

```swift
var session: RecordingSession? = RecordingSession(id: 33)
weak var observer = session
print(observer != nil)
session = nil
print(observer == nil)
```

В этой маленькой проверке выйдет `true`, отметка из `deinit`, `true`. Не называй наблюдателя «вторым сильным владельцем»: иначе весь расчёт будет неверным.

## Завершение работы не равно освобождению

На собесе тебя спросят, почему не стоит переносить важное сохранение данных в `deinit`. Модель может ещё жить у другого владельца, её может держать цикл, а завершение процесса вообще не обещает аккуратный вызов всех деструкторов. Пользователь нажал «Завершить» — вызови отдельное действие и обработай его результат.

`deinit` годится для финальной уборки ресурсов экземпляра, когда он действительно освобождается. Для асинхронной операции нужен явный жизненный цикл: обычный `deinit` из этого урока не является `async`-методом и в нём нельзя просто поставить `await` и ждать сохранения.
