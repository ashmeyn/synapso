## Что нужно сохранить, а что можно забыть

Давай отделим оригинал от ускорения: источник может снова отдать обложку альбома 41, а кэш держит её удобную копию в памяти. Если копия исчезла, приложение загружает данные снова.

NSCache — системный кэш объектов. Это не постоянное хранилище и не обещание, что обложка останется до конца запуска. Для этой миссии источник локальный; сетевая реализация может позже использовать клиента из urls.

## Пишем в лоб: один id на разные картинки

Попробуй предсказать столкновение двух запросов. Размер влияет на результат, но ключ его забыл.

```swift
import Foundation
func artworkKey(id: Int, version: Int, size: String) -> String {
    "album:\(id)"
}
let small = artworkKey(id: 41, version: 1, size: "small")
let large = artworkKey(id: 41, version: 1, size: "large")
print(small == large)
```

Вывод true: маленькая и большая обложки получили одинаковый адрес в кэше. Даже без запуска NSCache видно, что записи не различимы. Исправим сам ключ, а не будем угадывать порядок вытеснения.

## Построим ключ результата

Назови всё, что определяет конкретную картинку. В нашем контракте это id альбома, версия содержимого и размер.

```swift
func artworkKey(id: Int, version: Int, size: String) -> String {
    "album:\(id):v\(version):\(size)"
}
```

41/v1/small и 41/v1/large больше не совпадают; новая версия тоже имеет новый ключ. Ключ — подпись на коробке с копией: если на разных коробках одна подпись, достанешь не ту. Здесь значения контролирует приложение; для произвольных строк понадобится однозначная схема ключа.

## Источник остаётся главным

Не привязывай алгоритм к URLSession.shared. Источник должен уметь вернуть нужные байты или бросить ошибку; это знакомый протокол.

```swift
import Foundation
protocol ArtworkSource {
    func fetchBytes(for key: String) throws -> Data
}
```

В локальных проверках три байта [1, 2, 3] — тестовые данные, не изображение. Они нужны для проверки вызовов и восстановления после очистки, а не для показа настоящей обложки.

## Проверим память до загрузки

В ArtworkLoader уже есть memory: `NSCache<NSString, NSData>` и source: any ArtworkSource. Сначала ищем объект; при отсутствии обращаемся к источнику.

```swift
func loadBytes(for key: String) throws -> Data {
    let cacheKey = key as NSString
    if let bytes = memory.object(forKey: cacheKey) {
        return bytes as Data
    }
    let bytes = try source.fetchBytes(for: key)
    memory.setObject(bytes as NSData, forKey: cacheKey, cost: bytes.count)
    return bytes
}
```

object возвращает Optional: hit означает найденную копию, miss — отсутствие. NSString и NSData нужны как объектные типы NSCache; мост `as` переводит Swift-строку и Data. Если источник бросил ошибку, до setObject не дошли и ложный успех не закэширован.

## Очистка — нормальное событие

Теперь проверь восстановление, а не только удачный hit. Явное удаление конкретного ключа позволяет обновить изменённую обложку.

```swift
func invalidate(key: String) {
    memory.removeObject(forKey: key as NSString)
}
func clearMemory() { memory.removeAllObjects() }
```

После удаления следующий запрос идёт к источнику. NSCache может вытеснять объекты и сам: нельзя требовать точного порядка или считать кэш обязательным условием работы. countLimit и totalCostLimit — ориентиры, не строгие гарантии.

## Байты ещё не изображение

Остановись перед UI: размер Data не доказывает, что файл можно показать. На iOS проверь декодирование отдельно.

```swift
import UIKit
func decodedCover(from bytes: Data) -> UIImage? {
    UIImage(data: bytes)
}
```

Наши [1, 2, 3] дадут nil. Для реального показа нужен допустимый формат изображения и запасной вид при отказе. Основа кэширует исходные байты; хранение декодированного UIImage требует другой оценки стоимости памяти.

## Собираем восстановимый кэш

Окей, вот самостоятельный клиент. Получение выполняется последовательно; одновременные запросы не объединяются этой реализацией.

```swift
import Foundation
protocol ArtworkSource {
    func fetchBytes(for key: String) throws -> Data
}
final class ArtworkLoader {
    private let memory = NSCache<NSString, NSData>()
    private let source: any ArtworkSource
    init(source: any ArtworkSource) { self.source = source }
    func loadBytes(for key: String) throws -> Data {
        let cacheKey = key as NSString
        if let bytes = memory.object(forKey: cacheKey) {
            return bytes as Data
        }
        let bytes = try source.fetchBytes(for: key)
        memory.setObject(bytes as NSData, forKey: cacheKey, cost: bytes.count)
        return bytes
    }
    func invalidate(key: String) {
        memory.removeObject(forKey: key as NSString)
    }
    func clearMemory() { memory.removeAllObjects() }
}
```

- Hit возвращает найденную копию; miss идёт к источнику.
- Включай в ключ всё, что меняет результат.
- Ошибка источника остаётся ошибкой, очистка остаётся поводом загрузить снова.

## Проверь себя

Представь, что память очистилась между двумя открытиями библиотеки.

- Почему это не должно удалить оригинал обложки?
- Какие две картинки смешает ключ только из id?
- Что вернёт клиент, если кэш пуст, а источник бросит ошибку?

## Ответы к «Проверь себя»

- Кэш держит только восстанавливаемую копию в памяти, а оригинал остаётся у источника (`ArtworkSource`). `NSCache` — не постоянное хранилище: он может вытеснять объекты сам, а `clearMemory()` и `invalidate(key:)` убирают лишь копии. Поэтому очистка — нормальное событие: следующий `loadBytes` получит miss и снова возьмёт байты из источника.
- Ключ `"album:\(id)"` смешает маленькую и большую обложку альбома 41: у них одинаковый адрес в кэше, и запрос large вернёт сохранённую small. По той же причине смешаются версии v1 и v2. Поэтому в ключ кладёшь всё, что меняет результат: `"album:\(id):v\(version):\(size)"`.
- При пустом кэше `memory.object(forKey:)` даёт `nil`, и `try source.fetchBytes(for: key)` бросает ошибку, которая уходит из `loadBytes` к вызывающему коду: данных клиент не вернёт. До `setObject` выполнение не дойдёт, поэтому ложный успех не закэширован. Следующий вызов снова пойдёт к источнику.

# ГЛУБЖЕ

## Стоимость байтов и стоимость пикселей

Сначала реши, что именно лежит в NSCache. Для NSData стоимость bytes.count — размер исходных байтов. Для декодированного CGImage можно оценить буфер через bytesPerRow × height; это не общий размер всей памяти UIImage.

Маленький сжатый файл после декодирования может занимать гораздо больше. Не называй размер JPEG расходом пиксельного буфера. Эта отдельная оценка проверяется письменно в банке.

## Одновременные miss

Два вызова могут оба увидеть отсутствие и оба запустить загрузку. Потокобезопасность операций NSCache не делает последовательность «проверил → загрузил → сохранил» одной операцией.

Для объединения одинаковых запросов нужен отдельный учёт выполняющихся работ, например изолированный владелец и таблица Task по ключу. Данная синхронная версия такого обещания не даёт.

## Диск и актуальность

Сравни скорость и срок жизни: NSCache даёт копию в памяти, файловый кэш может пережить запуск, но всё равно нуждается в проверке версии и правилах очистки.

В HTTP-кэше учитываются серверные правила, ETag и Cache-Control. Ключ с v2 удобен только если ты действительно знаешь, что сервер выдал вторую версию. NSCache сам не решает, устарела ли обложка.

## Пределы и проверка hit

Не пиши тест «после третьей записи обязательно исчезнет первая». У NSCache не обещан ни строгий лимит, ни LRU-порядок. Для проверки клиента отдели контракт хранилища от политики системы.

Локальная проверка hit может использовать управляемое подставное хранилище; сама работа NSCache проверяется отдельно без требований к вытеснению. В наших прогнозах с реальным NSCache сначала явно очищаем ключ, поэтому miss не зависит от давления памяти.
