## Начинаем в учебном репозитории

Здесь Git хранит версии текстовых настроек, а не исполняет Swift. Создай новый каталог в удобном месте; команды ниже выполняй только в нём. Имя коммита A — его сообщение. В схемах и ожидаемом log буквы A, B, C заменяют настоящие хэши; это обозначения, а не аргументы команд. Для выбора коммита используем реальные refs: main, HEAD и HEAD~1.

```bash
mkdir synapso-git-lab
cd synapso-git-lab
git init -b main
git config user.name Synapso
git config user.email learner@example.invalid
printf 'cyan\n' > theme.txt
git add theme.txt
git commit -m A
```

Коммит — снимок и ссылки на родителей. Ветка — указатель на коммит, HEAD обычно указывает на текущую ветку. Представь ветку как закладку: её перенос не перепечатывает уже существующие страницы.

## Попытка в лоб: add не следит за файлом

Сначала предскажи, что попадёт в B. Рабочее дерево — файлы на диске, индекс — подготовленный снимок для следующего commit. add копирует текущее содержимое в индекс; последующее изменение файла не обновляет индекс само. Поэтому B сохранит pink, а red останется незакоммиченным.

```bash
# В theme.txt коммита A записано cyan. Рабочее дерево чистое.
printf 'pink\n' > theme.txt
git add theme.txt
printf 'red\n' > theme.txt
git commit -m B
git log --oneline -2
git status --short
```

Нормализованный log: B B, затем A A. status --short покажет ` M theme.txt`: первый столбец относится к индексу, второй — к рабочему дереву. В чистом состоянии короткий status ничего не печатает. Перед переходом к следующему примеру выбери: сохранить red новым коммитом либо осознанно убрать его через git restore theme.txt.

## Две ветки — два указателя

Следующий пример начинается заново от чистого A. Создай theme, добавь отдельный preview.txt и коммит B. На main добавь help.txt и коммит C. Получается A→B на theme и A→C на main; B и C не меняют один файл. switch переключает ветку и соответствующее дерево, а switch -c создаёт новую.

```bash
git switch -c theme
printf 'preview\n' > preview.txt
git add preview.txt
git commit -m B
git switch main
printf 'help\n' > help.txt
git add help.txt
git commit -m C
```

Не выполняй независимые примеры подряд в одном состоянии без возврата к их условиям. log --oneline --all показывает доступные коммиты всех веток; --graph помогает увидеть родителей, а не только даты.

## merge и rebase решают разное

Для развилки A→B и A→C merge сохраняет оба существующих коммита и создаёт M с двумя родителями. Выполни на theme git merge --no-ff main: у M родители B и C. rebase main на theme переносит изменение B поверх C новым коммитом B′, получаем A→C→B′; сам B не редактируется. Это альтернативы на одной исходной развилке, не обязательная цепочка команд.

```bash
git switch theme
git rebase main
git log --oneline --all
git status --short
```

После rebase main остаётся на C, theme указывает на B′; оба файла preview.txt и help.txt присутствуют. Сообщение B остаётся B, но идентичность и родитель новые. Если ветку уже используют коллеги, не переписывай её без согласованной процедуры; обычный push нового rebase может быть отвергнут как non-fast-forward.

## Конфликт: Git не выбирает смысл

Теперь другой вход: от A обе ветки меняют одну строку theme.txt. main требует accent=blue и contrast=high, theme — accent=pink и contrast=normal. После git switch theme и git merge main появляется конфликт. Требование выпуска: сохранить pink и high. Не выбирай весь ours/theirs автоматически: каждая сторона содержит нужную часть.

```text
<<<<<<< HEAD
accent=pink
contrast=normal
=======
accent=blue
contrast=high
>>>>>>> main
```

Оставь две строки accent=pink и contrast=high без маркеров. Затем git add theme.txt отмечает файл разрешённым; git commit завершает merge. При конфликте rebase после add нужен git rebase --continue, а для отказа от начатого rebase — git rebase --abort. Во время rebase смыслы ours/theirs непривычны: сверяй содержание и требования, не название стороны.

## Черновик — в stash

Когда нужно срочно исправить main, незавершённое оформление можно временно спрятать. stash push сохраняет изменения отслеживаемых файлов; -u добавляет неотслеживаемые, но не ignored. apply возвращает изменения, оставляя запись stash; после проверки её можно drop. pop совмещает применение и удаление при успехе, при конфликте запись сохраняется.

```bash
git stash push -u -m theme-draft
git switch main
# Выполни и закоммить срочную правку main.
git switch theme
git stash apply
git status --short
# После проверки восстановленного черновика:
git stash drop
```

Не называй stash резервной копией всего проекта: ignored-файлы без -a и уже существующие коммиты — другой вопрос. Если apply конфликтует, разреши файлы и не удаляй запись, пока не убедился в результате.

## Отмена: что именно меняешь

Сначала назови слой. restore file по умолчанию копирует файл из индекса в рабочее дерево; restore --staged file возвращает индекс к HEAD, сохраняя рабочий файл. reset --soft HEAD~1 переносит текущую ветку на родителя и оставляет индекс и файлы; reset --hard HEAD~1 ещё приводит индекс и рабочее дерево к этому коммиту, уничтожая соответствующие правки. hard может удалить мешающие восстановлению неотслеживаемые файлы — это не команда для черновика.

```bash
# Только локальный последний коммит, изменения нужно оставить:
git reset --soft HEAD~1
git status --short
# Общая опубликованная ветка, последний коммит ошибочен:
git revert --no-edit HEAD
```

Эти строки — два независимых выбора, не выполняй их подряд как рецепт. revert создаёт новый обратный коммит (--no-edit принимает стандартное сообщение без редактора); старые остаются доступными коллегам. Для merge-коммита требуется выбрать mainline через -m; это не тот простой случай, который тренируем здесь.

## Итог: решаем по состоянию

Вернись к конфликту из основы: merge уже остановлен, theme.txt unmerged, других изменений нет. Полная последовательность ниже оставляет обе нужные настройки и завершает merge. Перед commit прочитай diff: Git подтвердит снимок, но не проверит продуктовую правильность цвета.

```bash
printf 'accent=pink\ncontrast=high\n' > theme.txt
git add theme.txt
git status --short
git diff --cached
git commit -m M
```

Для личной неопубликованной истории допустим rebase; для общей сначала выбирай merge или обратный коммит. Черновик сохрани до переключения. «status чистый» означает отсутствие видимых изменений, а не правильность решения.

## Проверь себя

Нарисуй родителей словами, затем выбери команду.

- Почему B сохранил pink, хотя файл уже red?
- Что сохраняет merge и что меняет rebase на развилке A→B, A→C?
- Как отменить опубликованную ошибку, а как снять только подготовку файла к коммиту?

## Ответы к «Проверь себя»

- `git add` копирует в индекс содержимое файла в момент вызова, а индекс — это подготовленный снимок для следующего commit. Последующий `printf 'red\n' > theme.txt` меняет только рабочее дерево, индекс сам не обновляется, поэтому B фиксирует pink. После коммита `git status --short` покажет ` M theme.txt`: изменение во втором столбце, то есть в рабочем дереве, и red остаётся незакоммиченным.
- `git merge --no-ff main` на theme сохраняет B и C как есть и добавляет коммит M с двумя родителями — B и C. `git rebase main` переносит изменение B поверх C новым коммитом B′: получается A→C→B′, сообщение то же, но идентичность и родитель новые, а сам B не редактируется; ветка-закладка просто переезжает. Поэтому rebase допустим для личной неопубликованной истории, а общую ветку без договорённости не переписывают: обычный push может быть отвергнут как non-fast-forward.
- Опубликованную ошибку отменяешь `git revert --no-edit HEAD`: он добавляет новый обратный коммит, и история коллег остаётся целой, в отличие от `reset`, который переносит саму ветку. Подготовку снимаешь `git restore --staged theme.txt`: индекс возвращается к HEAD, а рабочий файл с правками остаётся. `reset --hard` для этого не годится — он приводит индекс и рабочее дерево к коммиту и уничтожает правки.

# ГЛУБЖЕ

## Вернуть и staging тоже

Если до stash один файл был staged, а другой только изменён, обычный apply не обещает восстановить подготовку точно. Для попытки восстановить индекс используй git stash apply --index; при конфликте это может не удаться. Сначала посмотри status и diff --cached, потом удаляй запись. Так ты восстанавливаешь не только файлы, но и свой план следующего коммита.

## Ошибка после hard и reflog

Если потерял указатель на локальный коммит, проверь git reflog и найди прежнюю позицию HEAD, затем создай спасательную ветку от найденного ref. Не обещай вернуть любые файлы: reflog не хранит каждую незакоммиченную правку и записи со временем истекают. Перед рискованной локальной операцией отдельная ветка сохраняет ссылку на коммит.

## Публикация — контракт команды

Не лечи отказ push после rebase общим правилом «всегда force». Даже force-with-lease только проверяет ожидаемое состояние удалённой ссылки, не отменяет зависимость коллег от старых коммитов. Согласуй переписывание личной опубликованной ветки; в общей main обычно добавь новый коммит. Здесь реальные remotes не нужны, опасную публикацию не выполняем.

## Проверить конфликт до завершения

После ручной правки проверь git diff --check на лишние пробелы и некоторые следы конфликта, затем прочитай git diff --cached. Это дополнение к тестам приложения: успешный merge или rebase не означает, что программа работает. Если решения ещё нет, git merge --abort отменяет текущий merge; лучше начинать такие операции с чистым деревом, чтобы не смешивать их с черновиком.
