## Читаем вместе, меняем отдельно

Окей, данные маленькие: оригинал содержит «Кроссовки», в черновик добавляем «Полотенце». Оригинал должен остаться из одной вещи. Нам нужно поведение значения, хотя внутри ради совместного чтения хранится class.

Copy-on-Write, или CoW, означает отделение общего хранилища перед записью. Это способ реализовать нужное поведение, а не ещё один вид Swift-типа.

## Пишем в лоб: struct не спасла ссылку

Начнём со знакомого подвоха valref. ListStorage — класс с массивом items, PackingList хранит ссылку на него. Без проверки append изменяет общий объект.

```swift
struct PackingList {
    private var storage: ListStorage
    init(_ items: [String]) { storage = ListStorage(items) }
    var items: [String] { storage.items }
    mutating func append(_ item: String) {
        storage.items.append(item)
    }
}
```

После var draft = original и draft.append("Полотенце") оба списка видят две вещи. Копия самого массива внутри класса не появилась: обе обёртки продолжают обращаться к одному ListStorage.

## Спрячем хранилище

Давай оставим владельцу списка только значение items, а не изменяемую ссылку на ListStorage. Такой класс нужен реализации, но не интерфейсу черновика.

```swift
private final class ListStorage {
    var items: [String]
    init(_ items: [String]) { self.items = items }
}
```

private ограничивает доступ. Вычисляемое свойство items в PackingList только читает и возвращает [String], то есть значение; внешняя сторона не получает сам класс и не обходит правило отделения. Вещи здесь строки, а не классы с общей изменяемой жизнью.

## Сначала проверка уникальности

В mutating-методе уже доступна storage. Посмотри на проверку перед записью, не после неё.

```swift
if !isKnownUniquelyReferenced(&storage) {
    storage = ListStorage(storage.items)
}
storage.items.append(item)
```

Функция проверяет, известно ли, что объект удерживается единственной сильной ссылкой. true позволяет менять это хранилище; false означает, что уникальность не подтверждена, поэтому отделяемся консервативно. & передаёт переменную ссылки в проверку. Она не является замком и не делает одновременную работу безопасной.

## Обёртка отвечает за каждый путь

Теперь собери правило в типе. mutating разрешает методу структуры заменить собственную storage.

```swift
struct PackingList {
    private var storage: ListStorage
    init(_ items: [String]) { storage = ListStorage(items) }
    var items: [String] { storage.items }
    mutating func append(_ item: String) {
        if !isKnownUniquelyReferenced(&storage) {
            storage = ListStorage(storage.items)
        }
        storage.items.append(item)
    }
}
```

Новое ListStorage получает значение старого массива. Сама Array тоже может использовать CoW внутри; мы не обещаем глубокое немедленное копирование всех байтов. Важно, что будущая запись идёт через другой объект-хранилище.

## Пройдём одну добавленную вещь

Пройди original → draft: обе обёртки сначала могут читать общий ListStorage. При записи draft проверяет ссылку, создаёт своё хранилище, затем добавляет «Полотенце». original остаётся с «Кроссовки». Это как общий исходник документа, от которого берёшь отдельную редактируемую версию перед первой правкой.

Один только Array.append внутри общего класса уже не спасёт оригинал. CoW массива защищает разные значения Array, а не разные ссылки на один класс с единственным Array-свойством.

## Удаление тоже является записью

Назови все методы, которые меняют данные. removeLast должен сначала вернуть nil на пустом списке, а для непустого — проверить уникальность и только затем вызвать storage.items.popLast(). popLast удаляет последний элемент и возвращает Optional.

Не считай реализацию завершённой после одного безопасного append. Забытая проверка в удалении или замене снова объединит изменения копий. Это проверяется в ступени 6; чтение items само по себе не требует отделять класс.

## Собираем CoW-список

Вот самостоятельный пример. Сначала предскажи два массива по контракту, а не число выделений памяти.

```swift
private final class ListStorage {
    var items: [String]
    init(_ items: [String]) { self.items = items }
}
struct PackingList {
    private var storage: ListStorage
    init(_ items: [String]) { storage = ListStorage(items) }
    var items: [String] { storage.items }
    mutating func append(_ item: String) {
        if !isKnownUniquelyReferenced(&storage) {
            storage = ListStorage(storage.items)
        }
        storage.items.append(item)
    }
}
let original = PackingList(["Кроссовки"])
var draft = original
draft.append("Полотенце")
print(original.items)
print(draft.items)
```

- Обёртка скрывает изменяемый класс-хранилище.
- При неподтверждённой уникальности отделяется до записи.
- Каждый путь изменения соблюдает то же правило.

## Проверь себя

Закрой проверку и восстанови её место в алгоритме.

- Почему прежняя struct меняла оригинальный список?
- Почему проверка после append уже запоздала?
- Что будет, если append проверяет уникальность, а removeLast — нет?

## Ответы к «Проверь себя»

- `PackingList` — структура, но внутри хранит ссылку на класс `ListStorage`, поэтому `var draft = original` копирует ссылку, и обе обёртки смотрят на одно хранилище. `append` без проверки пишет прямо в общий `storage.items`, так что оба списка видят две вещи. CoW самого `Array` тут не помогает: он разделяет разные значения массива, а массив здесь один — внутри одного объекта.
- Проверка нужна, чтобы отделиться до записи: если уникальность не подтверждена, сначала `storage = ListStorage(storage.items)`, и только потом `storage.items.append(item)`. Если сначала сделать `append`, вещь уже попадёт в общее хранилище, и оригинал её увидит. Проверка после этого может лишь создать копию уже испорченных данных, а вернуть оригинал не сможет.
- Удаление — тоже запись, поэтому `removeLast` без проверки снова сделает `popLast()` в общем `ListStorage`, и оригинал потеряет вещь вслед за копией. Value-семантика держится, только если барьер `isKnownUniquelyReferenced(&storage)` стоит в каждом `mutating`-методе. Правильный порядок: `guard !storage.items.isEmpty else { return nil }`, затем проверка уникальности, затем `storage.items.popLast()`.

# ГЛУБЖЕ

## Цена копирования

Не переноси O(1) на любое присваивание и любую запись без условий. У стандартной Array разделение буфера — распространённая оптимизация, а изменение разделяемого большого массива может потребовать работы пропорционально числу элементов.

Наша обёртка явно может создать новый ListStorage; это ещё не измерение числа копий внутренних буферов или затрат Swift String. Если цена важна, измеряй конкретную операцию в конкретной сборке.

## Ссылки во время проверки

Перед isKnownUniquelyReferenced не создавай лишнюю сильную ссылку на storage «для удобства». Такая локальная копия может помешать подтвердить уникальность и привести к лишнему отделению.

Проверка учитывает сильные ссылки, а weak/unowned сами по себе не делают объект неуникальным. false не является универсальным измерителем точного числа владельцев. Общее изменение из нескольких потоков требует отдельной синхронизации.

## Массив элементов-классов и срез

Посмотри на тип элемента. Если items стал [EntryClass], отделение контейнера не создаёт независимые EntryClass: ссылки на элементы остаются общими. Нужно отдельно решить, заменяем элемент или копируем его состояние.

ArraySlice сохраняет индексы исходного массива и может удерживать его буфер. Для самостоятельного небольшого окна можно получить Array(slice); не обещай по этому вызову точное физическое размещение или объём освобождённой памяти.

## Пакет правок

Если интерфейс даёт edit с параметром `(inout [String]) -> Void`, сначала отдели storage, потом передай storage.items этому немедленному замыканию. Оно не должно сохранять изменяемый доступ после возврата.

Две правки в одном вызове должны работать на отделённом хранилище. Это отдельный интерфейс редактирования; убедись, что он не открывает наружу ListStorage и не пропускает ту же проверку уникальности.
