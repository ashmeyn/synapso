## Новая цена не приходит один раз

Давай зафиксируем данные: лот 9, версия 1, цена 100; затем версия 3, цена 130. Позже может прийти старая версия 2 с ценой 110. На экране должна остаться 130.

Каждое сообщение нашего контракта несёт полную текущую цену, а не прибавку к ней. Поэтому версия 3 заменяет предыдущую даже при пропущенной версии 2. Версия сравнима только внутри одного лота, а суммы здесь целые учебные единицы.

## Пишем в лоб: услышали только начало

Посмотри на тело async-функции: source и state уже заданы. Оно получает лишь одно значение.

```swift
if let quote = try await source.receive() {
    state.apply(quote)
}
```

При последовательности 1/100 → 3/130 результат останется 100. Один receive не означает подписку навсегда. У настоящего URLSessionWebSocketTask receive() тоже возвращает одно сообщение; следующий нужно запросить снова.

## Выберем способ доставки

Назови направление: WebSocket подходит для постоянного обмена в обе стороны, например ставки от клиента и цены от сервера. SSE передаёт поток от сервера к клиенту по HTTP; команды при этом можно отправлять отдельными запросами.

Polling периодически запрашивает свежий снимок: проще, но есть задержка и лишние обращения. Push через APNs уместен как уведомление или сигнал обновиться в фоне, а не гарантированный журнал всех цен. В нашей миссии это выбор архитектуры, без открытия соединений. Канал похож на способ связи: разговор, трансляция, повторные звонки или сигнал «проверь новости».

## Запишем выбор явно

Для письменной проверки зададим учебную политику: торги в обе стороны → WebSocket, только цены → SSE, редкие изменения → polling, фоновая подсказка → push. Это условия задачи, не единственные возможные решения любого продукта.

```swift
enum Need { case liveBids, priceOnly, occasional, backgroundHint }
enum Transport { case webSocket, sse, polling, push }
func transport(for need: Need) -> Transport {
    switch need {
    case .liveBids: return .webSocket
    case .priceOnly: return .sse
    case .occasional: return .polling
    case .backgroundHint: return .push
    }
}
```

Функция только выбирает значение enum. Она не создаёт сервер, соединение или APNs-регистрацию. Каждая ветка проверяется в ступени 6.

## Поток отдаёт полные состояния

Окей, отделим сообщения от транспорта. Quote содержит три числа, а наш протокол возвращает одну запись или nil, означающий конец локального источника.

```swift
struct Quote {
    let lotID, revision, amount: Int
}
protocol QuoteSource {
    func receive() async throws -> Quote?
}
```

receive — метод нашего адаптера, не новый API URLSession. Настоящий WebSocket при закрытии может бросить ошибку; адаптер должен явно определить, что считает завершением. Локальная реализация просто читает заданный массив и не делает сеть.

## Идентичность раньше версии

Не сравнивай версии двух разных лотов. Сначала проверь id, затем потребуй версию новее уже применённой.

```swift
struct LotState {
    let lotID: Int
    var revision = 0
    var amount = 0
    mutating func apply(_ quote: Quote) {
        guard quote.lotID == lotID, quote.revision > revision else { return }
        revision = quote.revision
        amount = quote.amount
    }
}
```

Пройди rows из начала: 9/1/100 применяется; 8/5/999 игнорируется; 9/3/130 применяется; 9/2/110 игнорируется. amount остаётся 130, revision — 3. Повтор версии 3 тоже не меняет состояние; конфликт двух разных цен одной версии должен решать серверный контракт.

## Получаем до завершения

Теперь замени if на while: после каждого значения снова просим следующее. QuoteSource и LotState уже объявлены.

```swift
func follow(
    source: any QuoteSource, state: inout LotState
) async throws {
    while let quote = try await source.receive() {
        try Task.checkCancellation()
        state.apply(quote)
    }
}
```

try await ждёт одно значение без блокирующего ожидания потока; while повторяет запрос. inout передаёт изменяемое состояние вызывающему коду, а mutating разрешает apply менять struct. Отмена проверяется перед применением полученного значения. Ошибка источника выходит через throws; скрытый бесконечный retry здесь не добавлен.

## Собираем получателя

Проверь весь маршрут на локальном массиве: получение → проверка отмены → фильтр id → фильтр версии → новая цена.

```swift
import Foundation
struct Quote {
    let lotID, revision, amount: Int
}
protocol QuoteSource {
    func receive() async throws -> Quote?
}
struct LotState {
    let lotID: Int
    var revision = 0
    var amount = 0
    mutating func apply(_ quote: Quote) {
        guard quote.lotID == lotID, quote.revision > revision else { return }
        revision = quote.revision
        amount = quote.amount
    }
}
func follow(
    source: any QuoteSource, state: inout LotState
) async throws {
    while let quote = try await source.receive() {
        try Task.checkCancellation()
        state.apply(quote)
    }
}
```

- Один receive даёт одно значение, а не всю подписку.
- id определяет сущность, revision — свежесть её состояния.
- Полные снимки и изменения-дельты требуют разных правил восстановления.

# ГЛУБЖЕ

## WebSocket: кадр ещё не модель

Не применяй к экрану сырое сообщение. URLSessionWebSocketTask.Message бывает .string и .data; сначала получи байты, затем декодируй модель по контракту.

```swift
import Foundation
func nextFrame(
    socket: URLSessionWebSocketTask
) async throws -> URLSessionWebSocketTask.Message {
    try await socket.receive()
}
```

Функция не создаёт и не запускает сокет. У настоящей сессии отдельно нужны создание задачи, resume, обработка ошибок и закрытие. В этой партии только компилируем API, не подключаемся к серверу.

## SSE и события по строкам

Сначала прочитай формат: SSE использует text/event-stream, поля data, event, id и пустую строку как границу события. Одна строка полученных байтов не обязана быть целым событием; несколько data-строк могут образовать одно сообщение.

В браузере EventSource реализует этот протокол. Для нативного клиента нужен свой корректный разбор или подходящая библиотека; не выдумывай URLSession.eventSource. Last-Event-ID помогает возобновлению, только если сервер поддерживает нужную историю.

## Переподключение и снимок

После разрыва не обещай, что каждое событие сохранено. Для нашего контракта получи полный актуальный снимок лота с revision, затем применяй доступные полные обновления, сохраняя наибольшую версию.

Если вместо полной цены сообщения содержат дельту «прибавь 10», пропуск становится ошибкой: нужны последовательные номера, восстановление истории или новый снимок. Уведомление push — повод получить актуальные данные, а не доказательство отсутствия пропущенных событий.

## Ритм polling и жизнь экрана

Не отправляй запрос на каждом кадре UI. Задай разумный интервал, не допускай наложения запросов и останови работу, когда она не нужна; после отказов учитывай серверные ограничения и backoff.

Наши локальные шаги polling не ждут часы и не запускают Timer: вызовы имитируют уже наступившие тики. Фоновые push не гарантированы; видимость экрана, батарея и ограничения системы — часть выбора транспорта. Обновление UI остаётся в нужном контексте MainActor.
