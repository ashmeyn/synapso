## Сначала договоримся об изменении

Давай разделим оригинал «Утро» и черновик «Вечер». Пока пользователь редактирует, исходный план должен оставаться прежним. id 12 обозначает один план в разных снимках состояния; разные снимки могут иметь один id.

Выбор struct или class влияет на поведение присваивания. Не выбирай тип по предполагаемому адресу памяти: сначала назови, должно ли изменение быть общим.

## Пишем в лоб: две ссылки, один черновик

Прогнозируй результат до запуска: экземпляр класса здесь создали только один раз.

```swift
final class RouteDraft {
    let id: Int
    var title: String
    init(id: Int, title: String) { self.id = id; self.title = title }
}
let original = RouteDraft(id: 12, title: "Утро")
let draft = original
draft.title = "Вечер"
print(original.title)
print(original === draft)
```

Вывод «Вечер», true. draft и original ссылаются на один объект. Оператор === проверяет, один ли это экземпляр класса; он не сравнивает поля и не заменяет id предметной области.

## Значение даёт самостоятельное изменение

Теперь выразим нужное правило через struct. Копия значения не должна менять исходное значение при редактировании собственного String-поля.

```swift
struct RouteDraft {
    let id: Int
    var title: String
}
let original = RouteDraft(id: 12, title: "Утро")
var draft = original
draft.title = "Вечер"
print(original.title)
print(draft.title)
```

Вывод «Утро», «Вечер». Это семантика значения, а не обещание немедленно скопировать каждый байт. Два документа можно редактировать отдельно, даже если реализация временно разделяет внутренние данные.

## Функция возвращает новый снимок

RouteDraft из предыдущего раздела уже объявлен. Давай передадим план в функцию без скрытой записи в оригинал.

```swift
func renamed(_ route: RouteDraft, to title: String) -> RouteDraft {
    var draft = route
    draft.title = title
    return draft
}
```

Параметр route — доступное для чтения значение; локальный var разрешает правку. Результат нужно явно принять вызывающему коду. Если функция должна изменить переданное значение, используй отдельный понятный контракт inout и & из func.

## Что let запрещает у класса

Вернёмся к классу из ошибочной попытки. let фиксирует ссылку в переменной, но не делает все свойства объекта неизменяемыми.

```swift
final class RouteDraft {
    let id: Int
    var title: String
    init(id: Int, title: String) { self.id = id; self.title = title }
}
let route = RouteDraft(id: 12, title: "Утро")
route.title = "Вечер"
print(route.title)
```

Печатается «Вечер». Переприсвоить route другой экземпляр нельзя, var title изменить можно, а let id менять нельзя. У структуры let запрещает прямое изменение её собственных хранимых свойств; это отдельное правило, не универсальная заморозка всех достижимых объектов.

## Вложенная ссылка остаётся общей

Остановись на границе: если struct хранит Participants как class, присваивание структуры копирует ссылку на Participants. Названия черновиков независимы, но счётчик участников общий.

```swift
final class Participants { var count = 1 }
struct RouteDraft {
    let id: Int
    var title: String
    let participants: Participants
}
```

После var draft = original и draft.participants.count = 2 оригинал тоже видит 2. let participants запрещает заменить ссылку, а не изменить её объект. Для независимого счётчика сделай Participants структурой и его поле в черновике — var; это письменно проверим в ступени 6.

## Выбери контракт до исправления

Пройди три действия: draft.title = «Вечер» меняет только копию структуры; правка Participants-класса меняет общий объект; вызов функции с inout и &original явно разрешает изменение исходного значения. Назови, какой путь нужен экрану.

Не «лечи» всю модель глубоким копированием наугад. Иногда участники действительно должны быть общими, а отдельным должен быть только локальный текст. Независимость означает заранее заданные правила изменения.

## Собираем независимый черновик

Окей, основной контракт снова простой: собственные поля значения и явный возвращённый результат.

```swift
struct RouteDraft {
    let id: Int
    var title: String
}
func renamed(_ route: RouteDraft, to title: String) -> RouteDraft {
    var draft = route
    draft.title = title
    return draft
}
let original = RouteDraft(id: 12, title: "Утро")
let draft = renamed(original, to: "Вечер")
print(original.title)
print(draft.title)
```

- Присваивание struct даёт значение, class — ссылку на экземпляр.
- let ссылки не делает var-свойства объекта константами.
- Ссылка внутри struct сохраняет свою ссылочную семантику.

## Проверь себя

Закрой код и объясни, какое состояние изменится.

- Почему первая class-версия поменяла original?
- Где вызывающий код принимает результат renamed?
- Почему struct с Participants-классом не является глубоким независимым снимком?

## Ответы к «Проверь себя»

- `RouteDraft` там — класс, а `let draft = original` копирует не объект, а ссылку на него: экземпляр создали один раз, и обе переменные указывают на него. Поэтому `draft.title = "Вечер"` меняет единственный объект, и `original.title` тоже печатает «Вечер». `original === draft` даёт true — это один экземпляр, а не два одинаковых плана.
- Вызывающий код принимает результат в строке `let draft = renamed(original, to: "Вечер")`. Внутри функция правит свою локальную копию `var draft = route` и возвращает её, а параметр `route` только читается. Поэтому оригинал остаётся «Утро», а если результат не присвоить, правка просто потеряется; для изменения самого переданного значения нужен отдельный контракт `inout` и `&`.
- Присваивание структуры копирует её поля, а поле `participants` хранит ссылку на класс, поэтому копируется ссылка, а не объект `Participants`. Названия у черновиков независимы, но `draft.participants.count = 2` меняет общий объект, и оригинал тоже видит 2. `let participants` запрещает лишь заменить ссылку; для независимого счётчика `Participants` делаешь структурой, а поле в черновике — `var`.

# ГЛУБЖЕ

## Стек и heap — модель размещения

Если тебя спросят про stack и heap, сначала отдели память от семантики. Стек удобно представлять как области вызовов, heap — как динамически управляемое хранилище. Но из слова struct нельзя вывести точное место хранения экземпляра.

В этой модели каждый вызов кладёт свой кадр на стек, а после возврата кадр снимается. Heap позволяет хранить данные дольше одного вызова. Это объяснение организации памяти, а не гарантированная схема для конкретного struct или class.

Значение может находиться внутри объекта класса, захваченного контекста или буфера коллекции, а оптимизатор может убрать отдельное размещение. Нужны конкретная сборка и измерение; пример с print не доказывает адрес или выделение памяти.

## Копия значения и стоимость

Не обещай, что присваивание обязательно копирует содержимое сразу. Стандартные коллекции используют Copy-on-Write: общая внутренняя память допустима, пока наблюдаемое поведение остаётся значением.

Стоимость зависит от типа, размера и выполняемой операции. В следующем уроке сделаем свою обёртку, где правило отделения перед записью видно в коде.

## Идентичность и равенство

Сравни два разных RouteDraft-класса с одинаковыми полями. === даст false; одинаковый id или title не делает их одним экземпляром. == требует отдельного правила равенства типа.

Для снимков данных часто уместны struct и сравнение значений. Для общего владельца ресурса может быть нужен class с явно общей жизнью. Не выбирай class лишь ради меньшего числа строк.

## Коллекция ссылок

Array сама является значением, но её элементы могут быть классами. Добавление элемента в копию массива не добавляет его в оригинальный массив; изменение общего элемента-класса видно через обе коллекции.

Перед исправлением спроси, копируешь ли набор ссылок или сами объекты. Для независимого состояния отдельного элемента можно создать новый экземпляр, сохранив его предметный id.
