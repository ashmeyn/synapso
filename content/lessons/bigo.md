scenario: После загрузки уведомлений нужно посчитать непрочитанные для каждого раздела. На маленьком наборе код работает быстро, а на большой истории повторно просматривает одни и те же уведомления.
goals:
- объяснять O(n), O(n²) и O(1) через количество действий при росте входа
- заменить повторные просмотры истории одним проходом со словарём
- отдельно оценивать время, дополнительную память и проверять вывод на подходящем входе

## Смотрим, что считает экран

Смотри: у каждого уведомления есть собственный `id` и номер раздела `sectionID`. Экрану нужна сводка «раздел 7 — два непрочитанных, раздел 9 — одно». Раздел 7 — доставка, 9 — новости приложения. Прочитанные уведомления в счётчики не входят; отсутствие ключа означает ноль.

```swift
struct AppNotification {
    let id: Int
    let sectionID: Int
    let isUnread: Bool
}
let notifications = [
    AppNotification(id: 1, sectionID: 7, isUnread: true),
    AppNotification(id: 2, sectionID: 7, isUnread: true),
    AppNotification(id: 3, sectionID: 9, isUnread: true)
]
```

Номера уведомлений во входной истории уникальны. Сначала считаем весь снимок, вопрос повторной доставки уведомлений оставим для углубления.

## Пишем в лоб и считаем одно заново

Тут стажёры часто считают раздел для каждого его уведомления. Результат верный, но для раздела 7 один и тот же ответ вычисляется дважды.

```swift
func slowCounts(_ notifications: [AppNotification]) -> [Int: Int] {
    var result: [Int: Int] = [:]
    for notification in notifications where notification.isUnread {
        var count = 0
        for candidate in notifications {
            if candidate.isUnread
                && candidate.sectionID == notification.sectionID {
                count += 1
            }
        }
        result[notification.sectionID] = count
    }
    return result
}
```

Каждое непрочитанное запускает полный просмотр истории. Словарь в конце хранит правильные числа, поэтому ошибка производительности не видна по одному результату.

## Считаем работу, а не секунды

Остановись на истории, где все уведомления непрочитаны. Для n уведомлений внутреннюю проверку выполним n × n раз: при 10 это 100, при 100 — 10 000. Вход вырос в десять раз, работа — в сто.

```swift
let smallN = 10
let largeN = 100
print(smallN * smallN) // 100
print(largeN * largeN) // 10000
```

Такой рост называют O(n²). Big-O описывает, как растёт объём работы с размером входа. Он не обещает конкретное время на телефоне: эти числа — количество проверок, а не миллисекунды.

## Каждое уведомление учитываем один раз

Окей, нам не нужен новый поиск по истории. Встречаем непрочитанное уведомление и увеличиваем счётчик его раздела. `default: 0` даёт начальный ноль, если ключа ещё нет.

```swift
func unreadCounts(_ notifications: [AppNotification]) -> [Int: Int] {
    var result: [Int: Int] = [:]
    for notification in notifications {
        if notification.isUnread {
            result[notification.sectionID, default: 0] += 1
        }
    }
    return result
}
```

Теперь уведомлений 10 — проходов через тело 10, уведомлений 100 — 100. С учётом средней стоимости операций словаря время растёт как O(n). Почему здесь говорим «в среднем», разберём в «ГЛУБЖЕ».

## Два прохода тоже могут быть линейными

Смотри на порядок действий, прежде чем считать циклы. Если сначала посчитать непрочитанные, а затем посчитать всю историю, мы пройдём её дважды подряд. Это примерно 2n шагов, а не n × n.

```swift
var unread = 0
for notification in notifications { if notification.isUnread { unread += 1 } }
var total = 0
for _ in notifications { total += 1 }
print(unread, total) // 3 3
```

При увеличении входа в десять раз оба прохода вырастут в десять раз. В Big-O постоянный множитель опускают: получаем O(n). Это не делает два прохода одинаковыми по секундам с одним проходом.

## За ускорение тоже платим памятью

Теперь спроси себя, что хранится сверх входного массива. Словарь содержит по счётчику на раздел с непрочитанными. Если таких разделов k, дополнительная память — O(k); в худшем случае каждый из n уведомлений из отдельного раздела, и k = n.

```swift
let counts = unreadCounts(notifications)
print(counts.count) // 2 раздела, а не 3 уведомления
```

Чтение одного готового счётчика по целочисленному ключу в среднем O(1). Но построение всей сводки остаётся O(n). Запомни это различие: быстро получить результат и быстро подготовить все результаты — разные операции.

## Подвох: тест без непрочитанных

Вот тут ловушка: запустили старый код на истории, где всё прочитано. Внутренний цикл не начался, ответ появился быстро. Такой вход не показывает случай, на котором алгоритм делает больше всего работы.

```swift
let readHistory = [AppNotification(id: 4, sectionID: 7, isUnread: false)]
print(slowCounts(readHistory).count) // 0
```

Для сравнения проверок возьми разные размеры истории, где все уведомления непрочитаны. Тебя спросят: «Почему O(n²), если здесь было быстро?» Ответь, что оценивал худший случай роста работы; затем назови его вход. Реальное время проверяют отдельным замером.

## Оставляем один проход

Окей, теперь объясни ревьюеру оба решения без слова «быстрее»: что мы перестали повторять и сколько уведомлений обязаны просмотреть. Финальная функция учитывает каждое непрочитанное ровно один раз.

```swift
struct AppNotification {
    let id: Int
    let sectionID: Int
    let isUnread: Bool
}
func unreadCounts(_ notifications: [AppNotification]) -> [Int: Int] {
    var result: [Int: Int] = [:]
    for notification in notifications {
        if notification.isUnread {
            result[notification.sectionID, default: 0] += 1
        }
    }
    return result
}
let notifications = [
    AppNotification(id: 1, sectionID: 7, isUnread: true),
    AppNotification(id: 2, sectionID: 7, isUnread: true),
    AppNotification(id: 3, sectionID: 9, isUnread: false)
]
let counts = unreadCounts(notifications)
print(counts[7, default: 0]) // 2
print(counts[9, default: 0]) // 0
```

- Если каждый элемент запускает полный проход по входу — проверь, не получился ли квадратичный рост.
- Если проходы идут подряд — складывай их работу; одинаковые линейные проходы остаются O(n).
- Если хранишь дополнительный результат — оцени его размер отдельно от времени.

## Проверь себя

Закрой итоговую функцию и попробуй объяснить её на десяти и ста уведомлениях. Не называй символ сложности, пока не объяснишь, какие действия считаешь.

- Во сколько раз вырастет число внутренних проверок старого кода при увеличении непрочитанной истории в десять раз?
- Почему два последовательных прохода дают O(n), а наши вложенные — O(n²)?
- Почему количество записей в словаре может быть меньше количества уведомлений?

## Ответы к «Проверь себя»

- В сто раз: когда все уведомления непрочитаны, каждое запускает полный просмотр истории, то есть n × n проверок. При 10 это 100, при 100 — 10 000: вход вырос в десять раз, работа — в сто. Это и есть O(n²), и считаем мы проверки, а не миллисекунды.
- Последовательные проходы складываются: два прохода по n элементов — примерно 2n шагов, и при росте входа в десять раз оба вырастут в десять раз. Постоянный множитель в Big-O опускают, получаем O(n). Во вложенных циклах каждый элемент снаружи запускает полный проход внутри, работа умножается, n × n, — поэтому O(n²).
- Ключ словаря — `sectionID`, а не уведомление: несколько непрочитанных из одного раздела увеличивают один и тот же счётчик через `result[notification.sectionID, default: 0] += 1`. Прочитанные в словарь не попадают вовсе, отсутствие ключа означает ноль. Поэтому записей столько, сколько разделов с непрочитанными (k), а дополнительная память — O(k), в худшем случае k = n.

# ГЛУБЖЕ

## Что означает «в среднем» у словаря

Смотри, словарь использует хеш ключа для поиска. Для `Int` мы рассматриваем вычисление хеша как действие постоянной стоимости, а поиск и вставку — как O(1) в среднем. Коллизии и расширение хранилища могут сделать конкретное обращение дороже.

Поэтому итоговая оценка — O(n) в среднем, а не обещание фиксированного времени каждого вызова. Это другое усреднение, чем выбор удобной истории уведомлений. Если заменишь `Int` длинными строками, стоимость хеширования их содержимого тоже нужно учитывать.

## Где здесь O(log n) и O(n log n)

Тебя спросят о других формах роста. Бинарный поиск в отсортированном массиве номеров каждый раз сокращает область поиска вдвое: O(log n). Сортировка сравнением обычно требует O(n log n) работы.

Если отсортировать уведомления по `sectionID`, можно затем считать группы за один проход. Но сортировка добавит работу; для нашей сводки словарь подходит проще. Даже если уведомления уже сгруппированы, нужно прочитать все их флаги, поэтому полный подсчёт не превращается в O(log n).

## Почему append называют амортизированным

Представь, что мы дополнительно собираем массив непрочитанных. Большинство `append` добавляют один элемент, но иногда массиву нужно расширить хранилище и перенести прежние значения. Одна вставка тогда дороже обычной.

Если распределить такие расширения по длинной серии вставок, стоимость одной вставки получается амортизированно O(1). Не путай это со средним хеш-поиском: речь о суммарной цене серии операций. Сам массив непрочитанных потребует до O(n) дополнительной памяти.

## Пришло одно новое уведомление

Окей, после полного подсчёта можно обновлять один счётчик при каждом новом уведомлении. Но сервер может прислать тот же `id` снова; без отметки обработанных номеров мы завысим результат.

```swift
var seenIDs: Set<Int> = []
var counts: [Int: Int] = [:]
for notification in notifications {
    if seenIDs.insert(notification.id).inserted && notification.isUnread {
        counts[notification.sectionID, default: 0] += 1
    }
}
```

Это подходит для новых уведомлений, чьи `id` ещё не обрабатывались. Обновление одного уведомления занимает в среднем O(1), но хранение всех `seenIDs` требует памяти по числу уведомлений. Изменение уже известного уведомления с непрочитанного на прочитанное требует отдельного обновления модели и счётчика.
