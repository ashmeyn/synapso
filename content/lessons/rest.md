## Сначала прочитаем контракт

У плейлиста 9 есть записи. GET /playlists/9/entries читает список. POST по тому же адресу с {"track_id":3} создаёт запись 101 и отвечает 201 с Location /playlists/9/entries/101. DELETE по адресу этой записи отвечает 204 без тела.

Это объявленный учебный API, не существующий сервис. REST — архитектурный стиль работы с ресурсами; сегодня разбираем его HTTP-контракт, а не все ограничения стиля. Запись плейлиста имеет свой id: один трек можно добавить несколько раз отдельными записями.

## Пишем в лоб: тело не меняет смысл GET

Посмотри на построенный запрос; отправлять его пока не будем.

```swift
import Foundation
let url = URL(string: "https://api.example.invalid/playlists/9/entries")!
var request = URLRequest(url: url)
request.httpMethod = "GET"
request.httpBody = Data(#"{"track_id":3}"#.utf8)
```

Клиент хотел добавить запись, но GET предназначен для чтения. Тело не превращает его в создание: по нашему контракту этот запрос не создаёт запись. Дальше уберём и !: ошибка построения URL должна оставаться явным результатом. .invalid выбран специально; реальные запросы не выполняем.

## Метод и адрес задают действие

Давай сначала назовём действие словами, а потом выберем метод. Для чтения выбирай GET. Для создания новой записи по адресу коллекции — POST. Для удаления — DELETE с id конкретной записи. Не подставляй track_id вместо entryID: трек 3 и запись 101 — разные сущности.

Дополняем контракт: PUT /playlists/9 принимает полное изменяемое представление {"name":"В дорогу"}; у плейлиста здесь только одно изменяемое поле name. PATCH /playlists/9/entries/101 меняет отдельную note через {"note":"Утро"}. PUT — замена, PATCH — описанное частичное изменение. Метод похож на глагол, адрес — на предмет действия; одного предмета без глагола недостаточно.

## Заголовок описывает тело

Собери POST. Content-Type описывает отправляемое тело; Accept — предпочтительный формат ответа. Они не меняют метод и не гарантируют успех.

```swift
import Foundation
func makeAddRequest() -> URLRequest? {
    let address = "https://api.example.invalid/playlists/9/entries"
    guard let url = URL(string: address) else { return nil }
    var request = URLRequest(url: url)
    request.httpMethod = "POST"
    request.setValue("application/json", forHTTPHeaderField: "Content-Type")
    request.setValue("application/json", forHTTPHeaderField: "Accept")
    request.httpBody = Data(#"{"track_id":3}"#.utf8)
    return request
}
```

URLRequest — описание запроса, Data — байты. `#"..."#` позволяет записать JSON-кавычки без экранирования, `.utf8` даёт байты строки. Здесь текст JSON задан вручную; безопасную сборку из модели разберём в Codable. return nil сообщает о неудачной сборке адреса, запрос пока не отправлен.

## Удаляем запись, не трек вообще

Теперь выбери entryID 101. Правило учебного API требует положительный id.

```swift
import Foundation
func makeDeleteRequest(entryID: Int) -> URLRequest? {
    guard entryID > 0 else { return nil }
    let address = "https://api.example.invalid/playlists/9/entries/\(entryID)"
    guard let url = URL(string: address) else { return nil }
    var request = URLRequest(url: url)
    request.httpMethod = "DELETE"
    return request
}
```

У DELETE в этом контракте тела нет. Не пытайся удалить по адресу /tracks/3: это был бы другой ресурс и другое действие. Обрати внимание, что guard работает и для 0 — запрос не строится. Авторизация, если API её требует, передаётся заголовком Authorization, например схемой Bearer с настоящим токеном; в этом локальном примере токен не нужен.

## Код ответа читаем до тела

Не спеши открывать JSONDecoder: сначала посмотрим, что вообще ответил сервер. Обработаем удаление отдельно от разбора JSON.

```swift
func deleteMessage(status: Int) -> String {
    switch status {
    case 204: return "Удалено"
    case 401: return "Нужен вход"
    case 404: return "Записи нет"
    case 500...599: return "Сбой сервера"
    default: return "Неожиданный ответ"
    }
}
```

Наш DELETE успешно завершается именно 204: это ответ без содержимого. Пытаться декодировать его как JSON — ошибка клиента. 200 и 201 тоже успешные HTTP-статусы, но смысл и тело определяются операцией. 202 означает принятие к обработке, не обязательно завершение.

401 требует разобраться со входом, 403 — с разрешением, 404 — с отсутствием, 429 — с ограничением запросов. Не называй любой 2xx «всё уже сделано» и любой 4xx «плохой JSON».

## Пройди потерянный ответ

Представь неприятный момент: POST добавил трек 3, сервер создал запись 101, а клиент не дождался ответа. Если автоматически повторить POST, наш API может создать ещё запись 102. Таймаут не доказывает, что операция не случилась.

GET, PUT и DELETE идемпотентны по HTTP: повтор одного и того же запроса имеет тот же предполагаемый эффект, хотя коды ответов и журналы могут отличаться. POST такой гарантии по методу не даёт. Повтор удаления 101 может получить 404, но запись всё равно отсутствует. Для защиты создания нужен контракт сервера, например поддерживаемый ключ идемпотентности, а не случайный заголовок без договорённости.

## Собираем запрос и результат

Окей, сведём адрес, метод и результат в один пример. Он только строит запрос и разбирает заданный статус. Сети и ответа сервера здесь нет.

```swift
import Foundation
func makeDeleteRequest(entryID: Int) -> URLRequest? {
    guard entryID > 0 else { return nil }
    let address = "https://api.example.invalid/playlists/9/entries/\(entryID)"
    guard let url = URL(string: address) else { return nil }
    var request = URLRequest(url: url)
    request.httpMethod = "DELETE"
    return request
}
func deleteMessage(status: Int) -> String {
    switch status {
    case 204: return "Удалено"
    case 401: return "Нужен вход"
    case 404: return "Записи нет"
    case 500...599: return "Сбой сервера"
    default: return "Неожиданный ответ"
    }
}
if let request = makeDeleteRequest(entryID: 101) {
    print(request.httpMethod ?? "")
}
print(deleteMessage(status: 204))
```

Вывод — DELETE и «Удалено».

- Сначала выбирай ресурс и действие, затем тело и заголовки.
- Сверяй успешный статус с контрактом конкретной операции.
- Пустой 204 не декодируй; неизвестный исход POST не исправляй слепым повтором.

## Проверь себя

Укажи конкретные адреса, а не только названия методов.

- Почему создание идёт к коллекции, а удаление — к записи 101?
- Почему Content-Type application/json не исправит GET вместо POST?
- Что известно после 204 и чего нельзя заключить после таймаута POST?

## Ответы к «Проверь себя»

- Записи 101 до POST ещё нет, поэтому создание идёт к коллекции `POST /playlists/9/entries` с телом `{"track_id":3}`: сервер сам выдаёт id и отвечает 201 с `Location /playlists/9/entries/101`. Удаление касается одной конкретной записи, поэтому `DELETE /playlists/9/entries/101`, без тела. Трек 3 и запись 101 — разные сущности: один трек может стоять в плейлисте несколькими записями, а `/tracks/3` был бы другим ресурсом и другим действием.
- Действие задаёт метод, а `Content-Type` лишь описывает формат отправляемого тела. GET предназначен для чтения, и ни тело, ни заголовок не превращают его в создание; заголовки вообще не меняют метод и не гарантируют успех. Поэтому сверяешь сначала глагол и адрес: `request.httpMethod = "POST"` к `/playlists/9/entries`, и только потом JSON-заголовки и тело.
- После 204 известно, что DELETE успешно завершился, а тела в ответе нет: декодировать его как JSON — ошибка клиента. После таймаута POST неизвестно ничего: сервер мог уже создать запись 101, а потерялся только ответ. POST не идемпотентен по методу, поэтому слепой повтор может создать запись 102; защищать создание должен контракт сервера, например поддерживаемый ключ идемпотентности.

# ГЛУБЖЕ

## REST шире таблицы методов

Если тебя спросят, что такое REST, не останавливайся на названиях методов. HTTP-API с GET и POST не автоматически выполняет все ограничения REST. Важны работа с ресурсами, единообразный интерфейс, отсутствие клиентской сессии в серверной обработке запросов и другие ограничения стиля.

Наш урок помогает читать практический HTTP-контракт. Не используй слово REST как обещание, что любой сервер одинаково трактует URL, JSON и ошибки.

## Кэширование зависит от ответа

Не угадывай поведение кэша по одному методу. GET допускает кэширование, но реальное повторное использование определяется Cache-Control, проверками актуальности и другими условиями. Не обещай, что каждый GET будет закэширован.

POST тоже может иметь кэшируемый ответ при предусмотренных HTTP-условиях; просто это не обычная автоматическая гарантия. Кэшируемость, безопасность и идемпотентность — разные свойства.

## PATCH и повтор

Тут смотри на само изменение: PATCH описывает частичное изменение и сам по себе не гарантирует идемпотентность. Установка note в «Утро» может быть идемпотентной по конкретному контракту; команда «добавь одну запись» — нет.

Сначала прочитай формат patch-документа. application/json с нашей note — договорённость этого API, а не универсальный стандарт каждого PATCH.

## Параллельное редактирование

Представь, что плейлист редактируют с двух устройств. Два клиента могут прочитать старое имя плейлиста и перезаписать друг друга. Сервер может дать ETag, а клиент — отправить условие If-Match, чтобы изменение прошло только для ожидаемой версии.

Если условие не совпало, нужно заново получить состояние и решить конфликт. Это отдельное правило конкурентного обновления; один PUT не предотвращает потерю чужих изменений.
