## Сохрани знакомый инвариант

Начни с правила из race: два increment должны дать 2; claim(limit: 1) не должен принять две операции. Меняется механизм владения, а не смысл счётчика.

## Пишем в лоб: защищены части, но не решение

Не считай два внешних вызова одной транзакцией. Вспомни модель: A прочитал 0, B прочитал 0, каждый решил «место есть». Очередь или actor могут защищать отдельные чтения, но не этот общий вывод.

## Actor владеет изменяемым состоянием

Замени private queue на actor. Его изолированный код не исполняется одновременно с другим изолированным кодом того же экземпляра. increment не содержит await, поэтому его read-modify-write не разрывается.

```swift
actor CompletedCounter {
    private var stored = 0
    func increment() { stored += 1 }
    func read() -> Int { stored }
    func claim(limit: Int) -> Bool {
        guard stored < limit else { return false }
        stored += 1
        return true
    }
}
```

Снаружи другого изоляционного контекста пиши await counter.increment(), await counter.read(), await counter.claim(limit: 1). Это требует async-контекста; Task позволяет войти в него из синхронного кода. Внутри изоляции того же актора эти синхронные методы не требуют await.

## await — возможная пауза, не блокировка

Проследи один вызов: задача ждёт доступа к актору и может приостановиться, не удерживая поток ради ожидания. Actor не закреплён за отдельным потоком и не обещает FIFO по времени создания задач. Аналогия: один журнал ведёт один ответственный, но пока он ждёт подтверждение, может принять другое поручение.

## Подвох: состояние стареет между await

Прочитай before: оно взято до двух возможных приостановок. Пока confirm или pause ждут, другая операция может вызвать increment. Возвращаясь, метод всё ещё использует старое значение. Это reentrancy: другой код актора может исполниться между сегментами метода.

```swift
func claim(limit: Int, confirm: () async -> Bool,
           pause: () async -> Void) async -> Bool {
    let before = stored
    guard await confirm() else { return false }
    await pause()
    guard before < limit else { return false }
    stored = before + 1
    return true
}
```

Это метод внутри CompletedCounter со stored. Если before был 0, во время pause increment сделал 1, limit равен 1: старый метод вернёт true и запишет 1. Две принятые операции не должны вместиться в лимит 1. Это логическая ошибка без data race.

## Исправление: проверь после ожидания

Перенеси проверку актуального stored после всех await. Между guard и изменением больше нет await, поэтому другой изолированный код не вклинится в этот синхронный сегмент.

```swift
func claim(limit: Int, confirm: () async -> Bool,
           pause: () async -> Void) async -> Bool {
    guard await confirm() else { return false }
    await pause()
    guard stored < limit else { return false }
    stored += 1
    return true
}
```

В той же истории stored уже 1; исправленный метод вернёт false и сохранит 1. confirm проверяет внешнее условие, а окончательная проверка лимита опирается на текущее состояние.

## nonisolated для независимой подсказки

Отдели неизменяемую справку от счётчика. nonisolated-метод не входит в изоляцию актора и не вправе читать его изменяемый stored. Здесь возвращается фиксированная строка.

```swift
actor CounterHelp {
    private var stored = 0
    nonisolated func help() -> String { "Заверши упражнение" }
    func read() -> Int { stored }
}
```

Внешний caller вызывает help.help() без await; изолированный read — через await из другого контекста. nonisolated не является разрешением обходить защиту памяти.

## Итог: весь increment в одном сегменте

Собери actor и async-функцию вызова. async let создаёт две дочерние задачи; await пары дожидается обеих перед read. Не выводи порядок их запуска из расположения строк.

```swift
actor CompletedCounter {
    private var stored = 0
    func increment() { stored += 1 }
    func read() -> Int { stored }
    func claim(limit: Int) -> Bool {
        guard stored < limit else { return false }
        stored += 1
        return true
    }
}
func finishExercises() async {
    let counter = CompletedCounter()
    async let first: Void = counter.increment()
    async let second: Void = counter.increment()
    _ = await (first, second)
    print(await counter.read())
    print(await counter.claim(limit: 2))
}
```

Вывод 2, затем false: лимит 2 уже достигнут. Actor защищает данные; бизнес-инвариант держится потому, что claim проверяет и изменяет состояние без паузы между ними.

## Проверь себя

Проверь границы изоляции, не названия типов.

- Где внешнему caller нужен await?
- Почему before может устареть внутри одного метода?
- Что нельзя читать из nonisolated?

## Ответы к «Проверь себя»

- `await` нужен, когда вызываешь изолированный метод актора снаружи его изоляции: `await counter.increment()`, `await counter.read()`, `await counter.claim(limit: 1)`. Задача может приостановиться в ожидании доступа к актору, поэтому такой вызов возможен только в async-контексте, а из синхронного кода в него входят через `Task`. Внутри изоляции того же актора его синхронные методы вызываются без `await`.
- `before` прочитан до `await confirm()` и `await pause()`, а каждая такая пауза — место, где другой код актора может исполниться между сегментами метода (reentrancy). Пока метод ждёт, чужой `increment` меняет `stored`, а вернувшийся метод решает по старому значению и пропускает лишнюю операцию сверх лимита. Поэтому проверку `guard stored < limit` и изменение `stored += 1` ставишь после последнего `await`, без паузы между ними.
- Из `nonisolated`-метода нельзя читать изменяемое состояние актора, например `stored`: такой метод не входит в изоляцию актора. Зато его можно вызывать без `await`, как `help.help()` с фиксированной строкой. Поэтому `nonisolated` подходит для неизменяемой справки, но не служит способом обойти защиту памяти.

# ГЛУБЖЕ

## Снимок вместо двух getter

Если экрану нужны completed и failed одного момента, верни пару в одном синхронном actor-методе. Два внешних await могут разделить изменения, хотя каждый доступ по отдельности безопасен.

## Повторная проверка не откатывает эффект

Перед ожиданием не выполняй необратимый внешний эффект с обещанием, что поздний guard всё исправит. Для бронирования понадобится явное состояние резервирования и политика возврата; метод без await решает только локальный переход.

## Отмена и устаревшая сессия

Если счётчик сбросили для нового дня во время await, старую операцию можно отклонить по поколению generation: запомни номер до ожидания, после сравни с текущим. Это логическая актуальность, которую actor автоматически не проверяет.

## Передача значений между изоляциями

Начни с Int, Bool, String и снимков значений. Передача общей изменяемой ссылки требует отдельного контракта, проверяемого через Sendable и изоляцию. В Swift 5 диагностика строгой проверки может быть предупреждением; это не доказательство корректности произвольной ссылки.
