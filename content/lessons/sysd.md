## Сначала рамки задачи

На собесе уточни контент и размер страницы, нужен ли офлайн после перезапуска, можно ли менять закладки без сети, есть ли несколько устройств и удаление постов. Здесь договоримся: текстовая лента, 20 постов на страницу, сохранённая копия на диске, отдельный кэш изображений, сервер владеет текстом, закладка синхронизируется позже. Не проектируй чат и видео, если их не просили. Офлайн-копия — как сохранённый билет: доступна без сети, но сама не доказывает актуальность.

## Пишем в лоб: заменяем весь кэш

Если присвоить cached=serverPage, пропадут остальные страницы и несинхронизированная закладка. В задаче post 31 имеет revision=1 и pendingSaved=true; сервер прислал новую revision=2, isSaved=false. Текст надо обновить, локальный выбор — сохранить. Отличи копию сервера от намерения пользователя, тогда правило можно проверить.

```swift
struct Post: Equatable {
    let id: Int
    let revision: Int
    let order: Int
    let title: String
    let isSaved: Bool
}
struct CachedPost: Equatable {
    var server: Post
    var pendingSaved: Bool?
    var visibleSaved: Bool { pendingSaved ?? server.isSaved }
}
```

id — идентичность, revision — версия содержимого, order — отдельный ключ порядка. Равная revision означает одинаковую серверную запись по нашему контракту. В local каждый id уникален; отсутствие в странице не является удалением.

## API: курсор не номер страницы

GET /feed получает cursor и limit; ответ содержит items и nextCursor. nil в запросе означает первую страницу, nil в ответе — конец, поэтому нужен отдельный endReached. Курсор непрозрачен: не увеличивай его и не выводи из id поста. Сервер обещает устойчивый порядок в рамках выбранного прохода; повторы id всё равно обрабатываем. Для ошибок возвращаются различимые статусы/категории, а не пустой успешный список.

```swift
struct FeedPage { let items: [Post]; let nextCursor: String? }
struct CursorRequest { let cursor: String? }
```

begin выставляет loading, повторный begin пока loading возвращает nil. Только успешный ответ продвигает next; ошибка снимает loading и оставляет тот же курсор. Если запрос отменён, тоже явно заверши его состояние.

## Репозиторий объединяет источники

Раздели транспорт, декодирование, дисковое хранилище, репозиторий и состояние экрана. Сначала репозиторий отдаёт сохранённые записи, затем обновляет их ответом сервера; UI может показывать stale/loading/error отдельно от самих данных. Функция mergeOne ниже обновляет только более свежую серверную запись, оставляя pendingSaved. Post/CachedPost уже объявлены.

```swift
func mergeOne(_ remote: Post, existing: CachedPost?) -> CachedPost {
    guard var cached = existing else {
        return CachedPost(server: remote, pendingSaved: nil)
    }
    if remote.revision > cached.server.revision { cached.server = remote }
    return cached
}
```

Затем объединяем страницу по id и сортируем по order, не по названию и не по позиции ответа. Это не обещание, что вся лента навсегда помещается в память.

```swift
func merge(_ remote: [Post], local: [CachedPost]) -> [CachedPost] {
    let pairs = local.map { ($0.server.id, $0) }
    var index = Dictionary(uniqueKeysWithValues: pairs)
    for post in remote {
        index[post.id] = mergeOne(post, existing: index[post.id])
    }
    return index.values.sorted { a, b in
        if a.server.order == b.server.order { return a.server.id < b.server.id }
        return a.server.order > b.server.order
    }
}
```

## Офлайн и конфликт — отдельный контракт

Сохранённый пост и NSCache картинки решают разные задачи: NSCache может выбросить изображение и не является дисковой офлайн-базой. Закладка хранит pendingSaved до подтверждения конкретной операции; старый ack не должен стирать более новое намерение. Здесь выбираем локальный pending как видимое значение, а сервер отклоняет либо принимает запись с согласованным токеном/версией. Для нескольких устройств заранее договорись о конфликте, не называй «последняя по часам» универсальным решением.

## Реальное время не гарантирует полноту

Для этой ленты достаточно обычных запросов и push как сигнала «проверь обновления»; WebSocket/SSE выбирают при требовании меньшей задержки и допустимой стоимости подключения. Сигнал может потеряться, поэтому после восстановления связи запрашивай согласованный delta либо новый проход. Удаление приходит явно deletedIDs: по нашему контракту оно сильнее локальной закладки и убирает запись вместе с pending. Не считай отсутствующий id в странице удалённым. Метрики: задержка первого содержимого, доля ошибок, кэш-hit, конфликты и объём переданных данных.

## Ошибка не означает бесконечный повтор

Для идемпотентного чтения здесь максимум три попытки: после ошибок первой и второй планируем 1 и 2 секунды; после третьей останавливаемся. unauthorized требует восстановления авторизации, invalidData — разбора контракта, их этим правилом не повторяем. Функция возвращает план задержки, не спит и не запускает сеть.

```swift
enum FeedFailure { case transient, unauthorized, invalidData }
func retryDelay(_ failure: FeedFailure, attempt: Int) -> Int? {
    guard case .transient = failure, (1...2).contains(attempt) else {
        return nil
    }
    return [1, 2][attempt - 1]
}
```

В production добавь отмену, backoff с jitter и уважение Retry-After с пределом; для записи нужен контракт идемпотентности. Не повторяй неизвестную запись лишь потому, что чтение можно повторить. Продолжение загрузки должно быть явным и ограниченным.

## Итог: маленькие проверяемые решения

Самостоятельный CursorPager ниже не грузит сеть: выдаёт запрос и принимает решение о следующем курсоре. Кэш и merge — отдельная обязанность из основы. Это и есть ответ по слоям на собесе: сначала контракт, затем ключевое правило и его края, затем компромисс, а не диаграмма ради диаграммы.

```swift
struct CursorRequest { let cursor: String? }
struct CursorPager {
    private(set) var next: String?
    private(set) var endReached = false
    private(set) var loading = false
    mutating func begin() -> CursorRequest? {
        guard !loading, !endReached else { return nil }
        loading = true
        return CursorRequest(cursor: next)
    }
    mutating func accept(nextCursor: String?) {
        next = nextCursor
        endReached = nextCursor == nil
        loading = false
    }
    mutating func fail() { loading = false }
}
```

При новом refresh старый ответ не должен применяться: пометь проход generation и проверь её перед обновлением. Ниже самостоятельная модель этого правила, rows — только id результата.

```swift
struct RefreshToken { let generation: Int }
struct RefreshGate {
    private(set) var generation = 0
    private(set) var rows: [Int] = []
    mutating func refresh() -> RefreshToken {
        generation += 1
        return RefreshToken(generation: generation)
    }
    mutating func accept(_ ids: [Int], token: RefreshToken) {
        guard token.generation == generation else { return }
        rows = ids
    }
}
```

Для реального запроса объедини cursor и generation в request, проверь актуальность до изменения loading/next/rows. Восстановление после перезапуска требует персистентных записей и очереди намерений, а не одного такого struct.

## Проверь себя

Ответь как на собесе: требование → контракт → край → компромисс.

- Какие уточнения меняют выбор кэша, реального времени и API?
- Почему nil в первой загрузке не конец и почему страница не заменяет весь кэш?
- Когда прекращаешь повтор, как сохраняешь pending и что делаешь со старым ответом?

## Ответы к «Проверь себя»

- Сверяешь вопросы до схемы: какой контент и размер страницы, нужен ли офлайн после перезапуска, можно ли менять закладки без сети, есть ли несколько устройств и удаление постов. Офлайн после перезапуска требует сохранённой копии на диске, а не только NSCache; закладки офлайн — отдельного `pendingSaved` и синхронизации позже; несколько устройств — заранее согласованного правила конфликта; удаления — явных `deletedIDs` в API. Требование к задержке решает, хватит ли обычных запросов с push как сигналом «проверь обновления» или нужен WebSocket/SSE.
- В запросе `cursor == nil` означает «дай первую страницу», а в ответе `nextCursor == nil` — «дальше ничего нет», поэтому конец хранишь отдельным `endReached`, иначе первая загрузка и конец списка неразличимы. Страница — лишь часть ленты: `cached = serverPage` сотрёт остальные страницы и несинхронизированную закладку, а отсутствие id в странице не означает удаление. Поэтому сливаешь по id: `mergeOne` берёт серверную запись только при большей `revision` и сохраняет `pendingSaved`, затем сортировка по `order`.
- Повторяешь только `.transient` чтение: после первой и второй ошибки план 1 и 2 секунды, после третьей — `nil`, а `unauthorized` и `invalidData` этим правилом не повторяются вовсе. Закладка живёт в `pendingSaved`: `mergeOne` обновляет только `server` и pending не трогает, а снимаешь его лишь по подтверждению конкретной операции, так что старый ack не стирает более новое намерение. Старый ответ отсекаешь поколением: `refresh()` увеличивает `generation`, а `accept` применяет ids, только если `token.generation == generation`.

# ГЛУБЖЕ

## Истёкший курсор

Сервер может признать курсор устаревшим. Договорись об отдельной ошибке и начале нового прохода с сохранённым офлайн-кэшем, а не повторяй тот же токен бесконечно. Если nextCursor равен использованному токену, это нарушение ожидаемого продвижения: остановись и зафиксируй проблему.

## Очередь намерений и ack

Когда пользователь дважды меняет закладку, у операций разные токены. Подтверждение первой не очищает вторую. Персистентная очередь, дедупликация и серверный idempotency key помогают пережить перезапуск, но ровно один внешний эффект не получается только из локального Bool.

## Удаление и окно кэша

Кэш не обязан хранить историю целиком. Выбери окно и политику удаления, отдельно храни пользовательское намерение до его принятия или явного отказа. Для удалённого сервером поста правило урока отбрасывает закладку и сообщает причину; другой продукт мог бы предложить локальную архивную копию, но это другое требование.

## Метрика с знаменателем

Перед сравнением кэш-hit или процента ошибок зафиксируй период, версию и число запросов. Три попадания и один промах дают 0.75, ноль запросов не даёт 0%: данных нет. Для latency выбери измеряемый интервал и квантиль, не подменяй пользовательский первый экран временем одного HTTP-запроса.
