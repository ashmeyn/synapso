## Что должно услышать окно

У документа 32 есть изменения, затем он сохранён. Событие другого документа 33 не должно менять его надпись. После закрытия наблюдения даже новое сохранение 32 не должно приходить в обработчик.

Combine передаёт последовательность значений: publisher — источник, subscriber — получатель. Не начинай с длинной цепочки операторов; сначала проверим, что источник и получатель вообще встретились.

## Пишем в лоб: событие уже прошло

Попробуй угадать вывод до запуска.

```swift
import Combine
let events = PassthroughSubject<String, Never>()
events.send("Сохранён")
let subscription = events.sink { print($0) }
events.send("Есть изменения")
subscription.cancel()
```

Печатается только «Есть изменения». PassthroughSubject передаёт новые события текущим подписчикам и не хранит прошлое значение для будущей подписки. Переставь подключение sink раньше первого send, если нужно услышать именно то событие.

## Событие и состояние — разные источники

Давай сначала опишем, что несёт событие: documentID выбирает документ, isSaved показывает его статус. Never — тип, обозначающий невозможность значения ошибки; такой поток может завершиться нормально, но не отправить ошибку.

```swift
import Combine
struct DocumentEvent { let documentID: Int; let isSaved: Bool }
let events = PassthroughSubject<DocumentEvent, Never>()
```

Если нужен текущий статус сразу после подключения, используй CurrentValueSubject. Он хранит последнее значение и отдаёт его новому подписчику.

```swift
import Combine
let status = CurrentValueSubject<Bool, Never>(false)
let subscription = status.sink { print($0) }
status.send(true)
subscription.cancel()
```

Вывод — false, затем true. Для событий редактора выбираем PassthroughSubject; для текущего выбранного id в практике пригодится CurrentValueSubject.

## Отберём документ, затем построим подпись

Теперь соберём цепочку: events и DocumentEvent уже объявлены. filter пропускает только нужные значения, map превращает каждое прошедшее событие в строку; здесь это знакомые операции над потоком, не массивом. `$0` — первый аргумент замыкания.

```swift
let subscription = events
    .filter { $0.documentID == 32 }
    .map { $0.isSaved ? "Сохранён" : "Есть изменения" }
    .sink { print($0) }
```

sink подключает обработчик. Условие `isSaved ? A : B` выбирает A при true и B при false. Событие 33 отсеивается; событие 32 с false превращается в «Есть изменения». Подписка похожа на включённый радиоприёмник: настроил канал — слышишь новые сообщения, выключил — больше не получаешь.

## Сохрани срок жизни подписки

Тут легко потерять работающий код из-за одной детали: sink возвращает AnyCancellable, объект отмены. Когда последний владелец освобождает его, подписка отменяется. Не рассчитывай, что вызов sink без сохранения результата даст постоянное наблюдение.

```swift
final class DocumentMonitor {
    private var subscription: AnyCancellable?
    private(set) var message = "Нет событий"
    func start(events: PassthroughSubject<DocumentEvent, Never>) {
        subscription = events
            .filter { $0.documentID == 32 }
            .map { $0.isSaved ? "Сохранён" : "Есть изменения" }
            .sink { [weak self] value in self?.message = value }
    }
    func stop() { subscription?.cancel(); subscription = nil }
}
```

Контекст — import Combine и DocumentEvent выше. subscription хранится в наблюдателе, поэтому живёт после выхода из start. Повторный start заменяет старую подписку, а не намеренно копит несколько. Методы добавляют контроль жизни потока, не запускают сеть.

## Не замкни владельца и обработчик

Обрати внимание на weak self в sink. Наблюдатель хранит AnyCancellable, подписка хранит обработчик; сильный self в нём способен удержать наблюдателя обратно. Используем слабый доступ из clos: исчез объект — запись можно пропустить.

stop вызывает cancel и убирает сохранённую подписку. Это явная остановка, а не изменение надписи. После неё message останется последним полученным значением. Слабый захват и отмена решают разные вопросы: жизнь владельца и получение событий.

## Пройдём события и завершение

Начни с message «Нет событий». После подключения отправь 33/true — ничего не изменится. Отправь 32/false — «Есть изменения», затем 32/true — «Сохранён». Вызови stop; новое 32/false не меняет текст.

Источник можно завершить через `events.send(completion: .finished)`. После завершения он не передаёт новые значения. Never не означает бесконечный поток: это отсутствие ошибок, не отсутствие нормального конца. sink с одной closure подходит здесь именно потому, что Failure — Never.

## Собираем управляемую подписку

Окей, проверим всё вместе. Весь пример работает синхронно в одном месте вызова. Это проверка событий и владения, не демонстрация фонового потока.

```swift
import Combine
struct DocumentEvent { let documentID: Int; let isSaved: Bool }
final class DocumentMonitor {
    private var subscription: AnyCancellable?
    private(set) var message = "Нет событий"
    func start(events: PassthroughSubject<DocumentEvent, Never>) {
        subscription = events
            .filter { $0.documentID == 32 }
            .map { $0.isSaved ? "Сохранён" : "Есть изменения" }
            .sink { [weak self] value in self?.message = value }
    }
    func stop() { subscription?.cancel(); subscription = nil }
}
let events = PassthroughSubject<DocumentEvent, Never>()
let monitor = DocumentMonitor()
monitor.start(events: events)
events.send(DocumentEvent(documentID: 32, isSaved: false))
print(monitor.message)
monitor.stop()
events.send(DocumentEvent(documentID: 32, isSaved: true))
print(monitor.message)
```

Обе строки вывода — «Есть изменения»: второе событие отправлено после stop.

- Подключайся до нужного события и сохраняй объект отмены.
- Отбирай по id до преобразования статуса.
- Для последнего состояния выбирай CurrentValueSubject, для новых событий — PassthroughSubject.

## Проверь себя

Закрой цепочку и пройди одно событие руками.

- Почему событие до подписки пропало у PassthroughSubject?
- Что хранит subscription и как её исчезновение влияет на поток?
- Почему cancel не сбрасывает message и чем текущий статус отличается от события?

## Ответы к «Проверь себя»

- `PassthroughSubject` передаёт событие только тем подписчикам, которые уже подключены в момент `send`, и не хранит прошлое значение для будущих. «Сохранён» ушёл, когда `sink` ещё не было, поэтому печатается только «Есть изменения». Если нужно услышать именно это событие, подключаешь `sink` раньше первого `send`.
- `subscription` хранит `AnyCancellable` — объект отмены, который вернул `sink`. Пока наблюдатель держит его в свойстве, подписка живёт и после выхода из `start`. Когда последний владелец освобождает этот объект, подписка отменяется, поэтому `sink` без сохранения результата постоянного наблюдения не даёт.
- `cancel` останавливает получение событий, а не меняет надпись: обработчик больше не вызывается, и `message` остаётся последним полученным значением — в итоговом примере «Есть изменения». Событие — разовое сообщение, которое услышат только текущие подписчики, это `PassthroughSubject`. Текущий статус хранится и сразу отдаётся новому подписчику: `CurrentValueSubject<Bool, Never>(false)` при подключении печатает `false`, затем `true` после `send(true)`.

# ГЛУБЖЕ

## Получение UI на нужном исполнителе

Не переноси время выполнения этого примера на любой источник: здесь send и sink вызываются синхронно из одного места. Combine сам по себе не гарантирует главный поток для любого источника. Если значения приходят с другого потока, место доставки для UI нужно выбрать явно.

Перед sink часто ставят `receive(on: DispatchQueue.main)`. Это меняет доставку нижней части цепочки; subscribe(on:) решает другую задачу. Не добавляй планировщик в учебную проверку только ради вида: он изменит время получения и потребует дождаться результата.

## Ошибки и завершение

Представь источник, который может завершиться ошибкой. Тогда Failure уже не Never, а sink принимает две closure: receiveCompletion и receiveValue. Последнее значение не является уведомлением о завершении.

Обработка ошибки, повтор и новый источник должны выражаться отдельным решением. Отмена подписчика не равна отправке всем подписчикам .finished от самого источника.

## Повторяющиеся статусы

Если несколько событий подряд превращаются в «Сохранён», можно добавить removeDuplicates после map, чтобы не передавать одинаковые соседние строки. Но это изменит смысл: если важно считать каждое сохранение, повторные события нужны.

Попробуй назвать, что ты моделируешь: состояние надписи или журнал действий. Одинаковый текст не всегда означает одинаковое событие.

## Combine и Observation

Здесь легко спутать два инструмента. @Observable помогает SwiftUI наблюдать чтения модели. Combine описывает поток, его преобразования и подписки. Их можно использовать вместе: поток меняет модель, экран читает её свойства.

Для одного локального поля Combine может быть лишним; для нескольких источников и обработки событий он даёт отдельные инструменты. Не заменяй им любое @State лишь потому, что оба реагируют на изменения.

## Несколько подписок и $-издатель

Если документ получает несколько потоков, не заводи по свойству для каждой подписки: сложи AnyCancellable в Set. store(in:) сохраняет объект отмены в переданном множестве; само множество не предотвращает повторный start.

```swift
import Combine
final class DocumentSignals {
    @Published var revision = 0
}
let signals = DocumentSignals()
var subscriptions = Set<AnyCancellable>()
signals.$revision.sink { print($0) }.store(in: &subscriptions)
signals.revision = 1
subscriptions.forEach { $0.cancel() }
subscriptions.removeAll()
signals.revision = 2
```

Вывод 0, 1. @Published на свойстве класса создаёт издатель, доступный через $revision; revision — значение, $revision — источник его изменений. Новый подписчик получает текущее значение. Сначала отменили подписки, потом очистили Set; изменение до 2 уже не печатается.

Не считай Set счётчиком только активных потоков: завершённая подписка сама из него не исчезает. Для нового сеанса явно останови старый. removeAll освобождает хранящиеся ссылки, но при другом владельце токена может не отменить подписку; явный cancel делает намерение точным.

Проверь ещё одну деталь @Published: публикация происходит перед записью нового значения свойства. В обработчике читай пришедший value, если нужен именно новый результат.

```swift
import Combine
final class DocumentSignals {
    @Published var revision = 0
}
let signals = DocumentSignals()
let subscription = signals.$revision.sink { value in
    print(value, signals.revision)
}
signals.revision = 1
subscription.cancel()
```

Вывод «0 0», затем «1 0». Второй value уже новый, но чтение signals.revision внутри синхронного sink ещё видит прежнее значение. @Published не заменяет изоляцию MainActor, а store(in:) не устраняет сильные захваты владельца.
