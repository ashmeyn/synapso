## Начинаем с воспроизведения

После выбора ячейки 43 экран показывает «Секция А». Затем выбираем отсутствующую 99, но видим прежнее название. Не добавляй сразу десять print: запиши вход и ожидаемое «Не найдено». Отладчик — как стоп-кадр: ты рассматриваешь состояние в конкретной точке, не историю целиком.

```swift
struct Locker { let id: Int; let label: String }
final class LockerPanel {
    let values: [Int: Locker]
    private(set) var title = "Не выбрано"
    init(values: [Int: Locker]) { self.values = values }
    func select(id: Int) {
        guard let value = values[id] else { return }
        title = value.label
    }
}
```

## Обычный и условный breakpoint

Поставь breakpoint на guard в select, запусти выбор 43, затем 99. Выполнение остановится перед этой строкой, и ты увидишь id и values. Для частых вызовов открой Edit Breakpoint и задай Condition id == 99. Сначала убедись, что обычная точка срабатывает: неверное условие может скрыть нужную остановку. Это инструкция для Xcode, не запись проведённого сеанса.

## LLDB: читаем, прежде чем вычислять

В остановленном select команда frame variable id читает локальную переменную; v — её короткий вариант. p values.count вычисляет выражение, po title запрашивает объектное описание. bt показывает стек, а выбранный frame определяет видимые locals. В учебном условии id=99, values содержит только 43, title=«Секция А»: guard выходит, не очищая title. Представление и оформление ответа LLDB зависят от версии; здесь важны значения.

po и p могут выполнять код и менять состояние, поэтому не вызывай select из консоли ради «просмотра». Для простых locals начни с frame variable. Ниже после-фрагмент метода для ранее объявленного LockerPanel.

```swift
func select(id: Int) {
    guard let value = values[id] else {
        title = "Не найдено"
        return
    }
    title = value.label
}
```

## Действие без остановки и исключения

Чтобы увидеть каждый вход без правки исходника, добавь breakpoint action Debugger Command: frame variable id и отметь Automatically continue after evaluating actions. Для неожиданного Objective-C exception добавь Exception Breakpoint: он поможет остановиться у источника, а не только после раскрутки стека. Swift throw — другой механизм: для него есть Swift Error Breakpoint. Ошибка индекса массива и fatalError не становятся Objective-C exception.

## View Hierarchy: текст есть, места нет

Теперь title правильный, но подписи не видно. В учебном воспроизведении LockerView сначала создаётся с width=24: ширина подписи получается 0. Потом контейнер получает width=320, а прежний frame не пересчитывается. В Xcode после появления экрана нажми Debug View Hierarchy, найди titleLabel и сравни его frame с bounds родителя. Проверь также hidden, alpha, положение соседей и ограничения: наличие текста ещё не гарантирует видимость.

```swift
import UIKit
final class LockerView: UIView {
    let titleLabel = UILabel()
    override init(frame: CGRect) {
        super.init(frame: frame)
        addSubview(titleLabel)
        titleLabel.frame = CGRect(x: 12, y: 12,
                                  width: bounds.width - 24, height: 24)
    }
    required init?(coder: NSCoder) { fatalError("Кодовый пример") }
}
```

Не делай вывод, что viewDidLoad всегда получает нулевой размер. Здесь ошибка — одноразовый расчёт до изменения размеров. В контроллере layout-зависимый код относится к viewDidLayoutSubviews, в собственной UIView — к layoutSubviews; при Auto Layout меняй ограничения, а не frame, который они перезапишут.

## Memory Graph: кто сохраняет экран

Если экран после закрытия жив, сначала проверь ожидаемого владельца: navigation stack может держать его законно. Затем в Debug Memory Graph найди StatusPanel и входящие сильные рёбра. В примере panel→feed→onChange→panel — цикл; deinit не сможет сам начать разрыв, пока цикл удерживает объект. Источник здесь рассчитан на одного слушателя.

```swift
final class LockerFeed { var onChange: ((Int) -> Void)? }
final class StatusPanel {
    let feed: LockerFeed
    var free = 0
    init(feed: LockerFeed) {
        self.feed = feed
        feed.onChange = { value in self.free = value }
    }
    deinit { feed.onChange = nil }
}
```

Исправление — [weak self] в callback и явный контракт завершения подписки. weak-наблюдатель и deinit помогают воспроизвести удержание в коде; они не заменяют реальные рёбра Memory Graph и не доказывают утечку одним отсутствующим сообщением.

## print или Logger: выбираем вопрос

print удобен для быстрой локальной проверки вывода, но Logger даёт категории, уровни и правила приватности в unified logging. Для нашей ячейки id — учебный неперсональный идентификатор; для пользовательских кодов и текстов выбери private. Раздели лог «попросили id» и «применили id», иначе последняя строка не покажет, где значение стало неверным.

```swift
import os
let logger = Logger(subsystem: "dev.synapso.demo", category: "Locker")
let requestedID = 99
logger.debug("Выбор id=\(requestedID, privacy: .public)")
```

Logger.debug не обязан выводиться всегда в любой среде: учитывай уровень и настройки просмотра. Лог не заменяет breakpoint для текущего стека и граф для цепочки владельцев.

## Итог: проверяем ту же последовательность

После исправления сначала выбираем 43, затем 99. Полный код ниже не требует UI; он закрепляет причину неверного текста, найденную по состоянию. Отдельно измени размеры view и проверь новый frame, отдельно закрой экран и посмотри слабого наблюдателя. Один успешный сценарий не покрывает три разных бага.

```swift
struct Locker { let id: Int; let label: String }
final class LockerPanel {
    let values: [Int: Locker]
    private(set) var title = "Не выбрано"
    init(values: [Int: Locker]) { self.values = values }
    func select(id: Int) {
        guard let value = values[id] else {
            title = "Не найдено"
            return
        }
        title = value.label
    }
}
let panel = LockerPanel(values: [43: Locker(id: 43, label: "Секция А")])
panel.select(id: 43)
assert(panel.title == "Секция А")
panel.select(id: 99)
assert(panel.title == "Не найдено")
```

Рабочий маршрут: воспроизвести → остановиться в нужной точке → прочитать вход, состояние и стек → исправить правило → повторить тот же вход и край. Назови, какой инструмент дал доказательство, а какой только подсказку.

# ГЛУБЖЕ

## Остановка в оптимизированной сборке

Если local недоступен, не придумывай его значение. Оптимизация может убрать переменную или изменить соответствие строк; для воспроизведения начни с Debug и проверь symbols. Сам факт, что po не смог разобрать выражение, не доказывает баг модели. При просмотре frame variable ты тоже ограничен доступной debug-информацией.

## Стек и исключение: разные сигналы

Если UIKit бросил exception при dequeue незарегистрированной ячейки, Exception Breakpoint позволяет посмотреть аргумент reuseIdentifier у места проблемы. Это новый вопрос, отличный от исчезнувшей подписи. Если стек пришёл из async-кода, не трактуй его как полную синхронную цепочку всех прошлых await; найди актуальный кадр и источник задачи.

## Перекрытие — не нулевой размер

Для нового баннера на экране ячеек нулевая alpha-фона не означает пропуск касаний: прозрачная интерактивная UIView может перекрыть кнопку. В View Hierarchy изучи порядок siblings, затем отдельно проверь hitTest. Если баннер полностью декоративный, отключи interaction; если содержит кнопку, нужен выборочный пропуск касаний, как в теме hit.

## Данные наблюдения превращаем в регрессию

Нашёл конкретный переход 43→99? Сохрани его тестом состояния, чтобы ошибка не вернулась. Не делай скриншот единственным доказательством: текст, геометрия и владение требуют разных утверждений. Приватные значения оставляй скрытыми в логах; диагностический public должен быть осознанным выбором для неперсональных данных.
