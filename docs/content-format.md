# Формат контента

Тема = три файла с одним `id`: урок `content/lessons/<id>.md`, ступени `content/steps/<id>.json`, банк `content/bank/<id>.bank.json`. Тема должна быть в `content/base/content.json` (новая тема без старого контента добавляется туда как `"<id>": {}`), иначе сборщик остановится. Шпаргалка темы — `content/base/ref.json` → `cheat[id]`. Образец урока — `state`.

## Урок (стандарт v2)

Шапка в frontmatter, дальше Markdown. Реальный пример — начало `setdict.md` (сокращено):

```markdown
---
mission: ОПЕРАЦИЯ 10 · АКТИВНОСТЬ В ЧАТЕ
scenario: Из последовательности сообщений нужно показать число сообщений каждого автора и список имён без повторов в порядке первого появления.
goals:
- считать частоты через `Dictionary` с `default:`
- проверять уникальность через `Set.insert(...).inserted`
---

## Смотрим на желаемый экран

На входе `Анна, Илья, Анна`. Сводка должна сказать «Анна — 2, Илья — 1».

## Проверь себя

- Какой результат даст `seen.insert("Анна").inserted` при втором сообщении?

# ГЛУБЖЕ

## Та же идея в two-sum

Словарь может помнить не частоту, а индекс уже встреченного числа.
```

Правила шапки:

1. `mission` — `ОПЕРАЦИЯ N · ЗАГОЛОВОК`. N = позиция темы на карте (порядок `BRANCHES` в `engine/app.js`), заголовок целиком заглавными.
2. `scenario` — 1–2 предложения, обычное приложение (без бара и кафе).
3. `goals` — список. Каждая цель потом проверяется письменной ступенью.
4. `prereqs` — список id тем (`- coll`). Если предпосылок нет, строку не пишем вообще: `prereqs: []` парсер превращает в список символов.

Правила тела:

1. Разделы `##`. Последний раздел базового слоя — «Проверь себя» (вопросы списком).
2. Строка `# ГЛУБЖЕ` (один `#`) отделяет углублённый слой. Базовый слой и ступени не должны на него опираться.
3. Разрешено: абзацы, ```swift, списки `- `, плашки `> `, `код`, **жирный**, *курсив*, ссылки `[текст](https://…)`. Ручные переносы внутри абзаца склеиваются.
4. Голос ментора, одна аналогия на урок.
5. Код: строки до 80 символов, без пустых строк внутри и в конце блока.
6. В прозе «ступень 3», а не «s3». Идентификатор в начале предложения сохраняет регистр кода.

### Ответы к «Проверь себя»

Необязательный раздел сразу после «Проверь себя», ещё в базовом слое (до `# ГЛУБЖЕ`), с точным заголовком `## Ответы к «Проверь себя»`. Тело — список `- `: по одному пункту на вопрос, в том же порядке. Пункт — одна строка (можно `код` и **жирный**), 2–4 предложения голосом ментора по схеме «что → почему → последствия». Пример для `opt`:

```markdown
## Проверь себя

- Почему `return user.name` не компилируется, если функция возвращает `String`?
- Что покажет экран через `user.name ?? "Гость"`, если сервер прислал `""`? Как это починить?
- Где можно пользоваться `name` после `if let`, а где — после `guard let`?

## Ответы к «Проверь себя»

- `user.name` имеет тип `String?`: это «может быть строка», а функция обещает строку всегда. Swift не угадывает, что показать при `nil`, поэтому требует развернуть значение. Отвечаешь на вопрос «а если пусто?» прямо в коде: `if let`, `guard let` или `??`.
- Экран покажет пустой заголовок: `""` — это не `nil`, строка есть, просто без букв. `??` срабатывает только на `nil`, поэтому пустую строку пропускает. Чинится через `guard let name = user.name, !name.isEmpty else { return "Гость" }`.
- После `if let` развёрнутый `name` живёт только внутри фигурных скобок. После `guard let` он доступен до конца функции, потому что ветка `else` обязана выйти. Поэтому `guard` удобен, когда плохие случаи надо отсечь в начале, а дальше спокойно работать со значением.
```

1. Сборщик не кладёт раздел в текст урока: пункты уходят в `lesson.answers`, вопросы «Проверь себя» — в `lesson.check`. Число ответов должно совпадать с числом вопросов; раздел в слое ГЛУБЖЕ или без «Проверь себя» перед ним — ошибка сборки.
2. Ответы показываются на экране «Выгрузка» после того, как ученик открыл ответ. Пока у урока ответов нет, движок показывает шпаргалку темы (`ref.cheat[id]`) с пометкой «ответ ещё не написан».
3. Ответы не должны расходиться с уроком и шпаргалкой: при правке одного проверь остальные.
4. Заполнено во всех 75 уроках (чат 2б, 02.11); новый урок пишется сразу с ответами — `npm test` (suite `answers`) требует их у каждого урока.

## Повествование (стиль с 04.11, образец — `opt.md`)

Дан оценил переписанный `opt` на 7–7.5/10 и выбрал этот стиль для всех уроков. Правила для основы урока (ГЛУБЖЕ не трогаем, кроме переноса фрагментов в основу):

1. **Одна аналогия держит весь урок и стоит в основе**, в первом или втором разделе; дальше разделы на неё опираются («коробка» в `opt`). Если аналогия была только в ГЛУБЖЕ — перенеси в основу.
2. **Сквозная история.** Один экран обычного приложения и одна проблема, которая растёт от раздела к разделу. Каждый раздел `##` начинается мостиком (1–2 предложения: откуда пришли) и заканчивается крючком (1 предложение: что ещё не так). На телефоне раздел = карточка «Эпизода», поэтому мостик и крючок держат связь между карточками.
3. **В каждом разделе есть «почему»**: не только что делает конструкция, но почему Swift устроен так и что из этого следует.
4. **Одна пауза на вспоминание на урок** — до объяснения, в самом подходящем разделе. Синтаксис:
   ```markdown
   > ? Предскажи, не читая дальше: что напечатают две строки?
   > = `Нора`, потом `Optional("Нора")` — потому что …
   ```
   Строка `> ?` — вопрос, `> =` — ответ сразу под ним (движок прячет ответ под кнопку; пока не умеет — показывает две плашки). Не больше одной паузы: иначе теория дублирует ступень 1.
5. **«Пишем в лоб → ломается → чиним»** — не больше одного раза за урок и только там, где ошибка компилятора или краш сами объясняют «почему». Ошибки — настоящие (дословный текст компилятора).
6. **Объём основы ≤ 1000 видимых слов** (без кода и без «Ответов к „Проверь себя“»). Прирост от мостиков и паузы (~+150 слов) компенсируй: итоговые разделы, повторяющие код, сжимай до правил; повторы между разделами убирай.
7. **Всё, что нужно ступеням, есть в основе** (docs/audit-theory-practice.md): если тема там упомянута — закрой её дыры в этой же правке (коротко в основу, если приём базовый; иначе поменяй ступень).
8. После правки сверь шпаргалку (`ref.cheat[id]`) и «Ответы к „Проверь себя“» с новым текстом; цели и вопросы «Проверь себя» не меняй без причины.

## Ступени (`content/steps/<id>.json`)

Ровно 7 объектов `{id, title, prompt, code, key}` (+ `points` у длинных ключей), `id` = `s1`…`s7`:

```json
{
  "id": "s1",
  "title": "Ступень 1. Предскажи сводку",
  "prompt": "Что будет в counts и names? Почему порядок берётся не из Set?",
  "code": "let authors = [\"Анна\", \"Илья\", \"Анна\"]\n…",
  "key": "Будет 2 и [\"Анна\", \"Илья\"]. …"
}
```

### Пункты к длинному ключу (`points`)

Ключ длиннее 25 строк сверять по памяти нереально, поэтому у такой ступени есть поле `points` — 3–5 коротких обязательных пунктов. Ученик сверяет ответ с ними, полный код ключа остаётся под ними («полный код»).

```json
"points": [
  "`numberOfRowsInSection` → `games.count`.",
  "`cellForRowAt`: `dequeueReusableCell(withIdentifier: \"Game\", for: indexPath)` и `as! GameCell`.",
  "`cell.configure(games[indexPath.row])` — модель берётся по номеру строки.",
  "Строка `IndexPath(row: 1, section: 0)`: «Остров», `.none`, `representedID == 62`."
]
```

1. Пункт — одна строка (можно `код` и **жирный**), проверяемый факт: что обязано быть в ответе. Не пересказ ключа и не «код компилируется».
2. Пункты проверяют суть ступени: новую часть, ради которой ступень есть, а не общий каркас (модели, стек и т. п.), который повторяется во всех ступенях.
3. Порядок пунктов — порядок, в котором это встречается в ответе; итоговая проверка (assert, вывод) — последним пунктом.
4. Сборщик требует 3–5 непустых строк и падает на ключе > 25 строк без `points`; `npm test` (suite `answers`) это проверяет.

Типичная лестница: s1 предскажи → s2–s3 напиши → s4 найди ошибку (часто чинит код s1, это схема «предскажи → почини») → s5 устно → s6 перенос на новый элемент → s7 проверка по памяти.

1. Условие не называет ответ.
2. «Найди ошибку» содержит настоящую ошибку, не заглушку.
3. Не «исправь тестовый JSON» вместо кода.
4. Имена под модель, у свойства и метода разные имена.

## Банк (`content/bank/<id>.bank.json`)

Массив задач; обычно три на тему, id `<topic>-b1…b3`:

```json
{
  "id": "clos-b1",
  "topics": ["clos"],
  "type": "Предскажи вывод",
  "title": "Подтверждение адреса доставки",
  "prompt": "Адрес редактировали после подготовки подтверждения. Какой адрес покажет действие?",
  "code": "var address = \"Дом\"\nlet confirm = { [address] in print(address) }\naddress = \"Офис\"\nconfirm()",
  "key": "Дом\n\n[address] сохранил строку «Дом» при создании…",
  "added": "2026-10-20"
}
```

1. `type`: `Предскажи вывод`, `Допиши`, `Найди ошибку`, `Перепиши`, `Устно`.
2. `added` — дата (по умолчанию 2026-10-11), `mins` — оценка в минутах (по умолчанию 6).
3. id уникальны по всему банку, включая `content/base/bank.json` (общие drills).
4. Файлы читаются по алфавиту, `zz-live.bank.json` последний: 20 задач live (`live-t01…t20`) и `live-b1…b3`.
5. Банк тренирует навык, которого нет в ступенях: три разных экрана, не повторяющие экраны других тем.
6. Повторяющийся каркас (например, стек CoreData) — в урок, в задачах только новая часть.
